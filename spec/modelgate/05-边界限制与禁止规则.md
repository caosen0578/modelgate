# Spec Me2AI · 05 · 边界限制与禁止规则

> **文档性质**：人工编写，AI 严格遵守，每条规则均为红线，不得以任何理由绕过
> **同步说明**：本版已与代码对齐（2026-08）：Boot 3.5.6 / Spring 6.2.11、无 MQ、无 Apollo、mapper/domain 包结构、逻辑删除 /
> 数据源与 Redis 已去 Profile 化直连（无 Venus、无内网 Redis 集群 SDK）/ 全项目不使用环境变量，配置一律 `application.yml` 字面量
> （详见 [11-变更记录 §19](./11-变更记录.md#19-数据源redis-去-profile-化直连配置去环境变量间接层cryptoservice-清理)）

## 1. 功能边界（禁止超范围实现）

| 禁止实现 | 原因 |
|---|---|
| 模型训练、微调、Fine-tuning | 不在本系统职责范围 |
| 用户个人账号体系（登录/注册/密码） | 不是 C 端产品，无用户维度 |
| 跨公司/跨外网访问能力 | 内网网关，不对外暴露 |
| 计费、账单、支付 | v1 不实现，Token 统计仅用于审计 |
| 模型推理能力（直接调用 GPU） | 只做流量转发，不做推理 |
| 多租户/多工作空间 | 单租户内网产品 |
| 前端 SPA 路由（React/Vue） | 管理后台用静态页面（admin.html） |

### 2.3 缓存架构禁令

```
禁止：
  - 在每个业务请求上增加一次 Redis 凭证/授权查询（热路径读取固定为 Caffeine → MySQL）
  - 把 Redis DEL 误当成跨实例 Caffeine 失效通知（当前没有 Pub/Sub）
  - 用手工 getIfPresent + put 替代 Caffeine 原子加载，造成同 key 并发 miss 同时打 DB
  - Redis 配额故障时 fail-close（QuotaFilter 必须按既定策略 fail-open）
  - 使用 spring-data-redis 直连（必须内网 com.pab.framework:redis CacheProvider）
  - 【2026-08-24 新增】使用任何 Lua 脚本：EVAL / EVALSHA / SCRIPT LOAD / SCRIPT EXISTS
  - 【2026-08-24 新增】在 CacheProvider 上增加非 Redis 原生命令的自定义方法
    （如 incrAndExpire、pipeline 批量接口）
```

> **Lua 禁令说明（2026-08-24 内网实测确认）**：内网 Redis **禁用 Lua 脚本**。
> `RateLimitService` 原有的四段脚本与 `CacheProvider.eval` / EVALSHA 优化已整体移除，
> 配额计数改用 `INCR` / `INCRBY` / `GET` / `EXPIRE` 原生命令（见 [11 §29](./11-变更记录.md)）。
>
> 之所以连"自定义方法"一并禁掉：`com.pab.framework.redis.CacheProvider` 在本仓库只是**源码桩**，
> 合入内网时要删桩换成内网 SDK 的同名接口。桩上加一个内网没有的方法，本地能编译、
> 合入内网必然编译失败，且失败点在调用方而不在桩本身，排查成本高。
> **桩上只允许出现 Redis 原生命令的标准签名**（内网 CacheProvider 底层就是 jedis，照抄 jedis 签名即可）。
>
> 直接后果：无法把"INCR + 条件 EXPIRE"合并成一次往返，`QuotaFilter` 每请求 Redis 命令数
> 由 1 条升到最多 3 条。这是硬约束下的既定代价，**不要试图用脚本或自定义方法优化回去**。

## 4. 安全红线

### 4.1 密钥处理禁令

```
禁止：
  - 数据库明文存储任何密钥（上游 API Key / SK、接入凭证，一律 AES-256-GCM 加密）
  - Bearer / api_key 校验解密后比较明文（必须 SHA-256 哈希比对，走 secret_hash）
  - 任何凭证比对使用字符串 equals（必须 MessageDigest.isEqual 常量时间）
  - 日志打印完整 API Key / SK / 密码（末 4 位可见）
  - 加密密钥硬编码在 Java 代码里（必须写入 `application.yml` 字面量配置项 `modelgate.crypto.key`；
    项目禁止使用环境变量间接层，见 [11 §19.3](./11-变更记录.md)——Spring 会用同名环境变量静默覆盖配置文件，
    比硬编码更隐蔽，故不用 `${MODELGATE_CRYPTO_KEY:...}` 这种写法，也不读 `System.getenv`）
  - 列表 / 详情类接口返回密钥密文或明文（含 ModelVO、AppCredentialVO）
```

#### 接入凭证可查看（本轮决策，推翻原"仅创建时返回一次"约束）

> **业务前提**：内网场景，接入系统投产后凭证轮转会中断关联系统的正常业务流程，
> 运维必须能找回既有密钥，而不是只能作废重建。**这是明确的安全取舍，勿擅自改回。**

`mg_app_credential` 对两种类型均在 `secret_encrypted` 留存 AES-256-GCM 密文：

| 类型 | access_key | secret_hash | secret_encrypted |
|---|---|---|---|
| `api_key` | 末 4 位（展示） | SHA-256（鉴权） | 全文密文（查看） |
| `ak_sk` | AK 明文（标识） | SHA-256(SK)（鉴权） | SK 密文（查看） |

```
强制：
  - 明文只允许经 GET /modelgate/credentials/secret 单条按需解密返回
  - 该接口必须打 INFO 日志（谁、何时、查了哪条），供事后追溯
  - Bearer / api_key 鉴权仍走 secret_hash 哈希比对，不得因为有了密文就改为解密比较
禁止：
  - 把 secret_encrypted 或解密结果放进任何列表 / 详情接口
  - 前端缓存明文（取到即用，关闭弹窗须从 DOM 清除）
```

> **`ak_sk` 是例外且必须如此**：HMAC-SHA256 验签需要用 SK 重算签名，
> `CredentialAuthFilter.verifyAkSkHmac()` 必然要解密 `secret_encrypted`——这是算法要求，不是违规。
> 比对结果时仍用 `MessageDigest.isEqual` 恒时比较。**勿把这段代码"修"成哈希比对，会直接破坏验签。**

> **残余风险（已接受，2026-08-17 用户确认维持现状）**：DB 与 `modelgate.crypto.key` 同时泄露时，
> 全部接入凭证一并失守。§19 决策后 `application.yml` 是单一固定文档，数据库连接串（含密码）
> 与加密密钥字面量**同处一份配置文件**——原「密钥必须与数据库分离保管」的缓解手段已不成立，
> 不再假装存在这层防护。当前无替代缓解措施，纯粹接受该风险；文件访问权限收口是唯一现实防线，
> 不属于本项目职责范围。
> 启用本项之前创建的 `api_key` 凭证 `secret_encrypted` 为空，无法找回，只能重新生成。

## 6. Filter 执行顺序保护

> **本条原为「禁止更改任意 Filter 的 order」，本轮经决策解除**：该禁令曾把一个真实缺陷
> 锁死——审计写在 `TraceFilter.doFinally`，而它当时排在鉴权之后（-150），
> 导致 401/403/429 等被拒请求**完全不进审计**。order 应服从实际链路需求，
> 而不是反过来。改 order 前按下列不变量评估即可，不再一刀切禁止。

```
必须满足的不变量（改 order 前逐条核对）：
  - TraceFilter 必须是 GlobalFilter 链的第一个（当前 -200）
      —— 审计在其 doFinally，排在任何拒绝型过滤器之后都会漏掉失败请求
  - CredentialAuthFilter 必须早于一切依赖 appId 的过滤器
      （AppAccessControl / ModelAuth / Quota 均从其注入的 X-Mg-App 取值）
  - BodyParseFilter(-175) 必须早于一切读取 model 字段的过滤器
      （ModelAuth -170 / Quota -160 / ModelRoute -140 读的都是它缓存的 mg.modelId）
  - ModelRouteFilter 之后不得再增加读取原始请求体的 Filter（流已被改写）
禁止：
  - 在 CredentialAuthFilter 之前增加依赖凭证信息的 Filter
  - 在不更新 00/02 两处链路图的情况下改动 order
```

## 6.1 通用服务接入禁令（2026-08-27 新增）

| 禁令 | 理由 |
|---|---|
| **禁止在过滤器里写路径字面量或 `startsWith` 做流量分流** | 判定规则必须只有 `TrafficType` 一个出处。散落各处时加一类流量就要逐个文件改，漏改一处的表现是"某类流量被错误的过滤器拦截或误放行"，极难定位 |
| **禁止把 `TrafficType.of` 的兜底改回 `INTERNAL`** | `UNKNOWN` 必须算业务流量（fail-closed）。路由谓词接受 `/v1` 与 `/v1;a=b/...`，判成 INTERNAL 会让这些能进链的请求跳过全部鉴权。见 02 §3.1 |
| **禁止修改 `mg_service.service_id`** | 它是对外 URL `/svc/{编码}/**` 的一段，改名等于换 URL、接入方必须同步改代码——那是"新建 + 下线"而不是"改名"。管理页面上该字段编辑时置灰 |
| **禁止在 `service-route` 上加 Retry** | 模型侧重试最多是重复计费，通用服务的 POST 是**业务写操作**，重试可能造成重复下单。将来确需重试必须按服务下发，且**显式**写上 `series:` 与 `exceptions:` 置空（默认值是 `[SERVER_ERROR]` 与 `[IOException, gateway TimeoutException]`，不写就会对任意 5xx 与超时都重试） |
| **禁止在 `ServiceRouteFilter` 里读或改写请求体** | 服务链路比模型链路轻一个量级的全部原因就在这里：不缓冲、不解析、不碰 `Content-Length`，原样流式透传。碰了 `Content-Length` 就必须先知道 body 多长，等于把省下的开销全付回去 |
| **禁止让服务侧管理接口与模型侧不同构** | 同一语义的子路径必须用同一个 HTTP 方法，由 `ServiceMirrorsModelTest` 钉住。确需不同的在 `SERVICE_ONLY` 登记理由，不要直接删断言 |
| **禁止管理面列表接口自己拼分页 Map** | 一律返回 `PageVo`。前端 `applyPage` 读的是 `items`/`total`/`pageIndex`/`pageSize`/`pages`，手拼 `records` 会让列表恒空而 `total` 正确——看起来像"数据没存进去"。由 `PageContractTest` 钉住 |
| **服务连通性探测默认 GET，非 GET 需显式登记并警告** | 通用服务的写接口可能真的建一条数据。白名单外的方法一律回落 GET，GET/HEAD 强制不带请求体，非 GET 探测服务端打 WARN 留痕 |
