## 35. 部署文根改为从页面自身路径推导（推翻 §20 的 hostname 判定）

> **一句话**：`CTX_ROOT` 原先按 `location.hostname` **猜**（只要是域名就固定拼 `/backend`），
> 现改为按页面自身所在目录**读**，照抄内网通用库 `pab-gateway-auth.js` 的 `pageBase()`。

### 35.1 现象与根因

域名访问时，管理页成片报错：

```
模型授权 / 服务授权 / 访问控制  →  Required query parameter 'appId' is not present
服务测试工具「开始探测」        →  HTTP 400
SLB 日志：Path=/backend/modelgate/services/test  ctx=/backend
          -> http://127.0.0.1:10811/backend/modelgate/services/test?serviceId=testsse&...
```

**页面本身挂在域名根下，而 JS 按 hostname 硬拼出一段 `/backend`。** 请求于是命中
SLB 的文根规则被转走，应用收到 `/backend/modelgate/...`——而**应用侧根本没有文根配置**
（`server.port: 10811`，application.yml 里没有 `spring.webflux.base-path`，已 grep 确认），
没有任何 handler 匹配。

> 内网参考应用 `user-behavior-track` 同样**没有** context-path（`server.port: 18088`）。
> 即内网约定是：**`/backend` 由 SLB/Nginx 剥掉，服务端永远不知道它存在**。
> 前端该带的前缀，等于**页面自己被挂在哪个目录**——读它一定对，猜它就会错。

### 35.2 改法

```js
const CTX_ROOT = (function(){
  var dir = location.pathname.replace(/[^/]*$/, '');   // '/backend/' 或 '/'
  return dir === '/' ? '' : dir.replace(/\/+$/, '');   // '/backend' 或 ''
})();
```

`isDirectHost()` 随之删除（已无调用方）。`defaultGatewayBase()` 不动，
它取 `location.origin + CTX_ROOT`，自动跟随。

| 页面 URL | CTX_ROOT | 管理接口 | 接入示例网关地址 |
|---|---|---|---|
| `https://域名/backend/admin.html` | `/backend` | `/backend/modelgate/...` | `https://域名/backend` |
| `https://域名/admin.html` | `''` | `/modelgate/...` | `https://域名` |
| `http://内网IP:10811/admin.html` | `''` | `/modelgate/...` | `http://内网IP:10811` |

### 35.3 这次反转推翻了什么，代价是什么

§20 当时**从 pathname 反推改成了 hostname 判定**，理由是"页面在 `static/` 下的存放层级
是前端自己的组织方式，多加一层目录会把静态资源目录拼进接口地址"。

**那个理由成立**，所以代价必须写明：

> ⚠️ **`admin.html` 必须平铺在 `static/` 根目录，不得移进子目录。**
> 移进去（如 `static/pages/admin.html`）会让 `CTX_ROOT` 变成 `/pages`，接口全部 404。
> 内网通用库 `pab-gateway-auth.js` 接受的是同一个约束——这是内网约定的一部分，
> 不是本项目的疏忽。新增管理页一律放在 `static/` 根目录。

两相权衡取 pathname：hostname 判定的失败模式是**部署形态一变就成片 404 且看不出原因**
（本次即是），而 pathname 的失败模式是**一个不会发生的目录调整**，且一旦发生立刻全页报错、
定位成本低得多。

### 35.4 验证

浏览器实测三种部署形态（同一份 admin.html 分别放在 `/admin.html` 与 `/backend/admin.html`，
拦截 `fetch` 取真实 URL）：

### 34.1 模型侧四处现存缺陷（**独立于服务接入，但必须一并合入**）

这四条是评估服务接入方案时顺带查出来的，都在模型转发热路径上：

1. **慢调用熔断把正常长请求判成故障。** `CircuitBreakerFilter`(order -50) 包在
   `NettyWriteResponseFilter`(order -1) 外层，量的是**响应体写完**的时长——一条 1200s 的
   *正常* SSE 流被记成"耗时 1200 秒的调用"。`CircuitBreakerMetrics` 把
   `minimumNumberOfCalls` 裁剪为 `min(100, slidingWindowSize)` = 20，
   于是最近 20 次里 18 次超过 180s 就 OPEN、全部流量 503。
   **改法**：`slowCallDurationThreshold: 24h` 让慢调用率恒为 0。
   ⚠️ **不能靠删掉这两行**——删了退回默认 `100% + 60s`，而判定是
   `slowCallRate >= threshold`，本项目几乎每次调用都超 60s ⇒ 100>=100 照样熔断，比原来更糟。

2. **HALF_OPEN 的 permit 会泄漏，可能永久卡死。** filter 只挂了 `doOnSuccess`/`doOnError`，
   SSE 客户端中途断开走的是 **cancel** 信号，两个回调都不触发 ⇒ permit 有借无还。
   而 `DEFAULT_WAIT_DURATION_IN_HALF_OPEN_STATE = 0`（无自动退出），
   5 个 permit 漏光后熔断器永久停在 HALF_OPEN 拒绝一切流量，**只能重启进程恢复**。
   **改法**：补 `doOnCancel` → `releasePermission()`（不是 onSuccess/onError——
   调用被调用方放弃，上游成没成是未知的）。

3. **Retry 的默认值与注释意图相反。** yml 只写了 `statuses` 和 `methods`，但
   `RetryConfig` 还有未覆盖的 `series=[SERVER_ERROR]` 与
   `exceptions=[IOException, gateway TimeoutException]`——**任意 5xx 和超时都会重试**，
   让上游从头再跑一遍几十秒到 20 分钟的推理。且重试必定失败：
   `ModelRouteFilter` 的 `DataBuffer` 曾在匿名类外复用，第二次拿到已 release 的废 buffer。
   **改法**：删掉整个 Retry 块；DataBuffer 改为每次订阅新建。

4. **`response-timeout` 的真实语义被误解。** `HttpClientFactory` 对 `responseTimeout`
   **零引用**——SCG 从不装配 reactor-netty 的 `ReadTimeoutHandler`；570s 只是
   `NettyRoutingFilter` 里一层 `Flux.timeout`，**计时终点是响应头**。
   ⇒ 流式请求本就不受限；**非流式请求这个值才是它的实际超时**，570s 会把 20 分钟的请求切掉。
   **改法**：放宽到 1800s（不取 -1，保留上游假死时的兜底）。

> 另有 `mg_model.timeout_ms` 是**死字段**（仅管理面探测使用，转发热路径从不读取），
> 且 DDL 默认值 30000 远小于 LLM 实际耗时，贸然启用会全线超时。**本轮不动**，
> 管理页面上应标注"仅用于连通性测试"。详见 12 §8.3。

### 34.2 服务接入的关键取舍

| 取舍 | 理由 |
|---|---|
| **分表而非泛化 `mg_model`** | 模型有 `api_spec`/`default_params`/`force_params`/`param_mapping` 一整套专属字段；且两者路由键本质不同（body 字段 vs path），合表迟早靠 `if(targetType)` 分叉 |
| **固定根前缀 `/svc/{编码}/**`** | 网关必须在**读 body 之前**判定流量类型。允许每服务自定义任意前缀则每请求都要拿完整 path 匹配前缀表，且存在与 `/v1/`、`/modelgate/` 撞前缀的运行时事故风险 |
| **服务链路不读 body、不碰 `Content-Length`** | 这是它比模型链路轻一个量级的**全部原因**。碰了 `Content-Length` 就必须先知道 body 多长，等于把省下的开销全付回去 |
| **配额 key 加 `svc:` 前缀** | 服务编码与 modelId 命名空间独立、可能重名。不加前缀两条链路的计数会串到同一个 Redis key 上，一边的流量吃掉另一边的配额，且监控上完全看不出来 |
| **审计加独立 `service_id` 列而非复用 `model_id`** | 现有用量统计按 `model_id` 分组，复用会让服务调用混进模型用量报表、平均耗时被短请求拉低——报表看着正常但数字是错的 |
| **服务侧熔断按 serviceId 隔离** | 四五个接入系统本就是彼此无关的上游，让 CRM 挂掉去熔断知识库没有道理。模型侧仍是单一全局实例（改成按模型隔离是独立的一项变更） |
| **`service-route` 不配 Retry** | 模型侧重试最多是重复计费，通用服务的 POST 是业务写操作，重试可能造成重复下单 |
| **连通性探测默认 GET、4xx 也判连通** | 通用服务没有统一接口形状，探测打根路径拿到 404 完全正常——那恰恰证明网络与地址都对。判成失败会让运营去改一个本来就对的配置 |

### 34.3 连接池：一个被推翻的风险判断（留档）

方案评估初期判断"模型与服务共用 `max-connections: 500` 会互抢"。
核实 reactor-netty 1.2.10 字节码后**该判断不成立**：
`PooledConnectionProvider.channelPools` 的类型是 `ConcurrentMap<PoolKey, InstrumentedPool>`，
`PoolKey = (SocketAddress, pipelineKey)` —— **连接池按上游地址分桶**，
`max-connections: 500` 是**每个上游 host:port 一份**。
四五个接入系统各有独立域名/端口 ⇒ **天然隔离，零配置**。

> 若将来确需按上游定制限额：reactor-netty 原生提供
> `ConnectionProvider.Builder.forRemoteHost(SocketAddress, Consumer<HostSpecificSpec>)`；
> 接入点是 `HttpClientFactory`（唯一带 `@ConditionalOnMissingBean` 的 bean）。
> ⚠️ **禁止**继承 `NettyRoutingFilter` 覆写 `getHttpClient` —— 它的 bean 定义**没有**
> `@ConditionalOnMissingBean`，会导致两个路由过滤器同时在链上、请求被转发两次。

### 34.8 修复：`upstreamUrl` 自带路径时，服务根被拼出多余尾斜杠

**现象**：服务 `testsse` 上游填 `http://127.0.0.1:9000/chat/completions`，
探测与真实转发都打到 `http://127.0.0.1:9000/chat/completions/`（多一个尾斜杠），
上游 404。而探测结论写的是"上游可达，但上游不认这个路径或方法"——
把一个**网关拼错地址**的问题描述成了接入方的配置问题，运营会去改一个本来就对的配置。

**根因**：`ServiceRouteFilter.resolveRemainder` 在剥完前缀为空时无条件补 `"/"`。
这条规则**只在 `upstreamUrl` 仅到 host:port 时成立**（不补会拼出没有 path 的地址，
有的上游直接 400），`upstreamUrl` 已带业务路径时补了就是错的。
原用例 `remainderNoDoubleSlash` 只覆盖了 host-only 那一半，所以没拦住。

**改法**：把"补不补斜杠"从 `resolveRemainder`（只管剥前缀）里拿出来，
下沉成 `ServiceEntity.joinUpstream(remainder)`，按 `upstreamUrl` 带不带路径分流。

| 位置 | 改动 |
|---|---|
| `ServiceEntity` | 新增 `joinUpstream(String)` + `baseHasPath(String)` |
| `ServiceRouteFilter.resolveRemainder` | `/svc/x` 与 `/svc/x/` 都归**空串**（同一个资源，这里不该有差异），补斜杠交给 `joinUpstream` |
| `ServiceConnectivityService.probe` | 探测路径空 / 裸 `"/"` 统一归空串，改用 `service.joinUpstream` |
| `admin.html` | JS 镜像 `svcJoinUpstream`/`svcBaseHasPath`，两处预览改走它 |

> **探测与转发必须共用同一套拼接**。探测的全部价值就是"它打的地址和真实转发一模一样"，
> 两边各拼各的会产出"探测通了但转发 404"这类最难查的不一致——两个界面各自看都是对的。
> `ServiceRoutePathTest.joinMatchesProbe` 把这条性质钉死了。

**顺带补的管理页提示**：服务弹窗的转发预览新增一行「服务根 `/svc/{编码}` → 实际地址」，
并在 `upstreamUrl` 带路径时给橙色警告——把完整接口路径写进「上游地址」的人
只会调 `/svc/{编码}`，而那正是唯一会因斜杠而 404 的情形，光看原来那行示例路径看不出来。

用例 `ServiceRoutePathTest` 由 16 条扩到 **24 条**，新增三组：
`joinUpstreamHostOnly` / `joinUpstreamWithPath` / `joinMatchesProbe`。

**补漏（同一问题的第三处）**：管理页一共有 **三处**上游地址预览，上一轮只改了两处，
漏掉「凭证 → 接入示例」里的「网关 → 上游」那一行——它自己拼 `{该服务的上游地址} + 剥完的路径`
并把空路径兜底成 `"/"`，于是继续显示带尾斜杠的错地址。
根因是它**拿不到 `upstreamUrl`**，只能打占位符，也就无从判断该不该补斜杠。
改法：`ServiceAuthVO` 补 `upstreamUrl` / `stripPrefix` 两个字段（该 VO 本就联查了
`ServiceEntity`，且服务管理页本来就明文展示上游地址，无新增暴露面），
预览改走 `svcJoinUpstream`，并顺带做到两件原先做不到的事：
显示**真实上游地址**而非占位符、按 `stripPrefix` 真实取值给出说明（原先固定按"剥离"写死）。

> 教训：这类"同一份规则在多处各写一遍"的地方，改的时候要先把**全部副本**找齐再动手。
> 三处副本我第一次只找到两处，第三处是用户用起来才发现的。

### 34.10 修复：模型对话测试与探测共用 15s 超时，慢模型必然超时

**现象**：「模型管理 → 🧪 测试」测 DeepSeek-V3 返回
`连接超时（超过 15000ms）：上游无响应，请检查地址与网络策略`，
而同一个模型走「接入示例」是通的。

**先排除了一个误判**：报告时怀疑是 `bcb5183`（admin.html 分区重构）引入的。
用"忽略注释与顺序后比较全部可执行代码行的多重集合"核对 `29dc960` → `bcb5183`，
两侧差集均为 **0 行**——那次重构是严格的纯移动，与本问题无关。

**根因**：`ModelConnectivityService.exchange` 被 `probe()` 与 `chat()` 共用，
超时统一取 `probeTimeoutMs = min(timeout_ms, 15_000)`。但两条通道的语义完全不同：

| 通道 | 请求体 | 等的是什么 | 15s 够不够 |
|---|---|---|---|
| `probe()` 探测 | `max_tokens=1` 的最小请求 | 连不连得上 | 够 |
| `chat()` 对话测试 | 管理页表单，默认 `max_tokens=1024` | 模型把整段结果**生成完** | **远远不够** |

接入示例走网关（`response-timeout: 1800s`）所以通——两条路径的超时差了两个数量级。
报错文案又写的是"请检查地址与网络策略"，把排查方向往网络上带。

**改法**：两条通道的超时彻底分开。

- `chat()`：默认 120s、上限 300s；等待发生在 WebClient 事件循环上，**不占 `AdminScheduler` 名额**
- `probe()`：维持默认 10s、上限 15s（探测放长了只是让人对着转圈等）
- 超时文案按通道分开：对话测试说明"本通道返回聚合响应、慢模型容易超时、可调小 max tokens
  或改用接入示例"，不再让人去查网络
- 管理页测试弹窗的占位文案补上超时上限与替代路径

### 34.11 新增：报文回放（报文记录 → ▶ 回放）

## 33. 修复：调用方凭证被原样转发给上游模型厂商

> **性质：安全缺陷修复**，非新功能。在评估「SSE 接口接入网关鉴权」方案时顺带发现——
> 该方案要求"网关把调用方凭证换成上游凭证"，核对现状时发现模型侧这个"换"只做到了一半。

### 33.1 问题

`ModelRouteFilter`(-140) 构造上游请求头的写法是：

```java
merged.putAll(super.getHeaders());   // 调用方原始头，含 Authorization
merged.putAll(info.headers());       // 适配器注入的上游凭证
```

**去除调用方凭证这件事，完全依赖"上游凭证恰好同名、把它覆盖掉"。** 实际只有一种 api_spec 满足：

| api_spec | 适配器注入的头 | 调用方 `Authorization` |
|---|---|---|
| `openai` | `Authorization: Bearer`（`setBearerAuth`） | ✅ 被覆盖 |
| `azure_openai` | `api-key` | ❌ **原样转发到上游** |
| `anthropic` | `x-api-key` | ❌ **原样转发到上游** |
| `custom` + `ak_sk` | `X-Access-Key` / `X-Secret-Key` | ❌ **原样转发到上游** |

全局也没有任何 `RemoveRequestHeader` 兜底（`application.yml` 的 `default-filters` 只有
`DedupeResponseHeader`）。

**后果**：调用方带的是 `mg_app_credential` 里的**本网关**凭证，它被明文发给了上游模型厂商；
上游拿这把 key 可以反过来调用本网关。同时 `X-Mg-App` / `X-Mg-Cred-Type` 这两个纯内部传参
也一并出网，白白泄露实现细节。

### 33.2 为什么可以直接删，不存在"透传模式"被打断

调用方那把 key 由 `CredentialAuthFilter`(-190) 对着 `mg_app_credential` 校验，**它对上游本来就没有意义**；
上游要的凭证一律来自 `mg_model_credential`、由适配器注入。所以不存在"某些模型靠透传调用方 Authorization 鉴权"
这种配置——那样根本调不通。

`X-Mg-*` 的三个读取方（`AppAccessControlFilter`/-180、`ModelAuthFilter`/-170、`QuotaFilter`/-160）
**order 全部早于 -140**；`TraceFilter` 的 `doFinally` 取的是 exchange attribute 而非请求头。删掉不影响任何下游逻辑。

**报文留档不受影响**：`PayloadCaptureFilter`(-145) 快照的是**入站**请求头，早于本过滤器，
排障时仍然能看到调用方带了什么。

### 33.3 改法

剔除必须**夹在两次合并之间**，三步顺序不能调整：

- 放到最前 → 会被 `putAll(inbound)` 重新带回来
- 放到最后 → 会把适配器刚注入的上游 `Authorization`（OpenAI 路径）一起删掉，上游 401

同时把这段逻辑从匿名 decorator 里抽成静态方法 `buildUpstreamHeaders(...)`，
否则这条安全属性不起一整套 exchange 就没法测。

剔除清单 `INBOUND_ONLY_HEADERS = [Authorization, X-Mg-App, X-Mg-Cred-Type]`。
`HttpHeaders` 底层是 case-insensitive map，与调用方大小写无关。

### 33.4 回归

新增 `ModelRouteHeaderTest`（main 方式，与既有测试一致），16 条断言全通过，覆盖：

- 四种 api_spec 逐一确认"上游凭证在、调用方凭证不在"
- 业务头（`X-Tenant-Id`、SSE 的 `Accept: text/event-stream` 等）不被误伤——剔除清单写宽了
  会表现为"某些请求上游行为异常"，极难定位
- 调用方用小写 `authorization` / `x-mg-app` 同样被剔除
- `Content-Length` 取改写后的长度

> **新增适配器时**：照抄 33.4 里那条 api_spec 用例，钉住同一条属性。

## 32. 审计日志 / 报文记录增加 appId 与应用编码筛选

> **需求**：审计页与报文页此前只有一个「接入系统」下拉可用，排查时手上直接有的
> appId / 应用编码反而没有入口。

### 32.1 应用编码怎么落地：不动热路径

`mg_audit_log` 与 `mg_request_payload` 里**只有 `app_id`，没有 `app_code`**。两条路：

| 方案 | 结论 |
|---|---|
| 把 `app_code` 冗余进这两张表 | ❌ **否决**。要改 DDL，且采集侧（`TraceFilter` / `AuditService` / `PayloadService`）每请求都要多拿一次应用编码——**违反"不为管理功能增加每请求解析或数据库操作"** |
| 查询时在 `mg_app` 把编码解析成一组 `app_id`，再 `app_id IN (...)` 查大表 | ✅ **采用** |

新增 `service/AppScopeResolver`，被审计 / 报文 / 用量统计三个 Controller 共用。
**转发热路径零改动**，多出的一次小表查询只发生在管理员点「查询」时
（`mg_app` 行数 = 接入系统数量，内网个位数到百级）。

### 32.2 语义（每一条都对应一个具体的坑）

- **精确匹配，不做模糊**。编码不是名称，用户手里就是完整值；做成 `LIKE` 会让
  `appCode=CRM` 顺带命中 `CRM_TEST`，把两个系统的流量混在一起看，**比查不到更糟**。
- **一个编码可能对应多个 appId**：`mg_app` 唯一键是 `app_id`，`app_code` 只做"系统内唯一"，
  不同 `sys_code` 下可以重名。所以解析结果是一组，不能想当然当成一个。
- **与 appId 同时给出取交集**（AND），不是二选一忽略其一。忽略其一会让页面显示的条件
  与实际执行的查询对不上。
- ⚠️ **编码查无应用 / appId 与编码矛盾 → 直接返回空页，不查大表。**
  这一分支**绝不能**退化成"不加 app 过滤"——那会把全部系统的数据当成该编码的数据返回。
  报文里是用户原始 prompt，这种越界展示比查不到严重得多。三个 Controller 都显式处理了这一分支。
- 单编码解析出 >200 个 appId 时报错要求补 appId：`IN (...)` 过长会让 MySQL 放弃
  `idx_app_id` 改走全表扫描。
- **`appCode` 不算模糊关键字的收窄条件**（与 `appId` 同档）：它最终就是被翻译成一组 appId，
  收窄能力只会更弱。`PayloadQueryBO.hasNarrowingFilter()` 逻辑未变，只补了说明。

### 32.3 用量统计必须一起改（否则卡片会骗人）

`GET /modelgate/stats/usage` 同步新增 `appCode`。审计页顶部四个卡片和下方列表用的是
同一组筛选条件，**卡片少支持一个条件，用户就会拿"全量汇总"去解释"按编码筛出来的列表"**，
拿着错误的数字对账。两者共用同一个 `AppScopeResolver`；编码查无应用时卡片直接归零、不查库，
与列表返回空页保持一致，避免"卡片有数、列表为空"的自相矛盾。

- `AuditLogMapper.selectUsageStats` 的 `appId` 单值参数改为 `appIds` 列表
  （`@Select` 加 `<script>` + `<foreach>`）。**没有新增第二个方法**——两份几乎相同的 SQL
  是后续行为漂移的现成温床。

### 32.4 前端：下拉与输入框谁是真值

两个控件提交同一个后端参数，必须只有一个是"真值"，否则会出现
"下拉显示 A、输入框写着 B、实际查的是 B"这种对不上的状态。约定：

- 「接入系统」下拉**只是挑选器**，`onchange` 把 appId 回填到输入框；**输入框是唯一提交来源**。
- 手输 appId 后若与下拉选中值不一致，下拉自动复位为「全部系统」。
- 之所以保留下拉又加输入框：下拉一次只拉 200 个应用（`pageSize=200`），
  应用多了想筛的那个可能压根不在里面；而排查时手上通常直接就有 appId / 应用编码。
- `resetPayloadFilters` 与 `payloadToAudit` 同步清空新控件。
  **`payloadToAudit` 这处最容易漏**：按 traceId 跳转时若不清 appId/appCode，
  两者会取交集，表现为"点了跳转却什么都没有"，而用户并不知道是被上一次筛选挡掉的。

## 31. 去 Lua：配额计数改用 Redis 原生 INCR / INCRBY / EXPIRE

> **触发原因**：2026-08-24 内网验证发现**内网 Redis 禁止使用 Lua 脚本**。
> 本项目所有 `EVAL` / `EVALSHA` 调用在内网必然直接报错，配额限流整条链路不可用
> （会全部走 `catch` 分支 fail-open，表现为**配额彻底失效但只有 WARN 日志**，
> 是最难被发现的一类故障）。故整体去 Lua。

### 31.1 改动范围

全仓只有两处用到 Lua，已全部清除：

| 位置 | 原实现 | 现实现 |
|---|---|---|
| `RateLimitService` | 4 段 Lua：`RATE_LIMIT_SCRIPT` / `MONTHLY_GET_SCRIPT` / `MONTHLY_INCRBY_SCRIPT` / `COMBINED_QUOTA_SCRIPT` | 全部删除，改 `INCR` / `INCRBY` / `GET` / `EXPIRE` 原生命令 |
| `RedisConfig.JedisCacheProvider.eval` | EVALSHA + NOSCRIPT 回退 EVAL（§26.10 的优化） | 整个方法删除，新增 `incr` / `incrBy` / `expire` |
| `CacheProvider`（源码桩） | 声明 `eval(script, keys, args)` | 删除 `eval`，新增 `incr` / `incrBy` / `expire` |

**不受影响**：`DynamicTaskScheduler` 的分布式锁走 `SET NX EX`（`CacheProvider.set`），
`GatewayCacheManager` 走 `get/setex/del`，两者本就不是 Lua。

### 31.2 去掉 Lua 之后原子性为什么仍然成立

这是本轮最需要说清楚、也最容易在后续改动中被破坏的一点。原先用 Lua 只为两件事：

1. **计数本身的原子性** —— 由 `INCR` / `INCRBY` **单命令**保证。Redis 单线程执行单命令，
   多实例并发不会丢计数。**这一条从来就不需要脚本**，Lua 在这里是多余的。
2. **"首次写入才设 TTL"这个条件判断** —— 挪到客户端：`INCR` 返回 1 时再发 `EXPIRE`。
   两步之间不再原子，最坏情况是**进程在 INCR 之后、EXPIRE 之前挂掉，留下一个没有 TTL 的 key**。

   **该残留不会造成配额判定错误**，因为三种 key 的名字里都带时间桶后缀：
   QPS key 带秒级时间戳、日 key 带 `yyyy-MM-dd`、月 key 带 `yyyy-MM`。
   下一个时间窗口用的是**另一个 key**，孤儿 key 再也不会被读到，只白占一点内存
   （量级：一次非正常退出最多泄漏 3 个 key）。

> ⚠️ **这是整个方案成立的前提，已写进 `RateLimitService` 类注释**：
> **若将来把时间桶从 key 名里去掉、改成靠 TTL 滚动窗口，上述结论立刻失效，必须重新设计。**

**为什么不无条件 `EXPIRE`**（那样能彻底杜绝孤儿 key）：稳态下每次计数都要多一次连接借还，
而热路径每请求走三层配额，代价直接乘三。用"孤儿 key 只泄漏内存、不影响正确性"换掉这个开销。

### 31.3 热路径代价（必须知道的回退）

`QuotaFilter` 每请求的 Redis 命令数：

| | 原（Lua） | 现（原生命令） |
|---|---|---|
| 稳态 | 1 次 `eval` | 最多 3 次（QPS `INCR` + 日 `INCR` + 月 `GET`） |
| 每个时间窗口的首个请求 | 1 次 | 额外各 1 次 `EXPIRE` |

- **短路语义与 Lua 版逐字一致**：QPS 超限就不再触碰日计数器，日超限不再触碰月计数器。
  顺序不能改——改了会让被限流的请求也白白消耗日配额。已由回归测试 ④ 专门守住这一条。
- 三个上限都 ≤0（全不限）时**一条命令都不发**，语义不变。
- 代价的实质不在端到端延迟（LLM 请求本身几十秒，几次内网 RTT 可忽略），而在
  **Jedis 同步阻塞客户端的连接借还次数由 1 升到最多 3**。
  这直接冲抵了 §22.4 / §26.10 两轮针对 Redis 往返做的优化，
  **下一轮压测必须重点看 Jedis 连接池水位**（已写入 [09 §D](./09-压测方案.md)）。
- **无法再压缩**：合并成一次往返需要在 `CacheProvider` 上加非原生方法或 pipeline 接口，
  而该接口是源码桩、合入内网要换成内网 SDK 的同名接口，加了内网没有的方法必然编译失败。
  禁令已写入 [05 §2.3](./05-边界限制与禁止规则.md)。

### 31.4 桩接口签名依据

内网 `CacheProvider` **底层就是 jedis**（2026-08-24 用户确认），故三个新增方法逐字照抄 jedis 3.x 签名：
`Long incr(String)`、`Long incrBy(String, long)`、`Long expire(String, int)`。
返回 `Long` 而非 `long`、`expire` 的 TTL 用 `int` 而非 `long`，都是为了删桩后不因拆装箱或
宽化转换而对不上。

### 31.5 顺带清理的死代码

`RateLimitService` 的 `isQpsAllowed` / `isDailyAllowed` / `checkMonthlyTokens` **零调用方**
（`QuotaFilter` 自 §22 起改走 `checkAllQuotas`，这三个方法就此悬空）。
本轮一并删除——否则等于要维护两套语义相同、实现却各自独立的非 Lua 计数逻辑，
是后续行为漂移的现成温床。`TraceFilter` 里引用旧方法名的注释同步修正。

### 31.6 回归验证

- 删除 `EvalShaTest`（验证的 EVALSHA 链路已不存在）。
- 新增 `QuotaCounterTest`（同样 `main()` 风格、打真实 Redis、连不上则跳过），
  **18 项全部通过**，覆盖最容易回归的几点：
  1. `INCR` 首次返回 1 且 TTL 被补上（不补 TTL 会让日/月计数器永不重置）
  2. 非首次不重复 `EXPIRE`，TTL 继续倒数（刷新 TTL 会让窗口无限后延、日配额形同虚设）
  3. 超限判定用 `>` 而非 `>=`：limit=N 时第 N 个放行、第 N+1 个才拒
  4. **三层短路**：QPS 超限时日计数器不能被 `INCR`
  5. 三项全不限时不产生任何 key
  6. `INCRBY` 首次写入补 TTL、累加正确、月配额达上限即拒
  7. 日计数器 TTL 指向当天结束
- QPS 用例在执行前自旋到刚过整秒再开始，避免三次调用跨秒落到两个 key 上导致偶发失败。
- `RedisConfig.JedisCacheProvider` 由包级私有改为 `public`，供测试直接构造真实实现
  （本项目不引入 Mock 框架，验证配额计数必须用真连接）。

### 31.7 文档同步

09（压测参数表、Redis 监控项、热路径成本、故障注入说明）、10（§1 资源清单去掉"需支持 Lua"）、

## 28. 模型 ID 语义收口与上次改动复审

### 28.1 最终业务约束（不得再次混淆）

| 字段 | 含义 | 使用位置 |
|---|---|---|
| `model_id` / `modelId` | ModelGate 对调用方暴露的路由 ID，可按业务需要创建或修改 | 入站鉴权、模型授权、限流配额、审计与报文检索 |
| `upstream_model_id` / `upstreamModelId` | 模型供应商提供的真实模型 ID；留空表示与 `modelId` 相同 | 发往模型供应商的请求体 `model` |

同一个真实模型可以建多条 `mg_model`，各用不同对外 ID 和上游地址、共同填写同一个
`upstream_model_id`。响应由供应商原样返回，**不把响应里的模型 ID 换回对外 ID**。

### 28.2 本次确认并修复的遗漏

1. `POST /modelgate/models/chat/test` 原先在 Controller 中执行 `body.put("model", modelId)`，
   明确把对外 ID 发给了供应商。现改为查库后由服务端解析真实上游 ID并强制覆盖；浏览器传入的
   `body.model` 不具有决定权。
2. 列表“连通性测试”构造的最小探测体同样误用 `modelId`，现改用 `upstreamModelId`（空则回退）。
3. 页面草稿明明提交了 `upstreamModelId`，但 `TestConnectionRequestBO` 没有该字段，Jackson 接收后被吞掉；
   同时草稿也漏了 `defaultParams/forceParams`。三项均已接通。
4. `ModelConnectivityService` 只调用供应商适配器，跳过了 `RequestParamMerger`，所以模型测试没有验证
   `default_params / force_params / param_mapping / upstream_model_id` 的真实行为。现与业务转发统一为
   **参数合并 → 供应商适配**，避免“测试通过、正式调用却变样”。
5. Anthropic 适配器缺少 `model` 字段时的 fallback 仍取对外 ID，现统一走
   `ModelInstanceEntity.resolveUpstreamModelId()`。
6. 上次“模型 ID 可修改”只清模型和凭证缓存，漏了外键级联修改后的 App 授权缓存；新 ID 可能在
   60 秒 TTL 内被误判未授权。现改名前先收集受影响 appId，提交后逐一失效。
7. 模型主表更新、凭证更新之前没有事务，后半段失败可能留下半完成配置。创建、更新、删除现使用
   `@Transactional(rollbackFor=Exception.class)`；缓存只在 `afterCommit` 后失效，避免并发请求在提交前
   把旧数据库值重新装入缓存。
8. 完整建表脚本漏同步两个 `ON UPDATE CASCADE`，虽然增量脚本已有，拿全量脚本新建库仍无法改名。
   `modelgate_schema.sql` 与接口数据结构文档现已补齐；文档中的模型/模型凭证唯一键也同步为实际使用的
   `(model_id, is_del)`，避免逻辑删除后无法按同名重建。
9. 模型 ID 放开编辑后，列表仍把 modelId 直接拼进 inline `onclick`，引号会让按钮失效并形成 DOM 注入面；
   同时启禁/删除请求未 URL 编码。现统一使用 JSON 字符串参数转义、显示值 HTML 转义和
   `encodeURIComponent`。
10. 从禁用模型行打开测试弹窗时，异步加载“仅启用模型”下拉会悄悄把目标换成第一条启用模型。
    连续打开 A/B 两条时，A 的慢请求还可能后返回并覆盖 B。现固定保留用户点击的原模型，
    并用加载序号丢弃过期响应，禁止测试错对象。
11. `param_mapping` 若把 `model` 改名为 `deployment`，旧顺序会先映射、再补回真实 `model`，结果同时出现
    两个身份字段且目标值仍可能是对外 ID。现固定顺序为
    `default → force → upstreamModelId → mapping`；模型身份也不再允许被 `force_params.model` 覆盖。
12. 原参数合并器遇到任一非法 default/force/mapping JSON 时会整段回退原报文，连
    `upstreamModelId` 改写也一并取消。现改为逐项解析、坏配置只忽略本项；请求体本身异常且已有字节偏移时，
    降级路径仍执行模型 ID 定点替换，避免普通参数配置错误改变路由身份。
13. 可编辑模型 ID 不只出现在模型列表，还进入模型授权表、授权启禁/撤销 URL、接入示例下拉和审计表。
    这些消费点原先仍有未转义 HTML/inline handler 或未编码 query 参数，现全部按上下文使用
    HTML 转义、`jsArg` 和 `encodeURIComponent`，避免自定义 ID 含特殊字符时页面失效或形成注入面；
    接入示例中的 curl/Python 模型 ID 也分别按 POSIX shell/Python 字符串规则转义；同时把授权空态行的
    `colspan` 从 8 校正为实际 9 列。
14. 编辑已有模型但不重填密钥时，保存前“测试连通”原先会丢弃整个表单 body，实际测试数据库中的旧地址、
    旧上游 ID 和旧参数。现始终提交当前草稿，由后端仅补入已保存的解密密钥；`authType=none` 明确清空
    历史 AK/SK。草稿与缓存凭证使用不同对象，且凭证 modelId 跟随当前草稿，避免测试操作意外修改
    Caffeine 中的可变实体或在改名草稿中保留旧 ID。
15. 最小探测体原先用字符串拼接 model ID，自定义 ID 含引号或反斜杠时会生成非法 JSON；现使用 Jackson
    节点构造并序列化，管理面测试可正确处理合法的任意字符串 ID，且不进入业务热路径。
16. 模型保存与草稿测试原先把含明文上游 SK 的对象直接写浏览器 console，对话测试也展开完整 prompt；
    探测失败时服务端还会记录默认最长 1 MiB 的上游正文。现统一为凭证脱敏、对话仅记录字段名，服务端失败
    日志只记录正文字符数；完整响应仍仅返回当前管理页面供排查。
17. 测试弹窗把 stream 控件禁用并强制非流式，但响应占位文案仍声称支持实时流式显示；现已改为与实际
    行为一致，避免管理员误判测试能力。
18. 模型改名级联升级脚本仍写着“旧 ID 立刻 404”并带本地测试库行数；同一张表还拆成两条 ALTER，
    存在短暂无外键窗口。现移除环境绑定数字，把每张表的 DROP+ADD 合并为单条 DDL，并明确 metadata lock、
    两张表非跨表原子、配额重置和多副本 TTL，要求在维护/低流量窗口暂停模型管理写操作后执行。
19. `force_params.model` 已不具备模型身份语义，但管理页/API 仍会接受并显示保存成功，形成新的“死配置”。
    现由页面提前提示、创建/更新/草稿测试 API 二次校验并明确返回 400；运行期仍强制以
    `modelId/upstreamModelId` 为准，防止历史数据或直接 SQL 写入绕过管理面后改变路由身份。
20. 三个参数字段原先允许非法 JSON、数组或无效 mapping 目标保存，直到每个业务请求运行时才 WARN 并忽略。
    现由页面和管理 API 在写入/草稿测试时校验“非空值必须是 JSON 对象”，并要求 mapping 目标为非空字符串；
    运行期容错继续保留，专门保护历史脏数据，校验不进入 `/v1/**` 热路径。
21. 新增模型草稿只填上游地址、未填 `modelId` 时，旧逻辑仍会构造 `model=""` 并请求真实生产上游。
    现允许编辑草稿从 query 原 ID 回退定位，但新增草稿没有任何可用 ID 时明确返回 400，不再发送无效探测。
22. 投产前巡检最初写成 `JSON_VALID(x) AND JSON_CONTAINS_PATH(x,...)`，隐含依赖 SQL 条件短路；
    优化器不保证该求值顺序，历史非法 JSON 可能让巡检自身报错。现用 `CASE` 先替换非法值再检查路径。
23. 复审事务装配时发现应用显式排除了 `DataSourceTransactionManagerAutoConfiguration`，项目内也没有任何
    `PlatformTransactionManager`；仅给 Service 加 `@Transactional` 会在运行期无事务可用。现由
    `TdsqlMybatisPlusConfig` 显式注册绑定 `tdsqlDataSource` 的 `tdsqlTransactionManager`、启用事务代理，
    并在模型写方法上按名称指定，避免内网将来出现多数据源后误选。
24. **改名会连带改掉「上游收到的模型身份」**（本轮复审新发现）。
    `resolveUpstreamModelId()` 在 `upstream_model_id` 为空时回退成 `model_id`，
    因此一个上游 ID 留空的模型，改名前上游收到旧 ID、改名后**直接变成收到新 ID**。
    而运维改名的本意通常只是换**对外那个标签**（例如绕开平台「模型 ID 重名」限制），
    上游根本不认识新名字——结果是改完之后该模型的**每一个请求**都被上游拒绝，
    且链路上没有任何一层会报错，只能靠上游返回的 model not found 反推。
    当前库里 `deepseek-ai/DeepSeek-R1` 的 `upstream_model_id` 正是空值，改名即命中。
    现在改名时若提交的上游 ID 为空，自动回填为**改名前的 ID**，让上游收到的字节一个都不变；
    提交值非空则尊重运维的显式选择（想让上游一起改名就显式填新 ID）。
    取值规则抽成 `ModelService.resolveUpstreamIdOnRename` 并由 `ModelServiceRenameTest` 单独回归——
    这条规则写反没有任何运行期信号，必须靠用例钉住。页面确认框同步列出该项。
25. `GatewayCacheManager` 已按真实代码纠正为 Caffeine → MySQL、无 Redis L2/广播，但 README、
    两份架构图、`CredentialService` 注释及 01/02/05/06/10 权威与运维文档仍残留“两级缓存 + L1 miss 拒绝”，
    甚至把 Druid 写成 HikariCP。现统一同步为真实生产链路、原子回源和多副本 TTL 边界；
    本轮只纠正文档与注释，不给 `/v1/**` 增加 Redis 调用。
26. 模型新增/更新请求发生网络异常或返回非 JSON 时，管理页原先会落入 Demo 分支、在本地数组伪造更新并提示
    “模型已更新（演示）”；启禁/删除也吞掉异常后照样提示成功。外键、事务或网络故障因此可能被运维误认为
    已落库。现三类模型写操作都只以服务端成功响应为准，失败时保留表单并明确提示，不再伪造生产状态。
27. 测试响应虽然已把展示上限从 500 字符放宽到 1 MiB，但 `WebClient` 默认约 256 KiB 的聚合解码上限
    会先抛 `DataBufferLimitException`，配置名义上放宽、实际上仍看不到大响应。现只给管理员手动测试构造的
    WebClient 实例按 UTF-8 最坏 4 字节/字符放宽 buffer，并把可配置展示上限硬性收敛在 4 MiB 字符内，
    防止误配置造成超大堆分配；不修改共享 Builder、不进入业务转发。新增 300 KiB 假上游回包回归。
    同时浏览器控制台不再打印完整上游正文，只保留状态、延迟和字符数。

### 28.5 数据库与合入要求

本节**没有新增增量 SQL**，但目标库必须已经执行：

1. `sql/upgrade_20260819_upstream_model_id.sql`：增加上游真实模型 ID 列；
2. `sql/upgrade_20260819_model_id_cascade.sql`：两个模型外键改为 `ON UPDATE CASCADE`。

第 2 个脚本会执行外键 DDL并可能等待 metadata lock；两张表之间不具备跨表原子性。生产须在维护/低流量
窗口暂停模型管理写操作，执行后确认两条 `UPDATE_RULE` 均为 `CASCADE`，再开放模型 ID 编辑。

投产前还要执行以下只读巡检；若有结果，把 `force_params.$.model` 迁入 `upstream_model_id`
并删除 JSON 中的 model 键，避免旧临时写法被误认为仍生效：

```sql
SELECT model_id, upstream_model_id, force_params
  FROM mg_model
 WHERE is_del = '0'
   AND JSON_CONTAINS_PATH(
         CASE WHEN JSON_VALID(force_params) THEN force_params ELSE '{}' END,
         'one', '$.model');
```

这里用 `CASE` 先把历史非法 JSON 替换为空对象；不能依赖 `JSON_VALID(...) AND ...` 的书写顺序，
SQL 优化器不保证短路求值，否则巡检本身可能被一条脏数据打断。

完整新建库直接使用已同步的 `sql/modelgate_schema.sql`。历史审计和报文不做回填、不随模型改名。

### 28.6 模型改名的生产边界（页面已显式告警）

1. 配额 Redis key 带对外 `modelId`。QPS 旧键约 2 秒自然失效；日调用量和月 Token 不做在线搬迁，

   窗口操作，优先新建一条模型并逐步切换调用方。
2. 当前缓存读取路径是各 JVM 的 Caffeine → MySQL，没有 Redis Pub/Sub 失效广播。管理请求所在实例在
   事务提交后立即清缓存；其他副本按模型/上游凭证 30 秒、App 授权 60 秒 TTL 收敛。此前代码注释所称

   视为已启用 L2。注释现已按真实调用链纠正，生产操作按最长 60 秒窗口预留。

### 27.2 实现

新增 `RequestParamMerger`，在 `ModelRouteFilter` 调适配器<b>之前</b>统一应用。
不写进各个适配器，是因为这三项是<b>模型级</b>配置、与 api_spec 无关，
写进适配器要在 4 个实现里各写一遍，迟早写歪。

| 字段 | 语义 |
|---|---|
| `default_params` | **业务可覆盖**：仅在请求体里没有该字段时写入 |
| `force_params` | **业务不可覆盖**：无条件覆盖同名字段 |
| `param_mapping` | **字段改名**，仅 `api_spec=custom` 生效；目标键已存在时跳过并告警，不静默覆盖 |

应用顺序 **default → force → 上游真实模型 ID → mapping**。mapping 放最后是因为它改的是<b>键名</b>，
必须等键值都确定后再动，否则 force_params 里写的是原名、改名后就落不上了。

顺序上还有一条：**先合并、再交给适配器**。反过来的话，适配器可能已经删掉了某些字段
（如 `AzureOpenAIAdapter` 会 `remove("model")`），配置就落在了会被删掉的字段上。

**性能**：三项都为空且上游 ID 留空/等于对外 ID 时（绝大多数模型）直接返回
<b>同一个数组引用</b>，不解析、不分配；只配置不同上游 ID 时走字节级定点替换。
有专门的用例断言引用相等来守住这条快路径。只有真正配置参数字段的模型才付
「解析 + 重新序列化」的代价。

管理 API 会在写入时拒绝非法配置；对历史脏数据或直接改库，运行期按字段逐项解析，
写错的一项只被忽略并打 WARN，其他参数和上游模型 ID 仍继续生效。请求体本身无法解析时才降级；
若已有 model 字节偏移，降级仍优先完成真实模型 ID 的定点替换。

### 27.3 ⚠️ 这是行为变更，重启前必须处理

接线意味着**库里已经填着的值会在重启后立刻开始生效**。巡检发现两条：

```
deepseek-ai/DeepSeek-R1   force_params = {"max_tokens": 512}
deepseek-ai/DeepSeek-V3   force_params = {"max_tokens": 512,"stream": true}
```

原样生效的后果：
- `max_tokens=512` **强制覆盖**调用方的值 → 所有回答截断在 512 token，
  对话系统上表现为「模型说到一半就没了」；
- `"stream": true` **强制把所有请求变成流式** → 非流式调用方期望 JSON 却收到 SSE，
  客户端多半直接解析失败。

从取值看（512 这种小值、强制 stream）更像早期联调的测试残留而非生产管控策略。
处理选项见 `sql/upgrade_20260819_force_params_review.sql`（清空 / 改值 / 保留，三选一）。

### 27.4 模型 ID 改名：早期临时方案（已被 §27.5 / §28 废止）

> 本小节记录当时的推导过程，**不再是当前配置方法**。当前必须填写专用
> `upstream_model_id`；`force_params.model` 不再具有修改模型身份的权限。

用户的场景：同一个真实模型部署在两个平台（两个域名），但平台以「模型 ID 重复」为由
拒绝新增第二个模型地址，因此需要网关对外暴露不同 ID、转发时改回真实 ID。

当时曾用以下临时方式满足：

```sql
UPDATE mg_model SET force_params = '{"model": "deepseek-ai/DeepSeek-V3"}'
 WHERE model_id = 'deepseek-v3-platform-b';
```

- 对外 ID 与上游 ID 完全解耦，调用方无感知
- 同一真实模型可挂任意多个对外 ID（多建几条 `mg_model`，各自独立 `upstream_url`）
- 审计与配额仍按**对外 ID** 统计，账不会乱
- 响应体里的 `model` 是上游返回的真实 ID，**不做反向替换**（已与用户确认不需要）

代价：配了 force_params 的模型每请求多一次「解析 + 重新序列化」。若将来在大 prompt 上
发现这笔开销不可接受，可以再加一个专用的 `upstream_model_id` 列走<b>字节级定点替换</b>
（利用 BodyParseFilter 流式扫描时顺带记下的 model 值字节偏移，一次 arraycopy 搞定，
不解析不建树）——但那是优化，不是必需。

### 27.5 新增专用字段 `upstream_model_id`（页面同步）

§27.4 说过 force_params 写 `{"model":"真实ID"}` 就能改名。用户追问「页面没加呢」——
这个反问是对的：**把「路由身份」塞进「强制参数」语义不清**，运维想不到去那里配，
模型列表展示不出映射关系，也无法校验。故单列一个字段。

| | 位置 |
|---|---|
| DDL | `mg_model.upstream_model_id VARCHAR(64) NULL`（`upgrade_20260819_upstream_model_id.sql`） |
| 实体/BO/VO | `ModelInstanceEntity` / `Create`+`UpdateModelRequestBO` / `ModelVO` |
| 页面 | 模型表单「上游真实模型 ID」，紧跟模型 ID 之后；含详情展示、编辑回显、清空重置 |
| 运行期 | `RequestParamMerger` |

**模型身份只由 `model_id / upstream_model_id` 决定**——即使后者留空回退前者，
`force_params.model` 也不能覆盖。custom 字段映射在身份值确定后执行。

#### 性能：三条路径

| 情况 | 代价 |
|---|---|
| 什么都没配（绝大多数模型） | **零**，返回同一个数组引用 |
| 只需改模型 ID | **一次 arraycopy 拼接**，不解析不建树不序列化 |
| 还配了 default/force/mapping | 复用那次已经付过的解析，改名不额外收费 |

定点替换靠的是 `BodyParseFilter` 流式扫描时**顺带记下**的 model 值字节偏移
（`mg.modelValueStart` / `mg.modelValueEnd`）——parser 此刻正停在该 token 上，取位置零成本。
偏移不可用时（BodyParseFilter 未生效）自动退回解析方式。

> ⚠️ **偏移差一个字节就会拼出坏 JSON，且要到真实转发时才炸**，不能靠「Jackson 应该是这么定义的」
> 推断。已在 `ResponseCaptureTest` 实测三种排布（model 在头 / 在尾 / 带空格），断言偏移精确覆盖
> 含引号的 token，并验证拼接结果仍是合法 JSON 且只有 model 变。

新值用 `objectMapper.writeValueAsBytes(String)` 生成带引号且转义正确的字面量，不自己拼字符串。

### 27.6 验证

新增 `RequestParamMergerTest` **20/20 通过**，重点覆盖三项语义里最容易搞反的地方：
default 只补缺、force 无条件覆盖、同字段 force 优先、mapping 仅 custom 生效且不覆盖已有键、
配置非法时不抛异常、以及「未配置时返回同一数组引用」这条性能保证。
另含用户场景用例：专用字段改名、禁止 `force_params.model` 篡改身份，以及 custom 映射后
目标字段携带真实模型 ID 且不残留原 `model` 字段。

## 26. 转发热路径性能优化（P0 + P1）

> 目标是"极致性能、极少转发损失"。先说判断口径，否则容易做无用功：
> **LLM 请求本身几十秒到几分钟，省几十微秒对端到端延迟毫无意义。**
> 真正有价值的只有两类——**事件循环占用**（决定单机并发上限）与**内存/GC**（决定稳定性）。
> 下面每一条都按这个标准取舍，不做"看起来更快"的改动。

### 26.1（P0）响应体不再无条件全量缓冲

`PayloadCaptureFilter` 原先只判断路径前缀就装饰响应，**与报文开关无关**——
每个请求的完整响应都攒进 `ByteArrayOutputStream`（上限 64MB），开关关着也照攒。
根因是 `TraceFilter` 需要响应体解析 Token（月度配额依赖它），报文留档只是顺带。
紧接着 `TraceFilter` 又 `toByteArray()` **再全量复制一份**。

流式尤其亏：SSE 每帧都重复 id/model/created 等元数据，整条流的体积常是最终文本的
**数倍到数十倍**，而解析 usage 只需要最后几帧。

新增 `ResponseCapture`，两种模式：
- **FULL**：报文开关开启（要落库原文），或**非流式响应**
  （非流式的 usage 在单个 JSON 里、位置不定，`readTree` 需要完整报文，截尾会直接丢掉 Token）
- **TAIL**：流式 + 报文开关关闭（绝大多数请求）→ 只留最后 64KB 环形缓冲

模式在**首个响应块写出时**惰性决定：那一刻响应头已就绪才判断得了流式与否；
`appId`/`modelId` 由 order=-190/-175 写入，到 -145 时早已可用。

> ⚠️ **`totalBytes` 必须独立累计**。TAIL 模式下 `toByteArray()` 只是尾巴，
> 不能再用它的长度做 Token 估算兜底——`parseStreamUsageOnly` 找不到 usage 时会按响应总字节数
> 估算，用尾巴长度会把结果压到极小、**悄悄少算月度配额**。这是本次最容易埋进去的暗坑，
> 已用独立计数 + 显式传参解决，并有回归用例覆盖。

### 26.2（P0）`parseStreamUsageOnly` 改成真正的尾部扫描

原实现虽然限制了「解析成 JSON 的帧数」，但开头先做
`new String(整个响应)` + `split("
")`——把整条 SSE 流物化成一个大 String
外加**每一行一个 String 对象**的数组。一条 500KB、两千帧的流，光这一步就是
500KB 字符串 + 2000 个 String + 一个大数组，每请求一次，全落在响应收尾路径上。
类注释里"只扫描尾部若干字节，成本可忽略"**对 CPU 成立，对内存完全不成立**。

改为在 byte[] 上从尾部反向找换行，**只对真正要解析的那几帧**做 UTF-8 解码。
分配量从"整条流"降到"最多 20 帧"。

### 26.3（P0）日志不再可能阻塞事件循环

两个问题叠加：
- `CONSOLE` 是**同步** ConsoleAppender 且直接挂在 root 上。容器里 stdout 常被日志驱动接管，
  对端一慢就反压到调用线程——很可能就是 Netty 事件循环。
- `AsyncAppender` 的 `neverBlock` **默认 false**（队列满即阻塞调用方），
  而这里又配了 `discardingThreshold=0`（永不按级别丢弃），等于把阻塞风险拉到最高：
  什么都不丢、满了就只能等。

改为：两个 appender 都包 Async，`queueSize=2048`、`discardingThreshold=256`
（优先丢 INFO/DEBUG，保住 WARN/ERROR）、**`neverBlock=true`**、`includeCallerData=false`（显式声明）。
取舍很明确：**宁可丢日志，也不能卡转发**。

> 顺带留了一条可选优化：CONSOLE 与 FILE 同时挂 root，意味着每条日志被格式化两次、写两次
> （PatternLayout + LogstashEncoder）。若确认容器侧不从 stdout 采集，去掉 ASYNC_CONSOLE
> 可再省整整一份格式化开销。这属于可观测性行为变更，**需要你确认采集方式后再动**。

### 26.4（P1）不再为读一个 `model` 字段解析整个请求体

`BodyParseFilter` 原先 `new String(bytes, UTF_8)` + `readTree(body)`——
为拿一个字符串字段，先把整个请求体复制成 String，再建一棵完整的 JsonNode 树。
多轮对话的 `messages` 动辄几百 KB 到几 MB，分配量与请求体成正比，
而且**跑在 Netty 事件循环线程上**：请求体越大，卡住 EventLoop 越久，
连累的是该 EventLoop 上的**所有连接**。

改用 `JsonParser` 只遍历顶层字段，遇到对象/数组值直接 `skipChildren()`（只做词法扫描、
不构造节点），扫到 `model` 立即返回。典型请求里 `model` 就在最前面，实际只读几十字节。

> 语义必须保持"只认顶层 model"：`messages` 里的用户内容完全可能出现同名字段，
> 建树版靠 `node.get("model")` 天然只取顶层。已有回归用例专门覆盖这一条。

### 26.5（P1）三层配额从 3 次 Redis 往返降到 1 次

`QuotaFilter` 每请求串行调 `isQpsAllowed` / `isDailyAllowed` / `checkMonthlyTokens`，
三次独立 `eval`。代价不在端到端延迟，而在**线程与连接的占用时长**：
Jedis 是同步阻塞客户端，三次调用 = 一个 boundedElastic 线程和三份连接借还全部乘以三。

合并为单个 Lua 脚本（`COMBINED_QUOTA_SCRIPT`），**短路语义与原实现完全一致**：
QPS 超限不再触碰日计数器，日超限不再触碰月计数器——顺序不能改，
改了会让被限流的请求也消耗日配额。三个上限都 ≤0 时直接返回、不打 Redis。

> ⚠️ **集群风险已登记**：三个 key 分属不同 slot，Redis Cluster 下会因 CROSSSLOT 被拒。
> 本项目 Redis 是**单机直连**（application.yml 的 `redis.local` host/port），当前无此问题。
> **若将来切集群，必须给三个 key 加相同 hash tag**，否则本方法整体失败并 fail-open——
> 等于配额全线失效，且只有一行 WARN。

顺带把 `auths.stream().filter().findFirst()` 换成普通 for 循环：热路径上 stream 的
Spliterator/Lambda 链每次都要分配，而授权列表通常只有个位数条目。

### 26.6（P1）`log.debug` 的隐藏分配

`TraceFilter.doFinally` 里那条 8 参数 `log.debug`，**即使 debug 未开启，
varargs 的 `Object[8]` 仍会分配**，每请求一次。加 `isDebugEnabled()` 守卫。

### 26.9 补充优化（本轮追加）

**① 解密失败改为说得清的 400**（原先是 500 「internal server error」）

`CryptoService.decrypt` 原先一律抛 `RuntimeException("Decryption failed")`，
运维完全看不出到底是「密钥配错了」还是「这条密文本身坏了」——两者处置方式截然不同：
前者改 `modelgate.crypto.key`，后者重新生成凭证。现在按失败类型分开：

| 失败类型 | 提示 |
|---|---|
| `AEADBadTagException` | 密钥不是同一把（最常见）/ 密文被篡改截断，并给出排查步骤 |
| Base64 非法 | 密文已损坏，需重新生成凭证 |
| 长度不足 | 同上，附实际字节数 |

新增 `CryptoService.CryptoException` 独立异常类型，`GlobalExceptionHandler` 据此回 **400** 而非 500。
实测 `/credentials/secret` 现在返回 HTTP 400 + 完整原因说明。

**② AKSK 热路径的两处每请求开销**

- `Mac.getInstance("HmacSHA256")` 每请求走一遍 JCA provider 查找 → 改为 `ThreadLocal<Mac>` 复用
  （Mac 非线程安全不能做单例，但每线程一个是安全的：`init(key)` 会重置内部状态）。
  跑在有界线程池上，ThreadLocal 数量天然受限于线程数。
- `cryptoService.decrypt(...)` 每请求做一次完整 AES-GCM 解密 → 新增 `decryptCached`，
  用 Caffeine 记忆化（密文→明文是纯函数）。**安全取舍**：明文 SK 在堆里驻留更久，
  故限制得很紧（`maximumSize=1000` + `expireAfterAccess=10min`）。
  不影响凭证启用/禁用实时性——那由 `credentialCache` 独立控制。

**③ `sha256Hex` 去掉 `String.format`**

这是热路径（每个 api_key 请求算一次）。原实现对 32 个字节各调一次 `String.format("%02x", b)`，
要解析格式串、走 Formatter、装箱参数，单次微秒级，32 次叠起来每请求几十微秒。改查表后是几十纳秒。

> ⚠️ **刻意没改的一处**：`input.getBytes()` 用的是平台默认字符集，这是已知隐患
> （Linux 通常 UTF-8、Windows 是 GBK，同一 key 两台机器算出不同哈希）。
> **但现在改会直接炸掉存量凭证**——库里 `secret_hash` 是当初用旧字符集算的，
> 换算法就再也匹配不上，且无法回滚（明文已不可得）。
> 实际暴露面只有 api_key 里拼接的 appId（`"mg-" + appId + "-" + randomHex(24)`），
> 密钥材料本身是 URL-safe Base64 纯 ASCII，两种字符集编码一致；当前库中 appId 均为数字，不受影响。
> **要修必须配套**：先扫出所有含非 ASCII appId 的凭证重新生成，再统一切 UTF-8。单独改一行等于埋雷。

**④ `encrypt` 里 `new SecureRandom()` 改为静态复用** —— 每次 new 都要重新播种，
开销远大于取几个随机字节；SecureRandom 实例本身线程安全。

### 26.10 EVALSHA / 字符集隐患 / 连接池（用户确认后追加）

> ⚠️ **本节 ① 已于 2026-08-24 整体废止**：内网 Redis 禁用 Lua 脚本，
> `eval` / EVALSHA 链路连同四段脚本一并删除，配额改走原生命令。见 **§31**。
> ②③ 两项（字符集、连接池）仍然有效。以下保留原文供追溯。

**① Lua 脚本改走 EVALSHA**（用户确认 `CacheProvider.eval` 底层就是 EVAL）

行内 `CacheProvider` 接口只有 `get / setex / del / eval` 四个方法、**没有 evalsha**，
调用方绕不开。好在 `JedisCacheProvider` 是本项目自己的实现类（`RedisConfig` 内部类），
直接在它的 `eval` 里做掉即可，**对所有调用方透明，不用改任何调用点**。

实现选的是「本地算 SHA1 → 直接 EVALSHA → catch `JedisNoScriptException` 回退 EVAL」，
而不是常见的「先 `SCRIPT LOAD` 再 EVALSHA」。理由：回退用的 EVAL 本身就会让 Redis
缓存住这段脚本，于是**预热是自动完成的**，且天然覆盖 Redis 重启 / `SCRIPT FLUSH` /
主从切换这些会让脚本缓存失效的场景——失效后第一个请求回退一次，之后继续走 EVALSHA。

配额脚本约 600 字节，在 `/v1/**` 热路径上每请求执行一次；EVALSHA 只传 40 字节的 SHA1。

> 实测（`EvalShaTest`，打真实 Redis）**6/6 通过**，含「SCRIPT FLUSH 后自动回退并恢复」这一条。
> Jedis 3.1.0 确实带 `JedisNoScriptException`（已 javap 核对），可直接 catch，不必按 message 判。

**② `sha256Hex` 字符集固定为 UTF-8**（用户确认存量是测试数据、可重新生成）

原先 `input.getBytes()` 取平台默认字符集——Linux 通常 UTF-8、Windows 是 GBK，
同一个 key 在两台机器上算出**不同的哈希**，表现为「凭证在某台机器上突然认不出来」。

顺带修正上一轮引入的一处不对称：`decrypt` 已改成 UTF-8，而 `encrypt` 仍是平台默认，
在非 UTF-8 平台上会出现「加密再解密拿到乱码」。`constantTimeEquals` 一并统一。

影响面：只有被哈希的字符串含**非 ASCII** 时新旧结果才不同。密钥材料本身是
URL-safe Base64（纯 ASCII），唯一暴露面是 api_key 里拼接的 appId
（`"mg-" + appId + "-" + randomHex(24)`）。因此**只有「appId 含非 ASCII」的 api_key 凭证会失效**，
ak_sk 完全不受影响（SK 与 appId 无关）。定位与处置见
`sql/upgrade_20260819_sha256_utf8_migration.sql`。

**③ 上游连接池补三个参数**（按信创 NPU 的 workload 定值）

| 参数 | 值 | 作用 |
|---|---|---|
| `max-life-time` | `10m` | 连接活满即退休。`max-idle-time` 只回收**空闲**连接，而持续被复用的连接永远不空闲、也就永远不被回收——上游滚动发布后请求会继续打到已下线实例，只能靠重启网关恢复 |
| `eviction-interval` | `60s` | 后台定期清理。默认只在「有人来借连接」时才顺带清理，低峰期过期连接白占 fd/内存，高峰第一波还要边清边建 |
| `leasing-strategy` | `lifo` | 优先复用最近归还的连接。默认 FIFO 轮着用，一大批连接都「温着」但每条都不够热；LIFO 让少数连接保持活跃、其余自然到期回收，池规模自动贴合真实并发 |

`max-life-time` 取 10m 而非常见的 30m/60m，是因为这个 workload 特殊：上游是信创 NPU
部署的模型，单次请求几十秒到几分钟，**TLS 握手那 100~200ms 占比不到 0.1%**。
既然连接复用的收益可以忽略，就该把这个自由度换成「更快跟上上游拓扑变化」。

> ⚠️ 配置项名是 `eviction-interval`（对应 `HttpClientProperties.Pool.evictionInterval`），
> **不是** `evict-in-background`——已用 javap 核对 setter 名。写错不会报错，只会静默不生效。
>
> `max-life-time` 只在连接**借出 / 归还**时判定，**不会掐断进行中的请求**，
> 对动辄几分钟的 LLM 请求是安全的。

## 25. 容器探测端点 + 写库失败重试 + 管理面限流护栏 + 文根修复

> 本节四件事：前两件是生产事故级（容器起不来 / 数据静默丢失），后两件是把 §24.8
> 定位到的问题补齐。全部改动均在<b>真实启动的实例上验证过</b>（临时实例，端口 10812）。

### 25.1 容器探测端点（容器一直重启的根因）

行内容器平台在三个场景调用固定路径判断应用状态，**拿不到 200 就认为应用没起来并反复重启**。
本项目从未实现这三个端点，平台一直拿到 404，所以容器起来后一直重启重试。

| 场景 | 路径 | 返回 200 的条件 |
|---|---|---|
| 存活检查 | `/actuator/detection/running` | **进程活着就永远 200** |
| 流量检查 | `/actuator/detection/available` | 启动完成 且 未在优雅退出中 |
| 优雅退出 | `/actuator/detection/shutdown` | 总是 200（幂等） |

三个设计决定，每个都对应一类真实事故：

- **存活检查绝不查 DB/Redis**。存活失败的语义是"进程坏了，重启它"。把依赖健康写进去，
  数据库抖一下就会让**所有实例同时被重启**，一次局部故障放大成全面中断，且重启后依赖仍没好，
  于是无限重启。本网关即使 MySQL 挂了，凭证/授权走 Caffeine 缓存仍能转发相当一部分流量。
- **存活检查在退出流程中仍返回 200**。此时进程在正常收尾，不是坏了；返回非 200 会让平台
  在收尾没做完时就把容器杀掉。
- **GET 与 POST 都接受**。平台用哪个方法未约定，405 同样不是 200，一样触发重启。
  用 `@RequestMapping(method = {GET, POST})` 而**不是**叠加 `@GetMapping + @PostMapping`——
  后者在同一方法上放两个 `@RequestMapping` 派生注解，Spring **启动时**就抛 IllegalStateException，
  应用根本起不来。

路径挂在 `UrlConstant.ACTUATOR_PREFIX` 之下，六个业务过滤器都按该前缀跳过，
探测请求天然不经过鉴权/授权/配额/熔断/路由，不需要单独开白名单。

优雅退出端点除了置 draining，还会**把审计与报文的内存队列尽力刷盘**（见 §25.2）。

实测（临时实例）：

```
GET/POST /running    → 200 running       （无任何凭证头）
GET/POST /available  → 200 available
POST     /shutdown   → 200 draining      第二次调用仍 200（幂等）
退出后   /running    → 200 running       ← 关键：存活仍然 200
退出后   /available  → 503 draining
```

### 25.2 写库失败不再丢弃：重试缓冲区

`AuditService`/`PayloadService` 原先是 `drainTo` 先把数据**取出队列**，再 try `batchInsert`，
catch 里只打一行 WARN。数据已离开队列，写失败就**永久消失**——管理面一个慢查询占满 Druid
连接池，就足以让 5000 条审计当场蒸发，月底对账对不上且无从补回。

新增 `PendingWriteBuffer`，失败整批进缓冲区等待重试。四个设计要点各对应一个翻车点：

1. **指数退避**（2s 起翻倍，上限 60s）——数据库已经挂了还每 2 秒猛敲，只会让它更难恢复，
   还会把连接池等待队列堆满，反过来拖慢网关侧鉴权。
2. **毒药记录隔离**——同一批连续失败 3 次后**对半拆分**重试。若失败原因不是"数据库不可用"
   而是"某条记录本身写不进去"（字段超长、编码非法），不拆分会让这一条坏记录**永久阻塞整批**，
   重试到天荒地老。拆分能在 log2(N) 轮内把坏记录缩到单条，只丢那一条、其余全部救回。
   这是"无限重试"方案最容易忽略的死穴。
3. **拆到单条仍失败才丢，且打 ERROR** + 记录摘要 + 累计数，让它进告警而不是混在 WARN 里。
4. **容量有上限**——数据库长时间不可用时无限缓冲会 OOM，那是整个网关挂掉，比丢审计严重得多。
   超限丢**最旧**批次并打 ERROR。

⚠️ **一个必须做对的细节**：月度 Token 累计（`accumulateMonthlyTokens`）挪到 DB 写入**之前**，
且**只在首次出队时执行一次**，重试路径绝不再累加。Redis 的 `INCRBY` 不是幂等的，
重试一次就多算一次 token，数据库抖动几轮就能把用户的月度配额凭空吃光，直接误伤线上业务。

同时新增**优雅退出刷盘**：`drainForShutdown()`（退出端点调用）+ `@PreDestroy`（兜底），
15 秒时限。发版是最频繁的进程退出场景，此前每次发版都在悄悄丢一批未落库的审计。

### 25.3 管理面限流护栏推广到全部列表接口

§24.8 只修了 `/modelgate/payload`。本轮补齐 `/audit`、`/models`、`/apps`：

- 新增 `PageSupport`（`MAX_PAGE_SIZE=200`、`MAX_OFFSET=50000`），四个接口统一调用。
  `BaseBo.setPageSize` 是裸 setter、框架层不收敛，实测**未加护栏时
  `GET /modelgate/audit?pageSize=100000` 返回 200 / 2.8 秒 / 1.7MB，把整张审计表吐了出来**。
- 新增 `AdminScheduler`：管理面全部查询共用一个 8 线程 / 队列 128 的专用池，
  不再用与网关五个 Filter 共享的全局 `Schedulers.boundedElastic()`。
  `PayloadController` 原先自建的私有池一并收口到这里。
- `TdsqlMybatisPlusConfig` 设 `defaultStatementTimeout = 30s`——**全局** JDBC statement 超时。
  此前三层都没有超时兜底（JDBC URL 无 socketTimeout、无 defaultStatementTimeout、
  Controller 无 `.timeout()`），一条跑飞的查询没有任何东西能掐掉。

上限取 200 而非更小：管理面「填充筛选下拉」处用的正是 `pageSize=200`
（`fetchSelectableModels` / `fillAuditFilters`），取小了会把自己的功能打掉。已实测 200 放行。

### 25.4 接口契约维度补审（此前两轮都没跑成）

手工把参数边界打了一遍，**没有发现 500，绑定失败一律干净 400**。发现并修复一处：

绑定失败的响应恒为一句 `"Validation failure"`，**不说是哪个参数**。
`?isStream=abc`、`?pageSize=abc`、`?startTime=乱写` 三种情况文案完全一样，排查时无从下手。
`GlobalExceptionHandler` 新增 `bindFieldDetail()`，从 `WebExchangeBindException` 提取字段级信息：

```
400  Validation failure —— 参数 isStream 取值 'abc' 无法解析
400  Validation failure —— 参数 isStream 取值 'abc' 无法解析; 参数 upstreamStatus 取值 'xyz' 无法解析
```

### 25.4 MybatisWiringSelfCheck 改为可移植（内网也应引入）

内网合并版**没有引入**这个自检类。原因很可能是它按 **bean 名**注入
`SqlSessionFactory tdsqlSessionFactory`——内网若用行内框架自己的 SqlSessionFactory，
bean 名对不上，引入即启动失败，于是干脆不引入。代价是内网**完全失去了这层保护**，
而它恰恰是用来兜住"基础字段不自动填充"这类静默故障的。

改为按**类型**注入 `ObjectProvider<SqlSessionFactory>`：有几个查几个，一个都没有就打 WARN
跳过而不是拦启动。任何环境都能安全引入，装配正确时只在启动打一行日志，零运行期成本。

异常文案也补了新的后果描述：MetaObjectHandler 缺失时，若全局 `insertStrategy` 会写出显式
NULL，会**覆盖建表的 `DEFAULT CURRENT_TIMESTAMP`**，表现为「新增数据的时间字段是空的」——
正是内网 mg_app 观察到的现象。

> 本仓库实测：重构后启动日志仍为
> `[MyBatis自检] 装配校验通过: MetaObjectHandler=AuditFieldMetaObjectHandler, 分页拦截器=已注册, 拦截器总数=2`

### 25.5 流量检查改为恒 200（可配置）

平台对"流量检查失败"的处理方式**尚未确认**：标准语义是把实例摘出负载均衡，
但有的平台会当成不健康直接重启容器——那会在优雅退出或启动稍慢时重启容器，
反而制造出本节正要解决的问题。

在摸清之前取保守值：新增 `modelgate.detection.available-always-200`，**默认 true**。
真实状态没有丢，响应体仍是 `available` / `starting` / `draining`，只是不再用状态码表达。

代价要说清楚：恒 200 意味着**优雅退出期间平台不会因为这个端点而停止派发新流量**，
只能依赖平台自己的摘流量流程。确认平台"流量检查失败只摘流量、不重启"之后，
把该配置改成 false 即可恢复标准语义。

### 25.6 四个 VO 漏掉时间字段（"数据没保存"的假象）

排查"mg_app 时间字段没有设置值"时发现：**数据库里值一直都在**
（实测 mg_app / mg_model / mg_app_credential / mg_app_model_auth 四张表的
`create_time`、`update_time` 空值行数均为 0），问题出在 VO 层——

| VO | 缺失字段 |
|---|---|
| `AppVO` | `updateTime` |
| `AppCredentialVO` | `updateTime` |
| `AppModelAuthVO` | `updateTime` |
| `AccessRuleVO` | `createTime` **和** `updateTime` |

接口因此从不返回这些字段，页面上的「更新时间」永远是空的，**看起来像数据库没存值**。
与 §16 里 `AuditLogVO` 漏掉 `requestPath` 是同一类问题：
<b>字段缺失发生在 VO 层，症状却表现为"数据没保存"，极易误判成写入逻辑有 bug。</b>
四个 VO 已全部补齐。

> 顺带确认了自动填充链路本身是好的：`AppInfoEntity` 的
> `@TableField(fill = INSERT/INSERT_UPDATE)` 标注齐全，`AuditFieldMetaObjectHandler`
> 正确实现了 `insertFill`/`updateFill`，`MybatisWiringSelfCheck` 会在启动时断言
> handler 已挂载。且 `modelgate_schema.sql` 里两个时间列都带
> `DEFAULT CURRENT_TIMESTAMP`，而 MyBatis-Plus 默认 `insertStrategy=NOT_NULL`
> 会把 null 字段排除出 INSERT，DB 默认值仍会生效——**三重保障**。

### 25.7 部署文根：接入示例与连通性测试调不通

行内部署时域名后挂 `/backend` 文根（前后端分离用同一域名按文根区分）。两个问题：

1. **接入示例的网关地址漏了文根**。`openUsageModal` 取的是裸 `location.origin`，
   于是给接入方的示例写的是 `https://域名/v1/chat/completions`，
   而后端实际在 `https://域名/backend/v1/chat/completions`——示例是错的，
   页面上的「测试连通」也永远失败。新增 `defaultGatewayBase()` = `location.origin + CTX_ROOT`。
2. **`CTX_ROOT` 判定漏掉本机局域网 IP**。原判定只认 `localhost`/`127.0.0.1`/`::1`，
   用 `http://10.x.x.x:10811/admin.html` 打开时会被判成"域名"，于是**所有**管理接口都拼上
   `/backend` 而全部 404——模型测试、报文查询、列表加载统统调不通，且看不出原因。
   这正是"模型管理测试按钮也调不通"的真实成因（那里本来就走 `apiUrl()`，URL 拼接逻辑没错，
   错的是文根判定本身）。

改为 `isDirectHost()`：**主机名是 IP 字面量或 localhost → 直连（无文根），其余视为域名 → 带文根**。
`location.hostname` 不含端口，出现冒号只可能是 IPv6，可据此直接判定。
已对 14 种主机名做过用例校验，含 `cafe`/`ade` 这类纯十六进制字母域名不会被误判成 IPv6。

## 24. 报文记录管理面查询页

> 报文记录（`mg_request_payload`）此前只有**采集与落库**，没有任何查询出口——数据一直在写，
> 但要看只能登数据库敲 SQL，而报文默认只保留 7 天，等想起来查往往已经被清理了。
> 本节补上管理面查询能力。采集侧（`PayloadCaptureFilter` / `PayloadService` / `PayloadCleanupService`）
> 未作改动。

### 24.1 数据保留期（本次未改，此处明确记录口径）

三个已有配置项决定"报文能查多久"，均在 `application.yml` 的 `modelgate.payload-log` 下：

| 配置项 | 当前值 | 含义 |
|---|---|---|
| `retention-days` | `7` | 保留 7 天，超期由 `PayloadCleanupService` **物理删除**，不可找回 |
| `cleanup-cron` | `0 30 2 * * ?` | 每日 02:30 执行，刻意错开审计清理（02:00）避免抢 IO |
| `enabled` | `true` | 全局总开关；磁盘告警时的一键止血手段 |

保留期为何是 7 天而非跟审计一样 90 天：报文行含三个 `LONGTEXT`，单行体积是审计记录的
几十到上千倍，按审计的保留期存会让磁盘增速失控；排查场景也多是"最近几天出的问题"。
清理是**分批 + LIMIT**（每批 500 行、单次最多 200 批）——一次性 DELETE 大批量 LONGTEXT
会长时间持锁并撑大 binlog。

页面顶部的提示条直接从 `GET /modelgate/payload/meta` 读这三项显示，**不在前端写死**：
保留期是配置项，写死必然与实际部署漂移，而"查不到上周的报文"最容易被误判成功能坏了。

### 24.2 新增接口（3 个）

| 接口 | 说明 |
|---|---|
| `GET /modelgate/payload` | 分页列表，多条件检索，**不含正文全文** |
| `GET /modelgate/payload/detail?id=` | 单条全文（请求报文 / 响应原文 / 响应正文） |
| `GET /modelgate/payload/meta` | 总开关、保留天数、清理 cron、采集上限回显 |

**列表与详情严格分离**，这是本节最关键的一个设计约束：一页 20 条报文的正文合计可达几十 MB，
列表若用 `BaseMapper.selectPage`（`SELECT *`）会把三个 LONGTEXT 一起拖出来，DB 网络传输、
服务端堆内存、浏览器渲染一起遭殃——这正是当初把报文独立成表、不塞进 `mg_audit_log` 的理由，
列表查询必须把这个理由贯彻到底。故：

- `RequestPayloadMapper.selectListPage` 用**显式列清单**的 `@Select`，正文列只在 SQL 侧取
  `CHAR_LENGTH(...)`（体积）和 `LEFT(response_text, 160)`（预览），大列内容根本不出 MySQL；
- 列表用 `PayloadListVO`（无正文字段）、详情用 `PayloadDetailVO`（有），**在类型层面**堵死
  "列表顺手把 LONGTEXT 带出来"这条路。

排序为 `create_time DESC, id DESC`：报文与审计同属高频追加表，同一毫秒可写入多条，
只按 `create_time` 排会在翻页时出现重复行/漏行，必须补唯一列做次级排序（与 §16.4 同一个坑）。

### 24.3 检索条件

接入系统、模型、TraceID、流式与否、上游状态码、结束原因（stop/length/tool_calls/content_filter）、
截断标记、时间范围、**正文关键字**。

比审计页多出来的几项都对应审计表看不出来的排查入口：按 `finish_reason=length` 找被
`max_tokens` 截断的回答、按 `is_stream` 找 SSE 拼接问题、按 `upstream_status` 捞非 200 的
原始错误体。

**正文关键字有前置约束**：它是 LONGTEXT 上的 `LIKE '%x%'`，走不了索引。若允许单独使用，
一次点击就是全表扫描 + 把全部正文读进 buffer pool，足以拖垮在线业务的 DB。故后端强制要求
关键字必须与 系统 / 模型 / TraceID / 时间范围 中的至少一项同时使用（`PayloadController.validate`，
不满足直接返回 `INVALID_PARAMETER` 且错误文案就是操作指引），让 MySQL 先用
`idx_app_model_time` / `idx_create_time` 收窄候选集。前端在筛选区也提前把这条规则写出来。

关键字只匹配 `request_body` 与 `response_text`，**不匹配 `response_raw`**：raw 是 SSE 分帧原文，
同一句话被切碎在多帧里，LIKE 匹配不到完整词，搜它只会给出误导性的空结果。

### 24.4 列表上的 Token（跨表取，不冗余）

列表与详情都显示 **输入/输出 Token 与口径标记**。Token 在 `mg_audit_log` 里，报文表按设计
**不冗余存**（唯一真相在审计表，见 `RequestPayloadEntity` 类注释）——这里是**读取**而非复制，
不破坏该约定。

实现用**标量子查询**而非 LEFT JOIN，两个理由缺一不可：

1. **正确性**：两表 `trace_id` 上都只有普通索引、无唯一约束。JOIN 时审计侧一旦出现同
   `trace_id` 多行，报文行会被放大成多行，分页 `total` 与列表内容一起错乱。子查询带
   `LIMIT 1`，结构上保证一条报文只出一行。
2. **兼容 Wrapper**：`${ew.customSqlSegment}` 生成的是**不带表前缀**的列名（`app_id = ?`、
   `ORDER BY create_time`）。JOIN 进第二张表后这些列全部 ambiguous，SQL 直接报错——
   除非把整个查询改成手写参数，那样就丢掉了条件组合的灵活性。

子查询走 `mg_audit_log.idx_trace_id`，每行三次索引点查，一页 20 行可忽略。

详情接口因此也从 `BaseMapper.selectById` 换成 `selectDetailById`：前者只能取到报文表自己的列，
Token 会整体丢失。`PayloadDetailVO` 随之改为 MyBatis 直接映射，删掉原来的 `of(Entity)` 转换。

> **`null` 与 `0` 必须分开展示**：Token 为 null 表示关联审计记录查不到（审计留 90 天、报文留 7 天，
> 正常不该发生，是数据异常），为 0 表示确实没消耗。一律按 0 展示会把数据异常伪装成"这次没烧
> token"——这正是 token 恒为 0 的旧 bug 长期没被发现的原因，不能再犯。前端 `tokenCell` 按此区分。
> `token_source=estimated` 是本地按字符估算的，页面打黄标，不可当账算。

### 24.5 页面

侧边栏「运维」下新增「📨 报文记录」。列表列：时间 / TraceID / 接入系统 / 模型 / 类型（流式）/
上游状态 / 结束原因 / **Tokens（入/出）** / **请求报文** / 响应正文 / 操作。

请求与响应各占一列预览（各取前 160 字），字符数放进 tooltip——排查时"问了什么"和"答了什么"
要能在列表上并排比对，点进详情才看到就慢了一步。`truncated ≠ none` 在响应列打红标——
报文本身不完整时不能拿它当上游真实返回，必须一眼可见。

详情弹窗把三份正文分成三个 tab（请求报文 / 响应正文 / 响应原文），**不同时铺开**：单条报文可达
几 MB，一次性塞进 DOM 会把页面卡死。JSON 尝试美化，失败就原样显示——看到原文永远比看到
"解析失败"有用；SSE 原文不做任何处理，分帧结构本身就是要看的东西。

**详情弹窗尺寸**（用户反馈"不用搞这么小可以大方点"）：原先复用 `.modal-wide`（720px 宽）
且正文区写死 `max-height:420px`，读几千字的报文要反复滚。新增 `.modal-xl`
（1280px / 96vw × 90vh），正文区改为 flex 自适应高度，**随浏览器窗口一起长**而不是钉死。
实测 1920×1080 下阅读区 718px（原 420px，+71%），1280×720 下 394px 并正确内滚。

flex 容器里让内部滚动条正常工作有两个必要写法，缺一不可：外层 `overflow:hidden`，
正文 `min-height:0`。不写 `min-height:0` 时 flex 子项不会收缩到小于内容高度，
滚动条会跑到最外层去——整个弹窗跟着滚，头部和 tab 栏一起滚出视野。

顺带加了三个读长报文时实际会用到的东西：**自动换行开关**（SSE 原文与压缩 JSON 常有超长单行，
不换行要横向拖，换行又打乱缩进，两种读法都有用）、**字号增减**（11–20px，逐字比对时要放大）、
底部**字符数提示**（"看起来空空的"到底是内容少还是取回来就是空，要能一眼区分）。

**与审计页双向跳转**（两表本来就靠 `trace_id` 关联，排查时总是来回看）：
审计行新增「📨 报文」按钮 → 带 traceId 跳到报文页；报文详情里「看审计记录」→ 带 traceId 跳回审计页
看耗时/token/最终状态码。审计表因此多了一列「操作」，空态 colspan 同步从 8 改到 9。

### 24.6 上线后一轮排查修复（用户实测 400 触发）

用户点「类型=流式 + 关键字=4068cdd7791e」拿到一个无解释的 400。顺着查出 6 个问题，
其中 3 个是对**运行中实例** curl 实测确认的：

| # | 问题 | 确认方式 |
|---|---|---|
| 1 | `GlobalExceptionHandler` 吞掉 `BusinessException` 的 detail | 读码 + 实测响应体 |
| 2 | traceId 全等匹配，复制界面显示的截断值永远查不到 | **实测**：16 位 → 1 条，12 位 → 0 条 |
| 3 | LIKE 通配符未转义，一个 `%` 绕过全部防护 | **实测**：`keyword=%` → 全表 2735 条 |
| 4 | `pageSize` 无上限 | **实测**：`pageSize=5000` 被原样接受 |
| 5 | 收窄条件判定过松，任意时间下界即放行 | **实测**：`startTime=1990-01-01` → 200 |
| 6 | 跳转链路并发两个请求，慢的那个覆盖快的 | 代码审查 + 时延对比 |

**#1 影响面超出本功能**：`Result.fail(..., be.getErrorCode().getMessage())` 取的是 ErrorCode 的
**泛化**文案（"Invalid request parameter"），而调用点写的具体原因在 `be.getMessage()` 里，
被整个丢掉。`ModelController` 的 "modelId 不能为空" 等 3 处同样被吞了很久。改取 `be.getMessage()`。

**#6 是本功能自己引入的最隐蔽的一个**：`payloadOfTrace` 先 `navTo('payload')`（内部自动发一次
**无条件**查询），再设置 traceId 发第二次。两个请求并发在途，无条件那次数据量大、返回慢，
往往后到并把带条件的结果盖掉——表现是"筛选框里填着 traceId，列表却是全量"。
更糟的是**第二次点不同审计行**时，`pl_trace` 还留着上一个 traceId，于是两个请求带的是
**不同的** traceId，谁赢不确定；赢的若是旧的，页面会安静地显示**另一次调用**的报文，
而输入框显示的是新 traceId——全程没有任何异常信号。修法是给 `navTo` 加 `skipLoad` 参数，
带条件跳转时只发一次请求。`payloadToAudit` 同病（原先并发四个请求，含两次重复的 `loadStats`），
一并修。

**#5 的教训**：原来的 `hasNarrowingFilter` 只判 `startTime != null || endTime != null`。
"给了时间条件"和"给了**有界且够窄**的时间条件"是两回事——保留期只有 7 天的表上，
单端时间几乎等于全表。现在要求两端齐全且跨度 ≤24 小时。

**#3 不是 SQL 注入**（值仍是绑定参数），是通配符被当成语法解释。用反斜杠转义、不加 `ESCAPE`
子句，因为 MySQL 的 LIKE 默认转义符就是反斜杠。

前端配套：关键字缺收窄条件时**不再发请求等 400**，直接给引导面板并附两个一键补救按钮
（「按最近 24 小时搜」正好产出一个合规的 24 小时区间、「当 TraceID 搜」）——
从列表复制 traceId 粘到关键字框正是最容易走错的一步。`payloadNarrowed()` 与后端
`hasNarrowingFilter()` 逐条对齐，避免前端放行、后端拒绝。

### 24.7 `truncated` 的四态契约从未兑现

DDL 注释、04 文档、前端下拉都写着四态 `none|request|response|both`，但
`PayloadService.toEntity` 实际只写 `truncated ? "response" : "none"`。请求侧**结构上**没有截断机制：
`BodyParseFilter` 用 `DataBufferUtils.join` 一次性读全请求体，没有任何字节上限，
`max-capture-bytes` 只作用于 `PayloadCaptureFilter` 的响应采集侧。

危害是**静默误导**：用户选「请求被截」查排查问题，得到 200 + 空列表 + 一句"没有符合条件的报文"，
据此得出"这段时间没有请求被截断"的结论——而系统压根不记录这个状态，全程无任何异常信号。

收敛为两态：前端下拉去掉两个死选项；`PayloadController` 加 `truncated` 白名单让非法取值
**响亮地失败**；`sql/modelgate_schema.sql` 列注释改为"request/both 为预留值，当前实现不会写入"；
04 文档同步。`finishReason` **不加**白名单——取值由上游模型决定，写死会把新模型的合法值拒掉。

> 只改了 `modelgate_schema.sql`（新装生效），**没有出 upgrade 脚本**：这是纯列注释变更，
> 对已部署库做 `ALTER TABLE MODIFY COLUMN` 只为改一行元数据文本，收益为零、风险不为零。
> 已有库的列注释保持旧文案，以本文档与代码为准。若坚持要对齐，再单独出脚本。

### 24.8 补完审查：SQL 正确性 + 网关性能两个维度

§24.6 那轮开了 4 个维度，其中 2 个因会话额度耗尽没跑完。本轮补完，两个维度共提出 12 条。
**所有验证 agent 再次因额度耗尽失败，12 条全部由人工对真库（只读）复核**——
用 JDBC 直连跑实际 SQL 与 `EXPLAIN`，不是靠读代码推断。

#### 确认并修复（7 条）

**① [P1] Token 子查询在 trace_id 重复时张冠李戴。**
`TraceWebFilter.resolveTraceId` **优先沿用**调用方传入的 `X-Trace-Id`（设计意图就是跨系统串联），
所以一次上游事务扇出成多次模型调用时，几次调用带同一个 trace_id，两表各写 N 行。
三个 `LIMIT 1` 子查询只能取到其中一行 → N 行报文显示**同一份** Token，数字错且不报错。
另外三个子查询是三次独立求值，不加 `ORDER BY` 时"取哪一行"在 SQL 语义上未定义，
理论上 input/output/source 可以来自不同行。

修法（未根治，做到"确定 + 可见"）：三个子查询统一加 `ORDER BY a.id` 保证确定且可复现；
增查一个 `audit_match_count`，>1 时前端把 Token 显示成 **⚠ Token 存疑** 并在 tooltip 里
说明原因，而不是安静地展示一个可能属于另一次调用的数字。
根治需要给报文行冗余 audit 行 id（改采集侧 + DDL），超出本次范围。

> 实测当前库 `mg_audit_log` 重复 trace_id 组数 = **0**，即机制真实存在但**尚未触发**——
> 现有调用方没有传 `X-Trace-Id`。

**② [P1] 深翻页 / 「末页」按钮绕过全部防护。** 所有防护原先都挂在 keyword 分支上，
但一次**不带任何条件**的深翻页同样会全表扫，而 UI 上就有个按钮直接触发它——
分页条的「末页」精确命中最大合法 OFFSET。被跳过的行仍要从聚簇索引读出，
且正文列因被 `LEFT`/`CHAR_LENGTH` 引用而进了 read_set，每条跳过的行都要物化完整 LONGTEXT。
新增 `MAX_OFFSET = 50000`，超限时提示改用时间范围定位。

**③ [P1] 管理面与网关共用全局 `Schedulers.boundedElastic()`。**
`CredentialAuthFilter` / `ModelAuthFilter` / `AppAccessControlFilter` / `QuotaFilter` /
`ModelRouteFilter` 全在用同一个全局单例，默认 `maxThreads = 10 × 核数`（4 核 = 40），
比 Druid 的 maxActive=100 更早打满。失败模式尤其糟：Druid 拿不到连接会 fail-fast，
而 boundedElastic 队列深 100000 且**无超时**——网关鉴权任务只是安静排队，
不报错不降级，表现为 `/v1/**` 延迟整体抬升而日志干净。
改为专用池 `mg-admin-payload`（4 线程 / 队列 64），**再慢也烧不到网关线程**。

**④ [P2] 全链路无超时。** JDBC URL 无 `socketTimeout`、`MybatisConfiguration` 无
`defaultStatementTimeout`、Controller 无 `.timeout()`，一条跑飞的查询没有任何东西能掐掉；
Reactor 的取消信号对已进入阻塞 JDBC 调用的线程无效。加 `@Options(timeout = 30)`
（JDBC statement 级，真正在服务端取消）+ `.timeout(35s)` 兜底。
这条本身不制造问题，但它是前几条的**倍数放大器**：决定了"用户不耐烦连点 5 次"的代价是
5 倍而不是 1 倍，也决定了最坏情况有没有上界。

**⑤ [P1] `appId`/`modelId` 不足以充当 keyword 的准入券。** 两个维度独立提出同一条。
它们能走索引**定位**，但不给候选集任何**上界**：内网通常只接个位数的系统，
主力 appId 常占全表七成到十成。在"能不能收窄"这件事上，单独的 appId 和被显式拒绝的
`upstreamStatus=200` 是同一档。收紧为：keyword 只接受 **TraceID（≥8 位）** 或
**两端齐全且跨度 ≤24h 的时间范围**。前端同步。

**⑥ [P2] `escapeLike` 依赖 MySQL 的隐式反斜杠转义。** `sql_mode` 含 `NO_BACKSLASH_ESCAPES`
时不存在默认转义符，转义会静默失效——正常关键字（`100%`、`user_id`）匹配不到任何行而返回空列表，
单个 `%` 又变回大范围匹配。JDBC URL 也没用 `sessionVariables` 固定 `sql_mode`。
改用 `!` 作转义符并**显式写 `ESCAPE '!'`** 子句，语义与 `sql_mode` 完全无关。

> 实测当前服务端 `sql_mode` = `ONLY_FULL_GROUP_BY,STRICT_TRANS_TABLES,NO_ZERO_IN_DATE,
> NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION`，**不含**
> `NO_BACKSLASH_ESCAPES`——所以旧写法在这台机器上是碰巧能用，换台机器就未必。

**⑦ [P2] Mapper 注释"大列的内容根本不出 MySQL"会误导后人。**
这句对**网络与堆**成立，对**磁盘 I/O 与 buffer pool 不成立**：`LEFT()`/`CHAR_LENGTH()` 是
SQL 层表达式，InnoDB 没有下推能力，列进了 read_set 就会把行外存储的完整 LONGTEXT
物化到行缓冲区，SQL 层才截断。按原注释理解会得出"pageSize 开大点、翻到末页也没关系"的
错误结论——而那恰好是最贵的两条路径。注释已改写为"代价与**扫过的行数**成正比"。

#### 实测**否定**的 1 条

**[P2] "只给 appId 时 ORDER BY 无法走索引，filesort 会把整个候选集的 LONGTEXT 拉出来"** —— 
`EXPLAIN` 不支持这个结论：

```
只给 appId：    type=index  key=idx_create_time  Extra=Using where; Backward index scan
appId+24h 窗口：type=range  key=idx_create_time  rows=418  Extra=Using index condition; ...
```

优化器选了 `idx_create_time` 做**反向索引扫描**满足排序、用 `Using where` 过滤 app_id，
**没有 filesort**。收紧后的典型查询（appId + 24h）是干净的 range scan。
保留一句提醒：这是在小表 + 单一主力 appId 下的计划，数据量与分布变化后优化器可能改选，
不能当成永久保证。

#### 报告但**未修**（需要你拍板）

**[P1] `AuditService`/`PayloadService` 的 flush 在 Druid 被占满时会静默丢整批数据。**
`flush()` 先 `drainTo(batch, 5000)` 把数据**取出队列**，再 try `batchInsert`，
catch 里只 `log.warn`，不重试也不回队。一旦连接池被慢查询占满，
`batchInsert` 在 maxWait=3000ms 后抛 `GetConnectionTimeoutException`，
**最多 5000 条审计记录 + 一整批报文当场消失且不可恢复**，现场只留一行 WARN。

审计表是计费与合规依据，静默丢 5000 条比查询变慢严重得多。
这是**既有代码的问题、不是本次引入**，但本次功能是目前唯一可能长时间占住 Druid 连接的路径，
让它从"理论上"变成"够得着"。上面的专用线程池 + 超时已经大幅降低触发概率，
但没有消除。修法（失败回队 / 落盘暂存 / 至少把丢弃条数打成 ERROR 指标）
涉及审计写入链路，风险面比本次功能大，**没有你的确认我不动它**。

## 25. 容器平台探测端点 + 审计/报文写库失败重试（不再丢数据）

### 25.1 容器探测端点（修复容器反复重启）

**现象**：行内容器平台启动完成后反复重启重试，平台侧不知道应用状态。
**根因**：平台约定在三个场景调用三个端点判断状态，本项目<b>一个都没有实现</b>，
全部 404，平台据此判定应用没起来。

| 场景 | 路径 | 返回 200 的条件 |
|---|---|---|
| 存活检查 | `/actuator/detection/running` | **进程活着就永远 200** |
| 流量检查 | `/actuator/detection/available` | 启动完成 且 未在优雅退出中 |
| 优雅退出 | `/actuator/detection/shutdown` | 总是 200（幂等） |

新增 `ContainerDetectionController` + `ServiceState`（两个 volatile 标志，不做任何 IO）。

**几个刻意的设计决定**：

- **存活检查绝不查 DB/Redis**。这是探针设计里最容易犯、后果最严重的错误：
  存活检查失败的语义是"这个进程坏了，重启它"。若把依赖连通性写进去，数据库抖动的一瞬间
  **所有实例会同时探测失败、被同时重启**，一次局部依赖故障放大成整个网关集群全面中断，
  且重启后依赖仍没好，陷入无限重启。本网关即使 MySQL 挂了，凭证/授权走 Caffeine 缓存
  仍能转发相当一部分流量，把自己摘掉反而更差。
- **路径挂在 `/actuator/` 之下**：六个业务过滤器都按该前缀跳过，探测请求天然不经过
  凭证鉴权/授权/配额/熔断/路由，不需要单独开白名单。否则探测会被 401 拦掉——
  那正是"容器不知道应用状态一直重启"最常见的成因。
- **GET 与 POST 都接受**：平台用哪个方法未明确约定，405 同样不是 200，一样会触发重启。
  用 `@RequestMapping(method = {GET, POST})` 而非叠加 `@GetMapping + @PostMapping`
  ——后者在同一方法上放两个 `@RequestMapping` 派生注解，Spring **启动时**就抛
  IllegalStateException，应用根本起不来。
- **退出端点先摘流量再刷盘，然后立刻回 200**：置 draining → 流量检查转 503 →
  平台摘流量 → 再发 SIGTERM。在途请求继续跑完（LLM 请求动辄几十秒到几分钟，切不得）。
  刷盘失败也返回 200：返回非 200 会让平台认为退出出错而改用强杀，反而丢更多。

同时开启 Spring 优雅停机（`server.shutdown: graceful` +
`spring.lifecycle.timeout-per-shutdown-phase: 30s`）。

**已实测**（本地起实例逐个打）：

```
GET/POST /running   → 200 running     （draining 期间仍 200 ✓）
GET/POST /available → 200 available   （shutdown 后转 503 draining ✓）
GET/POST /shutdown  → 200 draining    （重复调用仍 200 ✓）
```

### 25.2 审计/报文写库失败不再丢弃

§24.8 报告过、当时未修的那条，本轮按"生产环境"标准处理。

**原实现**：`flush()` 先 `drainTo(batch)` 把数据**取出队列**，再 try `batchInsert`，
catch 里只打一行 WARN。数据已离开队列，写失败就**永久消失且不可恢复**——
管理面一个慢查询占满 Druid 连接池，就足以让 5000 条审计当场蒸发，
月底对账对不上且无从补回。审计表是计费与合规依据。

新增 `PendingWriteBuffer<T>`，两个服务共用。四条设计要点各对应一个真实翻车点：

1. **失败即回收**：写失败的整批进入缓冲区，由后续 flush 重试，不再丢弃。
2. **指数退避**（2s 起翻倍，上限 60s）：数据库已经挂了还每 2 秒猛敲，只会让它更难恢复，
   还会把连接池等待队列堆满，反过来拖慢网关侧的鉴权查询。
3. **毒药记录隔离**：同一批连续失败 3 次后**对半拆分**重试。若失败原因不是"数据库不可用"
   而是"某条记录本身写不进去"（字段超长、编码非法），不拆分会让这一条坏记录
   **永久阻塞**整批，重试到天荒地老——这是"无限重试"方案最容易忽略的死穴。
   拆分能在 log₂(N) 轮内把坏记录缩小到单条，只丢那一条、其余全部救回。
4. **容量有上限 + 丢弃必须响亮**：数据库长时间不可用时无限缓冲会 OOM，那是整个网关挂掉，
   比丢审计严重得多。超限丢最旧批次，且所有真实丢弃一律 **ERROR** 级别 + 记录摘要 + 累计数，
   不再像原来那样混在 WARN 里没人看见。

**一个必须小心的正确性陷阱**：月度 Token 累计（`accumulateMonthlyTokens` → Redis INCRBY）
**不是幂等的**，必须且只能在数据首次出队时累加一次，**重试路径绝不能再碰**。
否则数据库抖动几轮就能把用户的月度配额凭空吃光，直接误伤线上业务。
代码里 token 累计已移到 DB 写入**之前**，保证"写库失败进重试队列"这条路径不会漏加也不会重复加。

**优雅退出刷盘**：两个服务都新增 `drainForShutdown()`（退出端点调用）+ `@PreDestroy`（兜底）。
内存队列里的数据一旦随进程退出就永久消失，而**发版是最频繁的进程退出场景**——
这等于每次发版都悄悄丢一批审计。刷盘有 15s 时限：数据库不可用时不能无限卡住退出流程，
否则平台等不及会强杀，反而丢得更多。

**已实测**（`PendingWriteBuffer` 行为验证，4/4 PASS）：

| 场景 | 结果 |
|---|---|
| DB 恢复后重试落库 | 写入 100/100，积压 0，丢弃 0 |
| 毒药记录隔离（100 条里 row42 写不进去） | **救回 99/99，丢弃恰好 1 条**，坏记录未混入 |
| 容量上限（防 OOM） | 积压 200 ≤ 上限 250，超出部分丢弃并 ERROR |
| 退出刷盘遵守时限 | DB 全失败时 11ms 返回，未卡死 |

## 22. 压测优化：连接池打满 + 事件循环阻塞 + 缓存雪崩三点根因修复

> 起因：用户提供一份 Direct vs Gateway 压测对比（延迟测试 10 轮、吞吐测试并发 1/5/10/20、稳定性测试
> 20 轮），核心异常两条：① 并发从 5 升到 10 时 Gateway QPS 断崖式下跌（2.64→1.46），Direct 同期稳定；
> ② 20 轮持续负载下 Gateway TTFT +62%、总时长 p99 达 11s，长尾严重。用 6 路并行调查逐项对代码找证据
> （连接池配置、过滤器链阻塞调用、Redis/MySQL 池实际大小、Resilience4j 配置、服务端线程与日志、
> 模型路由缓存刷新机制），排除了"网关出站 httpclient 池"（已显式配 500，非瓶颈）和
> "Resilience4j"（无 Bulkhead/RateLimiter，CLOSED 态不限流，压测证实断崖时无 503，进一步排除），
> 定位到三处确凿根因，按下列顺序修复（P0 对应并发断崖，P1 对应持续负载长尾）。

### 22.1（P0）MySQL 连接池从 HikariCP 硬编码 10 换成 Druid，maxActive=100

- 根因：`ServiceConfiguration.java` 手工构建的 `HikariDataSource` 硬编码 `maximumPoolSize=10`，
  且没设 `minimumIdle`/`connectionTimeout`（默认 30s）——测试并发恰好等于池上限，10 是断崖发生的
  精确阈值。这个池还要跟每 2s 跑一次的审计/报文批量写入任务抢连接（见 §16.4 旧 local 分页问题
  同源：`@Scheduled` 默认单线程调度器，本轮 22.3 一并修）。
- **改用 Druid**（非继续调 HikariCP 数字）：`pom.xml` 里 mybatis-plus-spring-boot3-starter 早就排除了
  HikariCP 并注释"内网框架统一使用 Druid"（此前只排除、未真正切换，是遗留的半成品），本轮切实换成
  `com.alibaba:druid:1.2.28`，手工构建 `DruidDataSource`（不用 `druid-spring-boot-3-starter`，与
  Redis/Jedis 手工构建 Bean 的既有模式一致，避免其自动装配跟手工 Bean 冲突）。
- **池参数（生产评估值，用户拍板）**：`maxActive=100`、`initialSize=5`、`minIdle=10`、`maxWait=3000ms`
  （拿不到连接最多等 3s 就抛异常，不无限阻塞请求线程）；`validationQuery=SELECT 1` +
  `testWhileIdle=true`（后台校验闲置连接，不占请求路径开销，`testOnBorrow=false`）；
  `removeAbandoned=true` + `removeAbandonedTimeout=180s` + `logAbandoned=true`（连接泄漏兜底，
  业务代码忘关连接时 180s 后强制回收并打 ERROR，防止池被占满后无法自愈）。
- **顺带清理**：`com/pab/middleware/venus/datasource/VenusDataSourceBean.java` 确认全仓零引用后
  物理删除——这是 §19.1 早就声称"已删除"但实际仍留在仓库里的桩类，`pom.xml`/`application.yml`/
  `README.md` 里残留的 HikariCP 相关注释一并改成 Druid。

### 22.2（P0）`TraceFilter.doFinally` 里 `parseUsageOnly` 名不副实，实际占用事件循环线程

- 根因：`UpstreamResponseParser.parseUsageOnly` 类注释写着"只扫描尾部若干字节，成本可忽略"，
  实际实现却是直接调用全量 `parse()`——流式响应逐帧 JSON 解析、拼出完整正文，事后整段丢弃。
  这段代码在 `TraceFilter.doFinally` 里同步执行、无 `subscribeOn`，doFinally 触发时机在
  `chain.filter()` 完成之后，很可能就在 Netty 事件循环线程上跑，且这是**全部已完成请求**都会走的
  路径（不是缓存 miss 才触发），响应越长、并发越高，占用事件循环线程的时间越长——直接影响的是
  同一事件循环上复用的所有并发连接，比单纯的连接池打满更隐蔽也更严重。
- **修复**：重写 `parseUsageOnly` 流式分支为真正的尾部反向扫描——从 SSE 帧数组末尾往前找，
  命中 usage + finish_reason（通常在最后 1~2 帧）即提前结束，不拼正文、不做全量正向遍历，
  最多扫描尾部 20 个有效帧（`TAIL_SCAN_FRAME_LIMIT`，防止极端情况下 usage 缺失导致仍扫全量）。
  usage 缺失时的估算兜底也不再依赖拼出的正文长度，改用响应总字节数粗略估算
  （精度略降，但本身就是 `estimated` 口径，允许有损失）。非流式分支本就轻量（`readTree` 一次），
  未改动。
- `UpstreamResponseParserTest.java` 新增用例 ⑩ 验证估算兜底路径，10/10 通过。
- `TraceFilter.java` 补注释：该 `doFinally` 能继续同步跑在调用线程、不 `subscribeOn`，前提是
  里面每一步都有界（`parseUsageOnly` 现在最多 20 帧，audit/payload 均是队列 `offer`）——谁再往
  这里加无界或阻塞操作，必须同步挪线程。

### 22.3（P0+P1）`CredentialAuthFilter` 每请求必查 DB + 5 个 Caffeine 缓存雪崩，一并修

- **P0 根因**：`CredentialAuthFilter` 对每个已鉴权请求都调用不走缓存的 `AppService.findByAppId`——
  这是有意设计（作为 `credentialCache` 60s TTL 之外的"App 禁用立即生效"实时兜底），但代价是
  100% 命中率的同步 MySQL 查询，直接推高 22.1 连接池的实际压力，是并发断崖的第二个放大因素。
- **P1 根因**：`GatewayCacheManager` 的 5 个 Caffeine 缓存（credential/modelAuth/accessRule/
  model/modelCredential）全部用手工 `getIfPresent`+`put`，不是原子加载——缓存 30s/60s 过期瞬间，
  多个并发请求会同时判定 miss、同时打 DB，这是缓存雪崩，直接对应 20 轮持续负载测试里 p99 抖动
  （测试时长跨越多个 TTL 边界）。
- **修复**：
  - `GatewayCacheManager` 新增 `appInfoCache`（L1 60s，evict-on-write），`AppService` 新增
    `findByAppIdCached()`，`CredentialAuthFilter` 改调用它。**取舍已知会**：此前"完全不缓存"是
    独立于 `credentialCache` 之外的第二层实时兜底，现在两层共享同一套 evict-on-write 机制，
    理论上仍满足 05 §8「App 禁用必须立即失效」（四个写路径 update/enable/disable/delete 均已
    同步调用 `evictAppInfoCache`），但确实少了一层独立保险——已在代码注释里显式记录，供后续
    review 时不会被误认为疏漏。
  - 全部 6 个缓存（含新增的 appInfo）的 `get*` 方法统一改为 Caffeine 原子 `Cache.get(key,
    mappingFunction)`：并发 miss 只执行一次 mappingFunction，其余并发调用等待复用结果。
    `credentialCache` 额外保留"不缓存空结果"的反刷库设计——mappingFunction 对未命中的凭证返回
    `null`，Caffeine 遇 `null` 不写入缓存，行为与此前一致。

### 22.4（P1）Jedis 连接池按生产值配置 + 无限等待改显式超时

- 根因：`RedisConfig.java` 的 `JedisPoolConfig` 硬编码 `maxTotal=16`，且从未设置
  `maxWaitMillis`，继承 commons-pool2 默认值 `-1`（无限等待）——池耗尽时借连接的线程会**永久挂起**
  而不是抛异常，`QuotaFilter`/`RateLimitService` 的 fail-open 逻辑（`catch Exception` 才放行）
  根本触发不到，是"越跑越慢、且不会自愈"这类长尾现象的候选机制之一。
- **修复（生产评估值，用户拍板）**：`maxTotal=100`、`maxIdle=32`、`minIdle=10`，
  显式 `maxWaitMillis=3000`（耗尽了 3s 内快速失败，走 fail-open，而不是无限期挂起）；
  `testWhileIdle=true` + 后台淘汰线程校验闲置连接，`testOnBorrow=false`（不在请求热路径上加一次
  PING 往返），思路与 22.1 的 Druid 配置一致。
- **本轮未做**：`QuotaFilter` 每请求最多 3 次串行 Redis 调用（QPS/日/月配额各一次 Lua eval）
  折叠成一次 pipeline/脚本——这是更深的功能改动，用户本轮只要求调池大小，未要求做，留作后续项。

### 22.5（P1）`@Scheduled` 任务专用线程池

- 根因：`ModelGateApplication` 只有裸 `@EnableScheduling`，无自定义 `TaskScheduler` Bean，
  Spring Boot 默认给 5 个定时任务（`AuditService.flush`/`PayloadService.flush` 各 2s 一次、
  `PayloadCleanupService`/`AuditCleanupService` 每日清理、`GatewayConfigService.refresh` 30s
  一次）分配的是单线程调度器，彼此排队执行，两个高频批量写库任务经常因此被对方拖慢。
- 新增 `SchedulingConfig.java`：`ThreadPoolTaskScheduler`，`poolSize=6`（按当前任务数+1点余量），
  `threadNamePrefix=mg-scheduled-` 便于线程 dump 时识别。

### 22.6（待验证收尾）logback-spring.xml 去 Profile 分支

- 压测时用户确认断崖发生瞬间**没有出现 503**，据此排除 Resilience4j 熔断器作为直接原因
  （见本节开头），是纯粹的延迟/吞吐劣化，不是被熔断拒绝。
- `logback-spring.xml` 此前按 `springProfile` 分 `dev,local,default` 与 `prod` 两块——与项目
  "全项目不用 Spring Profile"（§19）方向矛盾，且 Spring 把字面量 `"default"` 视为未设置任何
  Profile 时的隐式激活，导致 `dev,local,default` 那块（业务包 DEBUG）在没设置任何 Profile 的
  情况下**一直生效**，每个请求多打若干条 DEBUG 日志，是长尾延迟的次要贡献因素。用户要求删掉
  多 Profile、只留一套按生产配置：现在是单一 `<root>` 块（CONSOLE + ASYNC_FILE），业务包 DEBUG
  覆盖整段删除，生产默认 INFO。
- `README.md`「本地联调」章节同步重写：删除 `@Profile("local")` Bean、
  `spring.config.activate.on-profile: local` 文档块、`SPRING_PROFILES_ACTIVE` 默认 local 等

## 21. 内网合并后两个问题排查：测试弹窗 DOM 防御性修复 + Gateway 404 根因

### 21.1 admin.html 测试弹窗 `Cannot set properties of null`（本仓库改动）

现象：模型管理页点击「测试」按钮，控制台报 `TypeError: Cannot set properties of null (setting 'value')`，
定位在 `addTestMsg` 内 `$('tmsg-cnt-' + id).value = content`。**仅内网复现，外网不复现。**

排查：`$` 即 `document.getElementById`；创建元素时写的 `id="tmsg-cnt-${id}"` 与查询用的
`'tmsg-cnt-' + id` 是同一个 `id` 变量、同步执行、中间无其它代码插入——正常 DOM 环境下这段逻辑
不可能查出 null（`innerHTML` 赋值同步解析子元素，`appendChild` 不影响此前已生成的子元素）。
只在内网复现，判断是内网侧某类 DOM 干扰（如网页防篡改网关 / 终端管控代理向页面注入监控脚本，
造成 DOM 时序被打断），不是代码逻辑 bug，无法在本仓库单独复现或根治。

修复（防御性，不依赖确诊具体是哪个内网组件在干扰，只是不再给它可乘之机）：
- `addTestMsg`：改为直接持有刚创建 `div` 的引用 `div.querySelector('textarea')` 赋值，赋值完再
  `appendChild`，不再"插入 DOM 后按拼接 id 二次 `getElementById`"。
- `_buildTstMessages`：改为 `blk.querySelector('select'/'textarea')` 局部查询，同样不再依赖拼接 id
  做全局查询。
- 用户已在内网验证按钮恢复正常。

### 21.2 网关 `/v1/chat/completions` 404（内网侧改动，不在本仓库）

现象：内网合并部署后业务请求 404，日志 `reason=No static resource v1/chat/completions`——请求没
进 Gateway 路由，被 WebFlux 当静态资源处理器兜底。

**排查中先排除的两个方向（记录结论，避免以后走回头路）**：
- 曾怀疑 `spring.cloud.gateway.server.webflux.routes` 新前缀不被 Gateway 4.3.0 识别、需回退旧前缀
  `spring.cloud.gateway.routes`——查证 Spring Cloud Gateway 官方文档（4.2.7/4.3.4 Server WebFlux 参考
  手册）确认该前缀就是这个版本线的正确写法，本仓库 `application.yml` 现有写法没问题，**不要回退前缀**。

### 19.3 CryptoService 最后一处 getenv + 一个未决的框架级发现

**代码改动**：`CryptoService` 构造函数里 `System.getenv("MODELGATE_CRYPTO_KEY")` 这段应用层兜底代码
删除（19.2 完成后，`application.yml` 里的值已是永不为空的字面量，这段代码实际上走不到）。
类注释、四处异常信息里的 `MODELGATE_CRYPTO_KEY` 字样统一改成配置项名 `modelgate.crypto.key`。

**⚠️ 验证时发现一个更深的问题，未解决，需要下一轮定夺**：

删完应用层代码后，用一个假密钥 `export MODELGATE_CRYPTO_KEY=...` 再启动，**密钥仍然被环境变量覆盖了**——
`@Value("${modelgate.crypto.key:}")` 这个写法本身，Spring Boot 框架自带"环境变量名与配置项名互相映射"
的机制（`MODELGATE_CRYPTO_KEY` 自动识别成 `modelgate.crypto.key` 的另一种写法），且**环境变量的优先级
天生高于 `application.yml`**。这不是应用代码里的逻辑，删代码堵不住，只要有人（或部署脚本/容器编排）
不小心 `export` 过一次这个名字的环境变量，就会**静默覆盖** `application.yml` 里的值——

**✅ 决策已定（不加代码屏蔽，改立项目规矩）**：不给这一项加非标准代码去剔除环境变量 PropertySource。
用户明确定下**整个项目不使用环境变量**这条开发规矩——新增任何配置一律写字面量到 `application.yml`，
不使用 `${ENV:default}`、不 `export`、不读 `System.getenv(...)`，往后的开发也不主动引入环境变量依赖。
从源头避免有人手滑 `export` 撞上同名变量，比给单个配置项打补丁更彻底。此规矩已存入跨会话记忆
（memory: `modelgate-no-env-vars`），后续会话应默认遵守，不需要每次重新确认。

## 17. 删除 application-local.yml，合并进 application.yml

> 触发原因：用户直接在 `application.yml` 里改 `modelgate.crypto.key` 的默认值，改完不生效，
> 且**没有任何报错提示**，产生了"不知道为什么没生效"的误导。

**根因**：Spring Boot 对 `application-{profile}.yml` 的加载优先级**高于** `application.yml`。
本地默认 profile 是 `local`（`spring.profiles.active: ${SPRING_PROFILES_ACTIVE:local}`），
只要 `application-local.yml` 还在，里面写死的测试密钥
`bW9kZWxnYXRlLWxvY2FsLWRldi1hZXMyNTYta2V5ISE=` 就会**覆盖** `application.yml` 里的任何改动——
不管怎么改后者，本地永远用前者的值，且这是 Spring 的正常加载行为，不会有任何日志或报错提示这一点。

**最终方案（几经调整，见下方两次弯路）**：删除 `src/main/resources/application-local.yml`，
原内容**原样**合并进 `application.yml`，用 Spring Boot 官方支持的
「profile 专属文档块」写法——文件末尾以 `---` 分隔，加一段
`spring.config.activate.on-profile: local`，块内内容只在 `local` Profile 激活时生效，
效果与独立的 `application-local.yml` **完全等价**，区别只是现在两者在同一个文件里，
不会再出现"改了一个文件、实际生效的是另一个文件"的错位。原 `datasource.local.*` /
`redis.local.*` / `crypto.key` / `mybatis-plus.configuration.log-impl` 的真实值全部原样保留，
本地起服务**不需要 export 任何环境变量**，行为与用 `application-local.yml` 时完全一致——
已用零环境变量启动实测：连上原联调库、`credId=2` 的旧凭证正确解密（证明密钥也是原来那把）、
SQL 日志（StdOutImpl）同样生效。

**⚠️ 走过的两次弯路（记录下来避免重蹈覆辙）**：

1. **第一版**：把 `datasource.local.*` 改成 `${LOCAL_DB_URL:占位符}` 式的环境变量驱动，
   默认值只是无害占位符、不含真实联调库信息。理由是 `application.yml` 已入库，
   照抄真实数据库密码等于把凭证提交进 git 历史。**但这直接导致本地启动失败**
   （占位符指向的 `127.0.0.1:3306` 没有 MySQL 监听，用户不设环境变量就连不上）。
2. **第二版（在第一版基础上打补丁）**：给 `ServiceConfiguration.localDataSource` 加前置校验，
   检测到占位符默认值就抛出清晰提示，替代深埋的 `Connection refused` 异常栈。
   这确实把报错做得更好懂了，但**没有解决用户的真实诉求**——用户要的是"和以前一样能直接用"，
   不是"报错报得更清楚"。
3. **本版（采纳用户反馈）**：用户明确指出 `application-local.yml` 里的配置本来就是可用的，
   直接合并真实值即可，不需要占位符这层保护。改用 profile 专属文档块，
   原值原样保留在同一文件里，`ServiceConfiguration` 的前置校验一并撤销（不再需要）。
   `application.yml` 会入库、库密码会随之可见——这是用户对自己仓库的权衡取舍，
   不再由本轮改动替用户做保守选择。

（`ServiceConfiguration.localDataSource` / `RedisConfig.localCacheProvider`），内网用
`SPRING_PROFILES_ACTIVE=dev/prod` 时该 `on-profile: local` 文档块整体不生效，
以上账号密码不会被内网环境读取，可放心合入内网。

**连带清理**：`.gitignore` 移除 `application-local.yml` 死条目；`ServiceConfiguration` /

## 16. 日志补全 + 投产审核

> 目标：把「出了事能不能查」这件事补齐。改造前的实际状态是——
> 最常见的 401 后端一条日志都没有、所有日志的 traceId 都是空的、
> 被拒绝的请求一条审计都不留、管理页上 4 个开关有 3 个是摆设。

### 16.1 日志补全

改前 4 个类挂着 `@Slf4j` 却零日志、4 个 Service 连注解都没有。补全后：

| 位置 | 补了什么 |
|---|---|
| `CredentialAuthFilter` | 4 个**静默拒绝**分支（未带 Authorization / 凭证禁用 / 凭证过期 / 系统不可用） |
| `ModelAuthFilter` | 0→2 条，403 带 appId+modelId+原因 |
| `ModelRouteFilter` | 0→7 条，**区分「模型不存在」与「apiSpec 无对应适配器」**——同为 404 但后者是配置错误，混在一起排查会一直往调用方身上找 |
| `QuotaFilter` | 429 打出是 QPS / 日调用量 / 月 Token 哪一层触发 |
| `TraceFilter` | 完成日志 + 审计写入异常保护 |
| `App/Credential/ModelAuth/AccessRule Service` | 补 `@Slf4j` + 全部写操作 INFO（20 条） |
| `DynamicConfigHolder` | 启动打出开关**实际生效值**（改后需重启，不打出来只能翻配置文件猜） |

刻意的设计：密钥只打末 4 位（`tail4()`，不足 4 位全打码）；`revealSecret` 打 INFO
（[05 §4.1](./05-边界限制与禁止规则.md) 强制要求可追溯）；**删光访问规则时打 WARN**
（规则为空 = 不限制来源，是语义翻转不是普通删除）；`revoke` 打影响行数
（该方法不做存在性校验，`rows=0` 是区分「撤销成功」与「本来就没有」的唯一线索）。

**Controller 层未做大规模补日志**：Service 已覆盖全部写操作 INFO，Controller 再打是双份；
查询类按 [03 §7](./03-编码规范.md) 只能是 DEBUG（生产关闭），价值低。

### 16.2 MDC traceId 彻底修复（新增依赖）

**问题**：WebFlux 下请求在 Netty 事件循环组装、阻塞逻辑在 boundedElastic 执行，
MDC 这种 ThreadLocal 不会跟着走。实测所有日志的 `[%X{traceId}]` 都是空的 `[]`；
更严重的是事件循环线程上 `MDC.put` 后无人清理，会被后续**其它请求**的日志继承（串号）。

**方案**（三个组件配合，缺一不可）：

1. **新增 `filter/TraceWebFilter`**（WebFilter，`HIGHEST_PRECEDENCE`）——
   生成 traceId 写入 **Reactor Context**（不直接写 MDC）。
   用 WebFilter 而非 GlobalFilter 是关键：后者只对**匹配路由**的请求生效（即只有 `/v1/**`），
   管理面 `/modelgate/**` 走 Controller、不匹配任何路由，此前完全拿不到 traceId。
   支持沿用调用方传入的 `X-Trace-Id` 做跨系统串联（带长度与字符白名单校验，
   它会进日志和审计表，不能让调用方塞任意内容）。
2. **新增 `config/ReactorContextPropagationConfig`** —— 注册 MDC 的 `ThreadLocalAccessor`
   并开启 `Hooks.enableAutomaticContextPropagation()`，Reactor 在**每次线程切换**时
   自动把 Context 里的值写入目标线程 MDC、任务结束后清理。
   清理用 `MDC.remove` 而非 `MDC.clear`——后者会抹掉同线程上其它组件写入的 MDC。
3. **`TraceContext` 重写** —— 静态方法降级为「仅供非响应式上下文（定时任务）使用」，
   并在类注释里写明为什么不能在响应式链路里手动操作 MDC。

**⚠️ 新增依赖 `io.micrometer:context-propagation:1.1.3`**（36KB，**零传递依赖**）。
合入内网需确认该坐标可用，**缺失会导致启动直接失败**（ClassNotFound）。

✅ 实测：同一请求跨 `reactor-http-nio` 与 `boundedElastic` 两类线程，traceId 一致；
不同请求 traceId 互不串号；管理面 Controller 日志（此前恒空）现在也有值。

### 16.3 被拒绝的请求现在进审计了（TraceFilter order -150 → -200）

**问题**：审计写在 `TraceFilter.doFinally`，而它当时排在 -150，
在 CredentialAuth(-190)、AccessControl(-180)、ModelAuth(-170)、Quota(-160) **之后**。
GlobalFilter 链在拒绝处即中断，这四类拒绝（401/403/429）根本执行不到 TraceFilter →
**所有失败尝试一条审计都没有**，而安全审计恰恰最需要它。

**改动**：
- `TraceFilter` order **-150 → -200**，成为链路第一环，`doFinally` 覆盖全部结局。
  ⚠️ 原 [05 §6](./05-边界限制与禁止规则.md)「禁止更改任意 Filter 的 order」经决策解除——
  该禁令曾把这个缺陷锁死。现改为列出**必须满足的不变量**供改动前核对。
- 随之而来的约束：TraceFilter 执行时下游还没写入 appId/modelId，
  故这些字段一律在 `doFinally` 里从 exchange attribute 读取。
  **不要改回在方法开头读请求头**——那样读到的永远是 null。
- `CredentialAuthFilter` 增写 `mg.appId` / `mg.credType` 两个 attribute：
  请求头挂在 `mutate()` 出来的新 request 上、原 exchange 读不到，而 attribute 前后是同一份。
- 审计条件由 `appId != null` 改为**全量**；`mg_audit_log.app_id` 本就可空。

**⚠️ 改造过程中自己踩的坑（已修，留档警示）**：
一度把 `X-Mg-App` / `X-Mg-Model` 响应头的写入也放进了 `doFinally`，结果**成功请求全部丢审计**——
响应一旦提交 `getHeaders()` 就返回 `ReadOnlyHttpHeaders`，`set()` 抛 `UnsupportedOperationException`，
把同一个 try 块里的 `auditService.log()` 一起带走（401 因响应尚未提交而侥幸成功，
表现为「只有被拒请求进审计」这种极具误导性的现象）。
现改为 `beforeCommit` 回调写头，并在 `doFinally` 里注明**审计必须是第一等公民、
其后不得再放任何可能抛异常的操作**。

✅ 实测：401（appId 为空）与 200（appId=93918, model=gpt-4o, 301ms）均入库，审计失败次数 0。

**顺带修复 `AuditLogVO` 缺 `requestPath`**：DB 与 Entity 一直有 `request_path`，
唯独 VO 漏了，审计接口从不返回它——排查时看不出调用的是哪个端点。
与此前 `AppVO.authCount`、`AppModelAuthVO.modelName` 是同一类「VO 缺字段 → 前端恒 undefined」问题。

### 16.4 local profile 分页失效（连带清理 Apollo 遗留的 Profile 拆分）

**问题**：`TdsqlMybatisPlusConfig` 标了 `@Profile("!local")`，注释称

✅ 实测：`total` 由 0 变为真实值（apps=1、models=3）。

## 15. 凭证「接入示例」一键复制请求报文

> 动机：接入方拿到凭证后，还得自己拼 `Authorization` 头、猜路径、猜 `model` 该填什么，
> AKSK 更要自己实现 HMAC 签名。这些信息此前只散落在文档里，管理页上一点都没有。

**入口**：接入系统 → 凭证列表 → 每行「📋 接入示例」按钮。
弹窗给出 **curl / HTTP 原文 / Python** 三种格式，一键复制。

**几个关键决策（改之前先看，都是有意为之）**

- **默认不含密钥明文**，示例里是 `<在此填入 API Key>` 占位符，需显式点「🔑 填入真实密钥」
  才走 `GET /modelgate/credentials/secret` 单条解密取回。理由：这个弹窗的用途就是**复制出去发给别人**，
  默认带明文等于诱导把密钥贴进 IM／工单。取回后弹窗顶部提示改为红字，**关窗即从 ctx 与 DOM 清除**
  （[05 §4.1](./05-边界限制与禁止规则.md)「前端缓存明文」禁令）。
  存量凭证 `secretRetrievable=false` 时该按钮置灰并说明原因。
- **AKSK 不给静态报文，给能算签名的脚本**：签名 = `Base64(HMAC-SHA256(SK, AK + ":" + 毫秒时间戳))`，
  且服务端校验 ±5 分钟（见 `CredentialAuthFilter.verifyAkSkHmac`）。
  写死的 `Authorization` 头复制过去必然 401，**比不给还坑**。故 curl 给 bash+openssl 版、
  Python 给 hmac 版；HTTP 原文那一栏则显式把签名位置标成 `{Base64(HMAC-SHA256(...))}` 占位并附说明。
  也因此 **AKSK 不给 OpenAI SDK 示例**——SDK 塞不进每次都变的动态头。
- **api_key 的 Python 示例直接用 OpenAI 官方 SDK**（`base_url` 指到 `{网关地址}/v1`）——
  本网关就是 OpenAI 兼容的，这是接入方最省事的接法。
- **模型下拉只列「已授权 + 授权启用 + 未过期」的模型**（`isAuthUsable`）。
  列出不可用的模型 = 生成一份必然 403 的示例。实测该系统的 `glm5` 授权已于 2026-08-05 过期，已被正确剔除。
- **示例路径随模型类型切换**：`chat` → `/v1/chat/completions`，`embedding` → `/v1/embeddings`。
  `image`/`audio` 在 OpenAI 兼容规范下没有统一请求格式，**不假装能直接跑**，
  改为出一行显式提示让调用方按上游实际接口调整。
- **网关地址是可编辑输入框**，默认 `location.origin`。管理页与业务流量入口在内网未必同一个地址／文根，
  写死会给出错的地址。

**后端配套改动（1 处）**：`AppModelAuthVO` 增加 `modelType`，
`ModelAuthService.listByAppIdWithModelName()` 的联查由「只取 modelName」改为「取整个模型对象」回填名称+类型。
**查询次数不变**（本来就是批量联查，非 N+1），前端据此决定示例路径。

**前端**：`admin.html` 新增 `usageModal` 弹窗 + `openUsageModal/setUsageFmt/fillUsageSecret/
usageParts/usageCurl/usageHttp/usagePython/renderUsage/copyUsage/closeUsageModal`；
新增 `currentCreds` 缓存（按 credId 回查凭证类型/AK/可否取明文，避免把这些值拼进 `onclick` 参数
——凭证名含引号会直接把 HTML 拼坏）。
弹窗打开时**主动 `await loadAuths()`**：授权列表原本只在切到「模型授权」子页时才加载，
从凭证页直接打开会拿到空下拉。

✅ 已验证：编译通过；`admin.html` JS 语法检查通过；三种格式 × api_key/ak_sk × chat/embedding/stream
共 6 种组合的生成结果逐一核对（签名算法与 `CredentialAuthFilter` 逐字节对齐）；
真实数据下授权过滤结果正确。

## 14. 启动完成提示（StartupBannerPrinter）

> 现象：启动成功的唯一标志是 Spring 自己那行 `Started ModelGateApplication in 11.843 seconds`，
> 夹在满屏 INFO 中间，目测极难发现。

**新增** `config/StartupBannerPrinter`（**唯一新增文件**，无其它代码改动）——
在它之后（`ApplicationReadyEvent`，启动流程最后一步）多打几行：

```
================================================================
  ModelGate 启动成功
  Profile : local   Port : 18088   PID : 22432
  管理后台: http://192.168.66.73:18088/admin.html
  业务入口: http://192.168.66.73:18088/v1/chat/completions
  健康检查: http://192.168.66.73:18088/actuator/health
================================================================
```

**⚠️ 定稿前有一版更复杂的实现（横幅 20 行 + 独立模板文件 + 占位符解析引擎），已废弃**：
最初做成了「资源模板 + `PropertyPlaceholderHelper` 渲染 + 运行期变量表」，
理由是"版式与取值分离，改版式不用重新编译"——**对打印几行启动提示这件事是过度设计**，
本轮改为固定字符串直接拼，去掉模板文件与解析逻辑。**若后续真需要外部可配的版式，
再引入不迟；不要为尚不存在的需求预先搭基建。**

**实现要点（不多，都在这一个类里）**

- `log.info` 一条多行文本块（`"""..."""`），**不是** `System.out.println`（[03 §7](./03-编码规范.md) 禁令）；
  JSON 文件 appender 里也是完整一条（`\n` 转义），不会被切碎——已验证。
- 端口取自 `WebServerInitializedEvent`，不是读 `server.port` 配置项：
  配了 `server.port=0`（随机端口）时只有前者是真实值。
- 打印时机是 `ApplicationReadyEvent`，排在 `Started ...` 之后，是启动流程最后一条输出——

## 12. 新增模型 400 修复 + 可观测性补齐

> 现象：管理后台「模型管理 → 新增模型 → 保存模型」，`POST /modelgate/models` 返回 **HTTP 400**，页面提示 `失败: undefined`，后端控制台**无任何日志**。

**根因一：Jackson 未知字段导致请求体解码失败（→ 400）**
- `config/JacksonConfig` 的 `@Primary ObjectMapper` 为裸 `new ObjectMapper()`，`FAIL_ON_UNKNOWN_PROPERTIES` **默认开启**（Spring Boot 自动装配的 ObjectMapper 默认关闭）。该 Bean 被 WebFlux `Jackson2JsonDecoder` 用于解码全部请求体。
- `admin.html` 提交时携带 `paramMapping`，而 `CreateModelRequestBO` **无此字段** → `UnrecognizedPropertyException` → `ServerWebInputException`(400)。**请求未进入 Controller**，故 Controller 内加日志也无输出。
- 修复：`JacksonConfig` 显式 `.disable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES)`，与 Spring Boot 默认行为对齐。

**根因二：前端返回结构解析未随 §1 落地（→ `失败: undefined`）**
- §1 记载"`admin.html` 前端解析同步改为 `resultCode==='00000000'`/`resultMessage`"，**实际代码未改**，仍在读 `j.code===0` / `j.message`（12 处）。因 `j.message` 恒为 `undefined`，且成功响应（`resultCode="00000000"`）也会走失败分支——所有管理接口的成功提示此前均失效。
- 修复：新增 `isOk(j)` / `errMsg(j)` 作为读取返回结构的唯一入口（兼容旧 `code/message`），12 处调用点统一替换；失败提示追加 HTTP 状态码与 `logTraceId`，便于与后端日志对照。

**`paramMapping` 字段补齐（此前被静默丢弃）**
- `mg_model.param_mapping` 与 `ModelInstanceEntity.paramMapping` 一直存在，`admin.html` 也一直提交与回显，但 `CreateModelRequestBO` / `UpdateModelRequestBO` / `ModelVO` 三者均缺该字段 → 自定义字段映射无法保存、编辑无法回显。三处补齐，[04 §2.2](./04-接口与数据结构.md) 创建/更新请求体示例同步补充。

**日志与可观测性**
- `GlobalExceptionHandler`：`ResponseStatusException` 与 `BusinessException` 两个分支原本**不打任何日志**（仅 `else` 兜底分支 log.error），现按 [03 §7](./03-编码规范.md) 补 WARN，输出 method/path/status；新增 `rootCauseMessage()` 剥出异常链最深层原因（解码失败时 `getReason()` 仅为笼统描述，真因在 cause 中）。
- `ModelController` / `ModelService`：补 `@Slf4j`，create/update/enable/disable/delete 记 INFO，查询类记 DEBUG；密钥类字段仅打末 4 位。
- `logback-spring.xml`：`local/dev` profile 此前**仅挂 CONSOLE 不挂文件**，`logs/modelgate.log` 恒为 0 字节；改为控制台+文件双写，并放开 `com.pab.ficc.ibp.modelgate` 包 DEBUG。
- `application-local.yml`：打开 MyBatis SQL 日志（主配置为 `NoLoggingImpl`，SQL 全静音）。**属本地兼容件，合入内网时随 §6 处理。**

**编辑模型时上游鉴权配置无法保存**

> 现象：编辑已保存的模型，把「上游鉴权类型」改成"不鉴权"，保存提示成功但库中 `mg_model_credential` 无变化。

- 根因：`UpdateModelRequestBO` **没有 `credential` 字段**，`ModelController.update` 也只更新 `mg_model`，
  凭证从头到尾没人写。前端一直在 PUT body 里带 `credential`，被整段丢弃。
  `ModelService.upsertCredential` 写好了但**零调用方**，是死代码。
- 修复：`UpdateModelRequestBO` 补 `credential` + `toCredential()`；`ModelService.update` 增加 credential 参数，
  新增 `applyCredentialUpdate` 落库，语义见 [04 §2.2](./04-接口与数据结构.md)（none 清空密钥 / 留空沿用原值 / 有值加密覆盖）。
- 凭证列清空改用 `LambdaUpdateWrapper` 显式 `set`——MyBatis-Plus 默认 NOT_NULL 策略会跳过 null 字段，
  实体更新清不掉密钥列。
- `update` 补 `evictModelCredentialCache`：原先只清模型缓存，改了鉴权方式转发仍用旧凭证。
- **连带修复适配器**：`OpenAIAdapter` / `AnthropicAdapter` / `AzureOpenAIAdapter` 原先只判 `secretKey != null`，
  完全无视 `authType`——即使库中是 `none` 也照发鉴权头。新增 `ProviderAdapter.shouldAuthenticate` 统一判定，
  `none` 时禁止附加鉴权头。（`CustomAdapter` 原本就按 authType 分支，无需改）
- `ModelVO` 补 `authType` / `accessKey` / `secretKeyConfigured`：原先 VO 不含鉴权字段，
  编辑弹窗 `m.authType` 恒为 undefined，**永远显示默认的 api_key**，改没改都看不出来。
  `secretKey` 仍不下发；列表页凭证批量查询避免 N+1。

**连通性测试由桩改为真实探测**

> 现象：`/modelgate/models/test` 恒返回 `{"success":true,"latencyMs":0,"message":"...not yet implemented"}`。
> 编辑已保存模型必得 200「连通成功」（哪怕配置是错的测试数据）；新增模型因记录未入库返回 404，`data` 为 null，
> 页面显示 `失败: undefined`。**错误配置被判为可用，是必须修掉的误导性行为。**

- 新增 `service/ModelConnectivityService`：向上游发送**真实**最小推理请求，复用 `ProviderAdapter`
  （请求体转换 / 鉴权 Header / 上游 URL 拼接与 `ModelRouteFilter` 同一套逻辑），故"测通"等价于"真能路由"。
- **判定收紧为仅 2xx 算连通**；401/403、404、400/422、429、5xx、超时 / DNS 失败 / 连接拒绝分别给出定位话术，
  并回传 `httpStatus` / `upstreamUri` / `upstreamBody`（截断 500 字符）便于排查。
- 探测超时 `min(model.timeoutMs, 15000)`，缺省 10000，避免沿用 570s 业务超时导致页面长时间转圈。
- 支持**草稿模式**：新增 `TestConnectionRequestBO` 作为可选 body，新增流程中未入库的表单配置可直接探测；
  无 body 时退回按 `modelId` 查库（SK 解密后使用）。查询参数 `modelId` 改为非必填。**契约扩展已同步 [04 §2.2](./04-接口与数据结构.md)。**
- 新增 `ConnectivityTestVO` 替代原 `Map<String,Object>` 返回值。
- **测试结果不作为保存前置条件**：`submitModel()` 从不读取测试状态，弹窗内新增文案明示"测不通也可以先保存"。
- 前端 `testModelConn()` 重写：提交草稿配置、区分「请求失败」与「探测失败」、上游原文与实际请求地址放入 `title` 悬停可见。
