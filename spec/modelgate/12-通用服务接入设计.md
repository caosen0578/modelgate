# ModelGate · 12 · 通用服务接入设计（SSE / 普通 HTTP 接口走网关鉴权）

> **文档性质**：新增子系统的完整设计，供实现与评审对照。**本文档定稿前无任何代码改动。**
>
> **一句话**：在现有模型流量链路旁边，加一条**更短**的通用服务链路——复用凭证鉴权、访问控制、
> 配额、熔断、审计、报文留档全部既有能力，只新增"按路径找上游"这一段。

---

## 0. 背景与结论

### 0.1 需求

四五个内网应用系统（对话 harness 后端及其依赖）需要通过本网关对外提供接口，其中含 SSE 长连接。
诉求是**复用现有的接入系统 / 凭证 / 授权体系**，不再各自造一套鉴权。

### 0.2 可行性结论

**可以做，且新链路每请求开销低于模型链路一个量级。**

模型链路的路由键是**请求体里的 `model` 字段**，因此必须 `DataBufferUtils.join` 把整个请求体读全再解析 JSON——
这是当前热路径最贵的一步。通用服务的路由键是 **path**，在请求行里，**一个字节的 body 都不用碰**。

新链路相对模型链路省掉：

| 省掉的步骤 | 模型链路的代价 |
|---|---|
| 请求体全量缓冲 | 几百 KB ~ 几 MB |
| 请求体 JSON 流式扫描 | `BodyParseFilter` |
| 适配器 `readTree` + 重新序列化 | `RequestParamMerger` / `ProviderAdapter` |
| 响应 token 解析 | `UpstreamResponseParser` |
| 响应体采集 | 开关关闭时 |

### 0.3 三条已验证的关键事实

设计中最关键的三个技术前提，均已在 4.3.0 / reactor-netty 1.2.10 的 class 文件层面核实：

1. **连接池按上游地址分桶，不是全局共享。**
   `PooledConnectionProvider.channelPools` 的类型是 `ConcurrentMap<PoolKey, InstrumentedPool<T>>`，
   `PoolKey = (SocketAddress, pipelineKey)`。因此 `max-connections: 500` 是**每个上游 host:port 一份**。
   四五个接入系统各有独立域名/端口 → **天然隔离，零配置**，不与模型上游互抢。
   如需按上游定制限额，reactor-netty 原生提供
   `ConnectionProvider.Builder.forRemoteHost(SocketAddress, Consumer<HostSpecificSpec>)`。

2. **要换连接池实现，扩展点是 `HttpClientFactory`，不是 `NettyRoutingFilter`。**
   `GatewayAutoConfiguration$NettyConfiguration` 里只有 `gatewayHttpClientFactory` 带
   `@ConditionalOnMissingBean`，`routingFilter` **没有**。
   ⚠️ 因此"继承 `NettyRoutingFilter` 覆写 `getHttpClient(Route, exchange)`"这条路会导致
   **两个 NettyRoutingFilter 同时在链上、同 order，请求被转发两次**。禁止走这条。
   正确做法：自定义 `HttpClientFactory` 子类，覆写 `protected buildConnectionProvider(...)`。
   （**本次方案用不到**，按第 1 条已无必要，此处仅作结论留档，避免后来人重新踩。）

3. **单请求超时可以按路由下发。**
   `NettyRoutingFilter` 从 Route 的 **metadata** 读 `response-timeout` / `connect-timeout`
   （两个字符串常量已在其常量池中确认）。`ServiceRouteFilter` 本来就要替换 Route 对象，
   顺手带上 metadata 即可实现**每服务独立超时**。

### 0.4 顺带发现：`mg_model.timeout_ms` 是死字段

全项目对 `getTimeoutMs()` 的唯一调用在 `ModelConnectivityService`（管理面连通性探测）。
**转发热路径从未读取它**——所有模型实际都在用全局 `spring.cloud.gateway.server.webflux.httpclient.response-timeout: 570s`。

这意味着运营在模型管理页把超时改成 30 秒，真实流量并不会 30 秒超时。属于**现存缺陷**，
与本方案独立，但修法与 §0.3-3 完全相同（`ModelRouteFilter` 重建 Route 时补 metadata）。
建议随本次一并修，见 §8.3。

## 1. 核心概念

新增一个与「模型」平级的概念：**服务（Service）**。

| | 模型（Model） | 服务（Service） |
|---|---|---|
| 对外路径 | `/v1/**`（OpenAI 兼容，形状固定） | `/svc/{服务编码}/**` |
| 路由键 | 请求体的 `model` 字段 | path 第二段 |
| 是否读 body | **必须** | **不读** |
| 上游改写 | 适配器按 `api_spec` 转换请求体 | **不改请求体**，只换 header 和 URL |
| 授权表 | `mg_app_model_auth` | `mg_app_service_auth` |
| 配额维度 | app × model | app × service |
| 报文开关粒度 | 授权行（app × model） | **服务本身** |
| 用量口径 | Token | 调用次数 / 字节数 |

### 1.1 为什么不把 `mg_model` 泛化成「上游目标」加个 `target_type`

- `mg_model` 有 `api_spec` / `default_params` / `force_params` / `param_mapping` / `upstream_model_id`
  一整套**模型专属**字段，服务一个都用不上，混进去语义会浑浊；
- 两者**路由键本质不同**（body 字段 vs path），塞一张表迟早要靠 `if (targetType)` 分叉；
- 报文开关的粒度也不同（授权行 vs 服务本身）。

分表的代价只是多两个过滤器，且这两个过滤器与模型侧同层、互不干扰。

## 2. 路径约定

```
/v1/**          → 模型流量（现状，不动）
/svc/{code}/**  → 通用服务流量（新增）
/modelgate/**   → 管理面（现状，不动）
/actuator/**    → 运维端点（现状，不动）
```

### 2.1 录入的是「服务编码」，不是整个前缀

管理页面上只填 `crm` 这样一个短标识，`/svc/` 由网关拼接。
**不允许**运营手填 `/svc/crm`、`svc/crm`、`/svc/crm/` 三种写法，那会立刻产生匹配歧义。

校验规则（录入时拦截，不是运行时才炸）：

- 正则 `^[a-z0-9][a-z0-9-]{1,31}$`（小写字母数字连字符，2~32 位）
- 全局唯一（含逻辑删除位，见 §3.1 唯一键）
- 因整体位于 `/svc/` 之下，**结构上不可能与 `/v1/`、`/modelgate/`、`/actuator/` 冲突**

### 2.2 路径翻译

默认规则：**剥掉 `/svc/{服务编码}`，剩余部分原样拼到 `upstream_url` 之后**，query string 保留。

| 调用方请求网关 | 服务编码 | `upstream_url` | 网关实际转发 |
|---|---|---|---|
| `POST /svc/crm/api/v2/customer/query` | `crm` | `http://crm.intranet:8080` | `POST http://crm.intranet:8080/api/v2/customer/query` |
| `GET /svc/kb/search/sse?q=x` | `kb` | `http://kb-svc:9000/gateway` | `GET http://kb-svc:9000/gateway/search/sse?q=x` |
| `POST /svc/agent/` | `agent` | `http://agent:8000/run` | `POST http://agent:8000/run/` |

**接入方内部接口一行都不用改**，各自路径风格全部保留。他们唯一要做的两件事：
base URL 换成 `http://网关/svc/自己的编码`，凭证换成网关发的 key。

`mg_service.strip_prefix` 提供开关：`1`（默认）= 上述行为；`0` = 完整路径原样转发
（上游确实需要看到 `/svc/{code}` 时用）。

### 2.3 为什么必须是静态前缀（而不是每服务在库里登记任意前缀）

网关必须**在读 body 之前**判定流量类型，否则就得对所有流量先读 body 再判断——
那正是最贵的一步，等于把新接口的成本拉回和模型一样高。

若允许每服务自定义任意前缀（`/crm/**`、`/kb/**`），则每请求都要拿完整 path 去匹配一张前缀表，
且存在与 `/v1/`、`/modelgate/` 撞前缀的风险——那是一类只在运行时才暴露的配置事故。
固定根前缀把这个风险从"运行时"提前到了"结构上不可能"。

> **替代方案（暂不采用，留档）**：若某接入方路径已固化、无法加前缀，可改用
> `Host` 或 `X-Mg-Service` 请求头分流，同样在请求头阶段即可判定，效果等价。
> 代价是排查时看 URL 看不出走的哪条链路。

## 3. 数据模型

三张新表，全部遵循 `sql/modelgate_schema.sql` 的既有风格：内部规范基础字段
（`creater` / `create_time` / `updater` / `update_time` / `is_del` / `creater_um` / `updater_um`）、
唯一键含 `is_del`、InnoDB + utf8mb4。

### 3.1 `mg_service` —— 服务注册

```sql
CREATE TABLE IF NOT EXISTS mg_service (
    id             BIGINT       NOT NULL AUTO_INCREMENT           COMMENT '主键，自增',
    service_id     VARCHAR(64)  NOT NULL                          COMMENT '服务编码（业务唯一键），对外路径 /svc/{service_id}/**；^[a-z0-9][a-z0-9-]{1,31}$',
    service_name   VARCHAR(128) NOT NULL                          COMMENT '服务展示名称',
    owner_system   VARCHAR(128)                                   COMMENT '所属业务系统中文名（与 mg_app.system_name 同口径，仅展示）',
    upstream_url   VARCHAR(512) NOT NULL                          COMMENT '上游地址（协议+域名+端口[+固定前缀路径]，末尾斜杠会被规范化去掉）',
    strip_prefix   TINYINT(1)   NOT NULL DEFAULT 1                COMMENT '是否剥掉 /svc/{service_id} 再转发：1=剥掉（默认）0=完整路径原样转发',
    -- 每服务独立超时，通过 Route metadata 的 response-timeout 下发给 NettyRoutingFilter。
    -- SSE 长连接服务要给大值；普通查询接口给小值，避免上游卡死时连接被长期占用。
    -- 0 = 沿用全局 spring.cloud.gateway.server.webflux.httpclient.response-timeout
    timeout_ms     INT          NOT NULL DEFAULT 0                COMMENT '单请求超时（毫秒），0=沿用全局配置',
    sse            TINYINT(1)   NOT NULL DEFAULT 0                COMMENT '是否 SSE 服务：1=是（仅影响管理面展示与报文拼接方式，不影响转发）',
    -- 报文开关放在服务本身而非授权行：模型侧放授权行是因为不同接入系统合规要求不同；
    -- 服务侧的诉求是「每个接口录入时决定记不记」，粒度在接口本身，放这里更贴合且少一次查询。
    -- 将来若需按接入系统细分，再在 mg_app_service_auth 上加一个覆盖位。
    payload_log_enabled TINYINT(1) NOT NULL DEFAULT 0             COMMENT '请求/响应报文记录开关：1=记录到 mg_request_payload，0=不记录（默认关闭）',
    description    VARCHAR(512)                                   COMMENT '服务描述/备注',
    enabled        TINYINT(1)   NOT NULL DEFAULT 1                COMMENT '是否启用：1=启用 0=禁用（禁用后请求该服务返回 503）',
    creater        VARCHAR(50)  CHARACTER SET utf8mb4 COLLATE utf8mb4_bin DEFAULT NULL COMMENT '创建人',
    create_time    DATETIME     DEFAULT CURRENT_TIMESTAMP         COMMENT '创建时间',
    updater        VARCHAR(50)  CHARACTER SET utf8mb4 COLLATE utf8mb4_bin DEFAULT NULL COMMENT '修改人',
    update_time    DATETIME     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '修改时间',
    is_del         VARCHAR(50)  CHARACTER SET utf8mb4 COLLATE utf8mb4_bin DEFAULT '0' COMMENT '删除标志：1=已删除 0=未删除（逻辑删除）',
    creater_um     VARCHAR(100) DEFAULT NULL                      COMMENT '创建人 UM 账号',
    updater_um     VARCHAR(100) DEFAULT NULL                      COMMENT '更新人 UM 账号',
    PRIMARY KEY (id),
    UNIQUE KEY uk_service_id (service_id, is_del)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='通用服务注册（/svc/** 流量的上游目标）';
```

> **`service_id` 不做 `ON UPDATE CASCADE` 改名**：模型侧支持改名是因为 `model_id` 是对外协议字段
> （调用方请求体里写的就是它），有换名需求。服务编码是**路径的一部分**，改名等于换 URL，
> 接入方必须同步改代码——那不是"改名"，是"新建一个服务、下线旧的"。**服务编码一经创建不可修改**，
> 管理页面上该字段编辑时置灰。

### 3.2 `mg_service_credential` —— 上游鉴权凭证（与 `mg_service` 一对一）

```sql
CREATE TABLE IF NOT EXISTS mg_service_credential (
    id            BIGINT       NOT NULL AUTO_INCREMENT            COMMENT '主键，自增',
    service_id    VARCHAR(64)  NOT NULL                          COMMENT '关联 mg_service.service_id（一对一）',
    auth_type     VARCHAR(32)  NOT NULL DEFAULT 'none'           COMMENT '上游鉴权类型：none|api_key|ak_sk|custom_header',
    access_key    VARCHAR(256)                                   COMMENT 'AK（明文）；auth_type=custom_header 时不使用',
    secret_key    VARCHAR(512)                                   COMMENT 'SK/密钥，加密存储（AES-256-GCM，CryptoService）',
    -- 上游要求的固定自定义头，如 {"X-Tenant":"ficc","X-Channel":"gateway"}。
    -- 值同样经 CryptoService 整体加密（可能含密钥类内容），读取时解密后逐个 set 到上游请求。
    extra_headers TEXT                                           COMMENT '附加上游请求头（JSON 对象，加密存储）',
    creater       VARCHAR(50)  CHARACTER SET utf8mb4 COLLATE utf8mb4_bin DEFAULT NULL COMMENT '创建人',
    create_time   DATETIME     DEFAULT CURRENT_TIMESTAMP         COMMENT '创建时间',
    updater       VARCHAR(50)  CHARACTER SET utf8mb4 COLLATE utf8mb4_bin DEFAULT NULL COMMENT '修改人',
    update_time   DATETIME     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '修改时间',
    is_del        VARCHAR(50)  CHARACTER SET utf8mb4 COLLATE utf8mb4_bin DEFAULT '0' COMMENT '删除标志：1=已删除 0=未删除（逻辑删除）',
    creater_um    VARCHAR(100) DEFAULT NULL                      COMMENT '创建人 UM 账号',
    updater_um    VARCHAR(100) DEFAULT NULL                      COMMENT '更新人 UM 账号',
    PRIMARY KEY (id),
    UNIQUE KEY uk_service_id (service_id, is_del),
    CONSTRAINT fk_svccred_service FOREIGN KEY (service_id) REFERENCES mg_service (service_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='服务上游鉴权凭证';
```

`auth_type` 语义：

| 值 | 网关注入的上游请求头 |
|---|---|
| `none` | 不注入（上游在内网且自身不鉴权） |
| `api_key` | `Authorization: Bearer {secret_key}` |
| `ak_sk` | `X-Access-Key: {access_key}` + `X-Secret-Key: {secret_key}` |
| `custom_header` | 仅注入 `extra_headers` 里的内容 |

四种情况都**额外**注入 `extra_headers`（若非空）。

### 3.3 `mg_app_service_auth` —— 接入系统对服务的授权

```sql
CREATE TABLE IF NOT EXISTS mg_app_service_auth (
    id             BIGINT      NOT NULL AUTO_INCREMENT            COMMENT '主键，自增',
    app_id         VARCHAR(64) NOT NULL                          COMMENT '关联 mg_app.app_id',
    service_id     VARCHAR(64) NOT NULL                          COMMENT '关联 mg_service.service_id',
    enabled        TINYINT(1)  NOT NULL DEFAULT 1                COMMENT '是否启用：1=启用 0=禁用（禁用后该系统访问该服务返回 403）',
    qps_limit      INT         NOT NULL DEFAULT 0                COMMENT '每秒请求数上限，0=不限',
    daily_limit    INT         NOT NULL DEFAULT 0                COMMENT '每日请求数上限，0=不限',
    expires_at     DATETIME                                      COMMENT '授权过期时间，NULL=永久授权（过期等同禁用）',
    creater        VARCHAR(50)  CHARACTER SET utf8mb4 COLLATE utf8mb4_bin DEFAULT NULL COMMENT '创建人',
    create_time    DATETIME     DEFAULT CURRENT_TIMESTAMP        COMMENT '创建时间',
    updater        VARCHAR(50)  CHARACTER SET utf8mb4 COLLATE utf8mb4_bin DEFAULT NULL COMMENT '修改人',
    update_time    DATETIME     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '修改时间',
    is_del         VARCHAR(50)  CHARACTER SET utf8mb4 COLLATE utf8mb4_bin DEFAULT '0' COMMENT '删除标志：1=已删除 0=未删除（逻辑删除）',
    creater_um     VARCHAR(100) DEFAULT NULL                      COMMENT '创建人 UM 账号',
    updater_um     VARCHAR(100) DEFAULT NULL                      COMMENT '更新人 UM 账号',
    PRIMARY KEY (id),
    UNIQUE KEY uk_app_service (app_id, service_id, is_del),
    KEY idx_service_id (service_id),
    CONSTRAINT fk_svcauth_app     FOREIGN KEY (app_id)     REFERENCES mg_app (app_id),
    CONSTRAINT fk_svcauth_service FOREIGN KEY (service_id) REFERENCES mg_service (service_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='接入系统对通用服务的调用授权';
```

**没有 `monthly_tokens`**：服务不产生 Token，该维度对它无意义。
`RateLimitService.checkAllQuotas` 的月度参数传 `0`，方法内 `≤0` 直接跳过，**不额外发 Redis 命令**。

**没有 `payload_log_enabled`**：见 §3.1 的说明，报文开关在服务本身。

### 3.4 审计与报文表的改造

**复用 `mg_audit_log` 与 `mg_request_payload`**，不新建表——否则要把缓冲队列、批量刷盘、
失败重试、退出刷盘、保留期清理这整套机制再造一遍。

两张表各加两列：

```sql
ALTER TABLE mg_audit_log
    ADD COLUMN traffic_type VARCHAR(16) NOT NULL DEFAULT 'model' COMMENT '流量类型：model=模型流量 service=通用服务流量' AFTER trace_id,
    ADD COLUMN service_id   VARCHAR(64)                          COMMENT '服务编码（traffic_type=service 时写入，model 流量为 NULL）' AFTER model_id,
    ADD KEY idx_service_id (service_id);

ALTER TABLE mg_request_payload
    ADD COLUMN traffic_type VARCHAR(16) NOT NULL DEFAULT 'model' COMMENT '流量类型：model=模型流量 service=通用服务流量' AFTER trace_id,
    ADD COLUMN service_id   VARCHAR(64)                          COMMENT '服务编码（traffic_type=service 时写入，model 流量为 NULL）' AFTER model_id,
    ADD KEY idx_service_time (service_id, create_time);
```

> ⚠️ **`mg_audit_log` 是高频追加表，可能已有大量数据**，两个 `ADD COLUMN` + 一个 `ADD KEY`
> 在生产上必须评估锁表时长（MySQL 8 的 `ADD COLUMN` 多为 INSTANT，`ADD KEY` 为 INPLACE 但仍需时间）。
> 执行前先 `SELECT COUNT(*)`，必要时安排在低峰或走 `pt-online-schema-change`。见 §9 手动执行清单。

**⚠️ 为什么不复用 `model_id` 列装 `service_id`**：现有用量统计 SQL 按 `model_id` 分组，
塞进去会让服务流量混进模型用量报表。加独立列 + `traffic_type`，
**现有统计查询只需补一个 `WHERE traffic_type = 'model'`**（默认值保证历史数据自动归位）。

## 4. 过滤器链

### 4.1 总览

| order | 过滤器 | 模型流量 | 服务流量 | 改动 |
|---|---|---|---|---|
| — | `TraceWebFilter`(HIGHEST) | ✅ | ✅ | 无 |
| -200 | `TraceFilter` | ✅ | ✅ | **改**：计算流量类型；service 跳过 token 解析 |
| -190 | `CredentialAuthFilter` | ✅ | ✅ | **零改动** |
| -180 | `AppAccessControlFilter` | ✅ | ✅ | **零改动** |
| -175 | `BodyParseFilter` | ✅ | **跳过** | **改**：按流量类型短路 |
| -170 | `ModelAuthFilter` | ✅ | **跳过** | **改**：按流量类型短路 |
| **-170** | **`ServiceAuthFilter`** | **跳过** | ✅ | 🆕 |
| -160 | `QuotaFilter` | ✅ | ✅ | **改**：配额键按流量类型取 model/service |
| -145 | `PayloadCaptureFilter` | ✅ | ✅ | **改**：开关来源按流量类型不同 |
| -140 | `ModelRouteFilter` | ✅ | **跳过** | **改**：按流量类型短路 + 补 Route metadata |
| **-140** | **`ServiceRouteFilter`** | **跳过** | ✅ | 🆕 |
| -50 | `CircuitBreakerFilter` | ✅ | ✅ | **改**：按目标取熔断器实例 |

> `ServiceAuthFilter` 与 `ModelAuthFilter` 同为 -170、`ServiceRouteFilter` 与 `ModelRouteFilter`
> 同为 -140 是**有意的**：同一时刻只有一个会真正执行（另一个按流量类型立即 `chain.filter` 放行），
> 两者互斥，相对顺序无意义。同 order 的 GlobalFilter 由 Spring 按 bean 名排序，稳定但不需要关心。

### 4.2 流量类型只算一次

**这是本方案对现有 `/v1/**` 链路唯一的正向改动。**

现状：`ModelRouteFilter` / `QuotaFilter` / `ModelAuthFilter` 等**每个过滤器都在重复做 2~3 次
`path.startsWith(...)`**（管理面前缀、actuator 前缀、业务前缀各一次）。

改为在 `TraceFilter`(-200，第一个 GlobalFilter) 里算一次，存 attribute：

```java
public enum TrafficType { MODEL, SERVICE, INTERNAL }
// exchange attribute key: "mg.trafficType"
```

判定规则（顺序不可换，`INTERNAL` 必须最先判）：

```
path.startsWith("/modelgate/") || path.startsWith("/actuator/")  → INTERNAL
path.startsWith("/v1/")                                          → MODEL
path.startsWith("/svc/")                                         → SERVICE
其余                                                              → INTERNAL（保守放行，交由路由 404）
```

后续过滤器一律读 attribute，**禁止再写任何路径字面量判断**——这条与
`UrlConstant.BASE` 的既有约束同性质，写进 05 文档。

**净效果：现有模型链路每请求少做十几次字符串前缀比较，比现状略快。**

### 4.3 `ServiceAuthFilter`（order = -170）🆕

结构与 `ModelAuthFilter` 一一对应，逐条对照实现：

1. `trafficType != SERVICE` → 直接 `chain.filter(exchange)`
2. 从 path 第二段取 `serviceId`；取不到（如 `/svc/` 或 `/svc`）→ 404 `SERVICE_NOT_FOUND`
3. 写入 attribute `mg.serviceId`（供 QuotaFilter / PayloadCaptureFilter / ServiceRouteFilter / TraceFilter 复用，
   **不再二次解析 path**）
4. `Mono.fromCallable(() -> Optional.ofNullable(checkAuth(appId, serviceId)))`
   `.subscribeOn(Schedulers.boundedElastic())` —— **必须包 `Optional`**，
   原因见 `ModelAuthFilter` 里那段注释（`Callable` 返回 null 会让 Mono 变 empty、
   flatMap 不执行、链路静默断掉、返回 200 空响应）
5. `checkAuth` 判定顺序与模型侧一致：

| 检查 | 失败返回 | HTTP |
|---|---|---|
| 服务存在 | `SERVICE_NOT_FOUND` | 404 |
| 服务已启用 | `SERVICE_DISABLED` | 503 |
| 存在授权行 | `SERVICE_NOT_AUTHORIZED` | 403 |
| 授权行已启用 | `SERVICE_NOT_AUTHORIZED` | 403 |
| 授权未过期 | `SERVICE_AUTH_EXPIRED` | 403 |

新增 `ErrorCode` 枚举 5 项，编号段与模型侧错开。
HTTP 状态取自 `ErrorCode` 自身，**不要写死 403**——模型侧踩过这个坑
（"状态码 403、响应体 code:404" 的自相矛盾，见 `ModelAuthFilter` 注释）。

### 4.4 `ServiceRouteFilter`（order = -140）🆕

比 `ModelRouteFilter` 简单得多：**不读 body、不解析 JSON、不做参数合并、无适配器**。

1. `trafficType != SERVICE` → 直接放行
2. 读 attribute `mg.serviceId`（`ServiceAuthFilter` 已解析并校验过存在性）
3. 从缓存取 `ServiceEntity` + 解密后的 `ServiceCredentialEntity`
4. 拼上游 URI：
   ```
   base      = upstream_url 去掉末尾 '/'
   remainder = strip_prefix ? path.substring("/svc/{serviceId}".length()) : path
   upstream  = base + remainder + (query != null ? "?" + query : "")
   ```
5. **替换 Route 对象**（与 `ModelRouteFilter` 同样的理由：只设
   `GATEWAY_REQUEST_URL_ATTR` 会被 `RouteToRequestUrlFilter`(order=10000) 用静态 uri 覆盖），
   并**带上 metadata**：
   ```java
   Map<String,Object> md = new HashMap<>(route.getMetadata());
   if (service.getTimeoutMs() != null && service.getTimeoutMs() > 0) {
       md.put("response-timeout", service.getTimeoutMs().longValue());
   }
   Route.async().id(route.getId()).uri(upstreamUri).order(route.getOrder())
        .asyncPredicate(route.getPredicate()).filters(route.getFilters())
        .metadata(md).build();
   ```
6. 用 `ServerHttpRequestDecorator` 覆写 `getURI()` 与 `getHeaders()`。
   **不覆写 `getBody()`** —— 请求体原样流式透传，这是新链路比模型链路轻的关键。

### 4.5 上游请求头构造：复用刚修好的那段逻辑

`ModelRouteFilter` 里刚修复的 `buildUpstreamHeaders(inbound, upstreamAuth, contentLength)`
（见 11-变更记录 §33）**上抽为公共工具** `UpstreamHeaderBuilder`，两条链路共用。

服务侧多两点：

- **不需要改写 `Content-Length`**（请求体没被改），因此提供不带该参数的重载
- `extra_headers` 里的自定义头合并进 `upstreamAuth`

**必须剔除的入站头（`INBOUND_ONLY_HEADERS`）**：`Authorization`、`X-Mg-App`、`X-Mg-Cred-Type`。

> ⚠️ 这一条对服务侧尤其重要。模型侧的教训是：合并逻辑靠"上游头同名覆盖"来去除调用方凭证，
> 四种 api_spec 里只有一种碰巧成立，另外三种把网关凭证明文发给了上游。
> 服务侧的 `auth_type` 有 `none` / `custom_header` 两种**根本不写 `Authorization`** 的取值，
> 若不显式剔除，网关凭证会直接散给四五个接入系统。

### 4.6 `QuotaFilter`（-160）改动

`RateLimitService` 的方法签名从 `(appId, modelId, ...)` 泛化为 `(appId, targetId, ...)`，
Redis key 前缀按流量类型区分，**避免 model 与 service 同名时计数串台**：

```
模型：rl:quota:qps:{appId}:{modelId}:{epochSec}
      quota:daily:{appId}:{modelId}:{yyyy-MM-dd}
服务：rl:quota:qps:svc:{appId}:{serviceId}:{epochSec}
      quota:daily:svc:{appId}:{serviceId}:{yyyy-MM-dd}
```

月度 Token 层传 `0`，`checkAllQuotas` 内 `≤0` 短路跳过，**不发 Redis 命令**。
服务流量稳态下最多 2 次 Redis 往返（QPS + 日），比模型侧还少一次。

> **⚠️ 禁止用 Lua**（内网 Redis 禁用 `EVAL`/`EVALSHA`/`SCRIPT LOAD`，见
> `RateLimitService` 类注释与 11-变更记录 §31）。新增 key 同样必须**在 key 名里带时间桶后缀**，
> 这是"能安全地把 `if current==1 then EXPIRE` 挪到客户端"的前提。

### 4.7 `PayloadCaptureFilter`（-145）改动

开关来源按流量类型分叉：

| 流量类型 | 开关来源 |
|---|---|
| MODEL | `mg_app_model_auth.payload_log_enabled`（授权行，现状） |
| SERVICE | `mg_service.payload_log_enabled`（服务本身，attribute `mg.serviceId` 已就绪） |

全局总开关 `modelgate.payload-log.enabled` 与内存保护阈值 `max-capture-bytes` 两条链路共用，不变。

**服务流量的响应解析**：不做 token 解析、不拼 `response_text`（那是 OpenAI 帧格式专用），
只写 `response_raw`。`finish_reason` / `input_tokens` / `output_tokens` 留空。

### 4.8 `CircuitBreakerFilter`（-50）改动

现状是**单一全局熔断器** `modelUpstream`——一个上游挂掉会拖累所有上游。
服务侧从第一天就按目标隔离：

```java
String cbName = trafficType == SERVICE ? "svc:" + serviceId : "modelUpstream";
CircuitBreaker cb = registry.circuitBreaker(cbName, "serviceUpstream");  // 服务用独立配置
```

服务的熔断阈值**必须与模型不同**——模型的 `slowCallDurationThreshold: 180s` 对普通业务接口是天文数字：

```yaml
resilience4j:
  circuitbreaker:
    configs:
      serviceUpstream:
        slidingWindowType: COUNT_BASED
        slidingWindowSize: 20
        failureRateThreshold: 50
        # 普通业务接口 5s 就算慢；SSE 长连接服务需在服务表上单独放宽（见下方 TODO）
        slowCallRateThreshold: 90
        slowCallDurationThreshold: 5s
        waitDurationInOpenState: 30s
        permittedNumberOfCallsInHalfOpenState: 5
        automaticTransitionFromOpenToHalfOpenEnabled: true
    instances:
      modelUpstream: { ... 现状不变 ... }
```

> **已定（2026-08-26 核实后修订）**：**慢调用熔断整体关闭**，只保留失败率熔断。
> 理由见 §11.2——慢调用阈值对本项目这种"正常就要跑很久"的负载是纯误报源，
> 而且现有实现还有一个 permit 泄漏 bug 会让熔断器永久卡死。
> 上表中 `slowCallRateThreshold` 与 `slowCallDurationThreshold` 两项**不要配**
> （`slowCallRateThreshold` 默认值就是 100，即永不因慢调用熔断）。
>
> `registry.circuitBreaker(name, config)` 是 `ConcurrentHashMap.computeIfAbsent`，
> 每请求一次，开销可接受。

### 4.9 缓存

`GatewayCacheManager` 新增两个 Caffeine L1，参数对齐模型侧：

| 缓存 | TTL | maximumSize | 说明 |
|---|---|---|---|
| `serviceCache` | 30s | 1_000 | `Optional<ServiceEntity>`，对齐 `modelCache` |
| `serviceCredentialCache` | 30s | 1_000 | `Optional<ServiceCredentialEntity>`，对齐 `modelCredentialCache` |
| `serviceAuthCache` | 60s | 5_000 | `List<AppServiceAuthEntity>` by appId，对齐 `modelAuthCache` |

全部用 `get(key, mappingFunction)` 原子加载（Caffeine 对同 key 并发 miss 只执行一次 loader，
防缓存击穿/雪崩）——这是 22 节压测优化定下的规矩，新代码必须照做，**禁止用
`getIfPresent` + `put` 的写法**。

## 8. 对现有 `/v1/**` 链路的改动点汇总

这是评审时最需要盯的部分——**所有改动都不应改变模型流量的行为**。

| # | 位置 | 改动 | 风险 |
|---|---|---|---|
| 8.1 | `TraceFilter`(-200) | 新增流量类型计算并存 attribute | 低 |
| 8.2 | 6 个过滤器 | 前缀判断从 `startsWith` 改读 attribute | 低，**净收益**（每请求少十几次字符串比较） |
| 8.3 | `ModelRouteFilter`(-140) | 重建 Route 时补 metadata，让 `mg_model.timeout_ms` **真正生效** | ⚠️ **行为变化**，见下 |
| 8.4 | `RateLimitService` | 参数名 `modelId` → `targetId`，模型侧 key **保持原样** | 低（key 不变，存量计数不失效） |
| 8.5 | `ModelRouteFilter` | `buildUpstreamHeaders` 上抽为 `UpstreamHeaderBuilder` | 低，纯移动，测试已覆盖 |
| 8.6 | `CircuitBreakerFilter`(-50) | 按流量类型取熔断器实例；模型侧仍取 `modelUpstream` | 低 |
| 8.7 | `mg_audit_log` / `mg_request_payload` | 各加 2 列 1 索引 | ⚠️ **大表 DDL**，见 §9 |
| 8.8 | 现有用量统计 SQL | 补 `WHERE traffic_type = 'model'` | 低（默认值保证历史数据归位） |

### 8.3 展开：让 `timeout_ms` 生效是一次真实的行为变化

现状所有模型都在用全局 570s。改动后，库里 `timeout_ms` 非 0 的模型会**按各自的值超时**。

`mg_model.timeout_ms` 的 DDL 默认值是 **30000（30 秒）**——如果存量数据大多是这个默认值，
**一上线所有模型都会变成 30 秒超时，而 LLM 请求正常就要跑 30~180 秒，等于全线中断。**

⚠️ **因此这一项必须先查存量分布再决定**：

```sql
SELECT timeout_ms, COUNT(*) FROM mg_model WHERE is_del = '0' GROUP BY timeout_ms;
```

三种处置，实现前必须选定：

- **A（推荐，最保守）**：本次**不动模型侧**，只给服务侧用 metadata；`mg_model.timeout_ms`
  维持现状（管理页上标注"仅用于连通性测试"），另开一轮专门处理
- **B**：先把存量 `timeout_ms` 批量刷成合理值（如 570000）再启用
- **C**：只有 `timeout_ms > 60000` 时才下发 metadata，小值视为误配忽略

**已定（2026-08-26 用户确认）：按 A 执行。**

用户原话：内部模型处理复杂问题时曾出现**跑满 20 分钟**才返回最后一次响应（`[DONE]`）；
网关侧的域名/负载均衡会另行设置超时；**本项目内不需要单独设置超时时间，等模型响应即可**。

因此：

- `ModelRouteFilter` **不引入** metadata，本方案范围内只做 8.5 的纯移动
- `mg_model.timeout_ms` 维持"仅用于管理面连通性测试"的现状，
  **管理页面上该字段必须加提示文案**「仅用于连通性测试，不影响真实转发超时」，
  否则运营会一直以为它管用
- 服务侧的 `mg_service.timeout_ms` 保留字段与 metadata 机制，但**默认值 0（沿用全局）**；
  它存在的意义是将来某个服务确实需要短超时时不必改代码

⚠️ 但"等模型响应即可"这句话与**当前配置的实际行为并不一致**，且不一致的地方不止一处。
详见 §11。

## 11. 超长请求（20 分钟级）的时限边界核实

> **背景**：用户确认内部模型处理复杂问题时，一次请求可能跑满 **20 分钟（1200 秒）**
> 才吐出 `[DONE]`，诉求是"网关不设超时、一直等模型响应"。
>
> **核实方式**：2026-08-26 对 reactor-netty 1.2.10 / spring-cloud-gateway-server 4.3.0 /
> resilience4j 2.2.0 的 **class 字节码**逐项核实（无 sources jar，用 `javap -c -p`
> 看常量池与指令）。以下每条都给出了据以判断的具体位置。

### 11.1 逐项结论

| # | 边界 | 配置值 | 对 1200s 请求 | 依据 |
|---|---|---|---|---|
| 1 | `httpclient.response-timeout` 对 **SSE 响应体** | 570s | ✅ **不掐断** | 见下 |
| 2 | `httpclient.response-timeout` 对 **非流式请求** | 570s | ❌ **第 570 秒 504** | 见下 |
| 3 | 连接池 `max-life-time` | 10m | ✅ **不掐断** | 见下 |
| 4 | 连接池 `max-idle-time` | 120s | ✅ **不掐断** | 同上 |
| 5 | 服务端 `server.netty.*` | 未配置 | ✅ **不掐断** | 三项默认全为 null |
| 6 | 优雅停机 `timeout-per-shutdown-phase` | 30s | ❌ **发版时硬切** | 见 §11.3 |
| 7 | 熔断器慢调用 | 180s / 90% | ❌ **误熔断** | 见 §11.2 |
| 8 | 上游侧 F5 / SLB idle timeout | 未知（注释称 600s） | ⚠️ **网关外，需运维确认** | — |

**第 1、2 条的机制**（这两条是同一个配置的两种表现，必须一起理解）：

`HttpClientFactory` 的字节码里对 `responseTimeout` 的引用数是 **0**——
**Spring Cloud Gateway 从不调用 `HttpClient.responseTimeout(...)`**，
所以 reactor-netty 那个 `reactor.left.responseTimeoutHandler`（本质是
`io.netty.handler.timeout.ReadTimeoutHandler`）**从未被装配**。

570s 只以 `NettyRoutingFilter` 里一层 `Flux.timeout` 的形式存在，
而它包住的那个 Flux 在**响应头到达**时就发射唯一元素并 complete，定时器随即取消。

- ⇒ **流式（`stream: true`）**：响应头几秒内就到，此后 1200 秒的 SSE 帧完全不在计时范围内，
  跑满 20 分钟没问题。**当前配置已经满足"一直等模型"的诉求。**
- ⇒ **非流式（`stream: false`）**：上游通常生成完才吐响应头，第 570 秒触发
  `TimeoutException("Response took longer than timeout: PT9M30S")` → 客户端收 **504**，
  而上游还在算。**这条今天就是坏的**，与本方案无关。

**第 3、4 条的机制**：`SimpleDequePool.evictInBackground()` 的字节码显示，
它只取 `IDLE_RESOURCES` 这一个队列做 `iterator()` 并逐个 `evictionPredicate.test(...)`。
正在被借出（`acquired`）的连接**不在这个队列里**，后台清理任务扫不到它。
`max-life-time` 与 `max-idle-time` 都只在**归还或借出**时判定。
⇒ application.yml 里那句注释「只在连接归还或借出时判定，不会掐断正在进行中的请求」**属实**。
一条被 1200 秒请求占用的连接，会在请求结束归还时才因超龄被销毁。

### 11.2 熔断器：会因"正常的长请求"而误开，且可能永久卡死

**这是本次核实里最严重的一条，且与用户"等接口响应就好"的诉求直接冲突。**

**慢调用阈值不掐断当前请求**——它只做统计。但统计到阈值后熔断器 OPEN，
**后续正常请求被直接 503 拒绝**，后果比掐断单条更大。

三个环节逐一核实：

1. **计时终点是"响应体全部写回客户端"**。
   `NettyWriteResponseFilter.WRITE_RESPONSE_FILTER_ORDER = -1`，而 `CircuitBreakerFilter`
   的 order 是 **-50**，更小 ⇒ 更靠外 ⇒ 它的 `chain.filter(exchange)` 把写响应体那一段也包了进去。
   ⇒ 一条 1200 秒的**正常** SSE 流，被记成 `onSuccess(duration = 1200s)`。

2. **有效 `minimumNumberOfCalls` 是 20，不是默认的 100**。
   `CircuitBreakerConfig.Builder.build()` 里**没有**裁剪（直接 `getfield`→`putfield`），
   裁剪发生在 `CircuitBreakerMetrics` 构造器：COUNT_BASED 分支执行
   `Math.min(config.getMinimumNumberOfCalls(), slidingWindowSize)` = `min(100, 20)` = **20**。
   ⇒ 窗口攒满 20 次调用就开始算比例。

3. **触发条件**：`slowCallRateThreshold: 90` + `slidingWindowSize: 20`
   ⇒ 最近 20 次里 **≥18 次超过 180 秒**，熔断器 OPEN 60 秒，期间所有请求
   走 `tryAcquirePermission()` 返回 false 的分支，直接 503 `UPSTREAM_CIRCUIT_OPEN`。

   本项目的真实负载是「正常 30~180 秒、复杂问题到 1200 秒」，
   **连续 18/20 次超过 180 秒是完全正常的业务形态**，不是故障。

4. **更糟的一条：HALF_OPEN 的 permit 会泄漏，可能永久卡死。**
   `CircuitBreakerStateMachine$HalfOpenState` 用一个 `AtomicInteger permittedNumberOfCalls`
   计数，`tryAcquirePermission()` 递减、`releasePermission()` 递增。
   而 `CircuitBreakerFilter` 只挂了 `.doOnSuccess(...)` 和 `.doOnError(...)`，
   **没有 `.doOnCancel(...)`**。SSE 场景下客户端中途断开会让 Mono 走 **cancel** 信号，
   两个回调都不触发 ⇒ **permit 有借无还**。
   而 `DEFAULT_WAIT_DURATION_IN_HALF_OPEN_STATE = 0`（本项目未配置该项），
   意味着 HALF_OPEN **没有超时自动退出**——
   `permittedNumberOfCallsInHalfOpenState: 5` 个 permit 泄漏完之后，
   熔断器**永久停在 HALF_OPEN 并拒绝一切流量，只能重启进程恢复**。

**结论与改法**：对本项目这种负载，**慢调用熔断必须整体关闭**，只保留失败率熔断
（5xx / 连接异常），后者才真正对应"上游故障"。同时补 `doOnCancel` 释放 permit。

```yaml
resilience4j:
  circuitbreaker:
    instances:
      modelUpstream:
        slidingWindowType: COUNT_BASED
        slidingWindowSize: 20
        failureRateThreshold: 50
        # 【已删除 slowCallRateThreshold / slowCallDurationThreshold】
        #   本网关的上游是 LLM，"正常就要跑几十秒到 20 分钟"，慢 ≠ 故障。
        #   保留这两项 = 把正常业务形态判成故障：最近 20 次里 18 次超过阈值就 OPEN，
        #   而那 18 次全都是成功返回的正常请求。
        #   slowCallRateThreshold 不写时默认 100（永不因慢调用熔断），正是我们要的。
        waitDurationInOpenState: 60s
        permittedNumberOfCallsInHalfOpenState: 5
        automaticTransitionFromOpenToHalfOpenEnabled: true
```

服务侧（`serviceUpstream` config）同理，见 §4.8。

### 11.3 优雅停机会硬切在途长请求

`server.shutdown: graceful` + `spring.lifecycle.timeout-per-shutdown-phase: 30s`：
30 秒到期后 Spring **只打一行 WARN 就继续往下走**，随后 `NettyWebServer.stop()`
关闭所有连接。一条已跑 10 分钟、还要再跑 10 分钟的 SSE 会被直接断开，
且因为响应头 10 分钟前就发出去了，**客户端看不到任何错误码**，只表现为"回答被截断"。

这不是本方案引入的问题，但服务接入后长请求会更多。三种处置：

- **A**：`timeout-per-shutdown-phase` 提到 1260s（21 分钟）。
  ⚠️ **必须同时**把容器平台的 `terminationGracePeriodSeconds` 提到 ≥1290s，否则 Spring
  还没等完就被 SIGKILL，改了等于没改。这一项在平台侧，需用户手工确认。
- **B**（推荐）：`timeout-per-shutdown-phase` 提到 600s，同时把
  `modelgate.detection.available-always-200` 改为 `false`（前提：已确认行内平台对
  "流量检查失败"只摘流量、不重启容器——这正是 application.yml 里自己写的待办），
  让平台在 draining 期间自动停发新流量，缩小要排空的量。
- **C**：维持 30s，在部署文档里写明"发版会切断超过 30 秒排空窗口的在途长请求"。

### 11.4 Retry 过滤器：建议直接删掉

`model-route` 上的 Retry 配置只写了 `statuses` 和 `methods`，
但 `RetryConfig` 构造器的字节码显示还有两个**未被覆盖的默认值**：

- `series = [HttpStatus.Series.SERVER_ERROR]` ⇒ **任意 5xx** 都重试，不只 502/503
- `exceptions = [java.io.IOException, org.springframework.cloud.gateway.support.TimeoutException]`
  ⇒ **570s 超时（§11.1 第 2 条）也会触发重试**

也就是说 application.yml 里那句注释「LLM 场景不对超时重试（避免重复计费/重复推理）」
**与实际行为相反**：一个非流式长请求会在 570 秒超时后，退避 1 秒，
**让上游从头再跑一遍 20 分钟推理**。

而且重试一旦真发生**还会失败**：`ModelRouteFilter` 里
`DataBuffer newBuffer = ...wrap(info.body());` 定义在匿名 decorator **之外**，
`getBody()` 每次都返回同一个 `Flux.just(newBuffer)`。第一次转发后 Netty 已经
release 了这个 ByteBuf、读指针也到底了，第二次 send 拿到的是废 buffer。
（对照：同仓库 `BodyParseFilter` 是每次新 `wrap`，Spring 自己的
`ServerWebExchangeUtils` 是每次 `retainedSlice()`。）

**建议**：直接删掉 `model-route` 上的整个 `- name: Retry` 块。
LLM 长请求场景重试的收益接近零，而代价是重复计费 + 一个会把可诊断的 504
变成莫名其妙 500 的 bug。若坚持保留，必须同时显式置空 `series` 与 `exceptions`，
并修掉 buffer 复用。

### 11.5 核实的完整性说明

本节结论由并行子代理产出，但**对抗性复核阶段因额度中断未能执行**。
因此上述每一条"承重"结论均由主代理**重新独立核实**过字节码位置：
`NettyWriteResponseFilter.WRITE_RESPONSE_FILTER_ORDER`、
`HttpClientFactory` 对 `responseTimeout` 的零引用、
`CircuitBreakerMetrics` 的 `Math.min` 裁剪、
`HalfOpenState.releasePermission` 与 `DEFAULT_WAIT_DURATION_IN_HALF_OPEN_STATE`、
`SimpleDequePool.evictInBackground` 的 `IDLE_RESOURCES` 迭代、
`RetryConfig` 的默认 `series`/`exceptions`。

**未经独立复核、可信度较低的次级结论**（实现前需自行验证）：
Retry 引起的 `cachedRequestBody` 内存放大量级、报文留档 64MB 阈值的扩容行为、
`UpstreamResponseParser` 的兜底 String 复制开销。
