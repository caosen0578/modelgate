## 0. 命名规范（与代码强一致）

| 类别 | 后缀 | 包 | 示例 | 说明 |
|---|---|---|---|---|
| 数据库实体 | `Entity` | `domain.entity` | `ModelInstanceEntity` | MyBatis-Plus 实体，`@TableName` 映射表 |
| 前端传值入参 | `RequestBO` | `domain.bo` | `CreateModelRequestBO` | 前端→后端请求体（行内 BO 规范，结尾加 BO） |
| 出参视图 | `VO` | `domain.vo` | `ModelVO` | 后端→前端响应对象 |
| 接口路径常量 | — | `common.UrlConstant` | `UrlConstant.MG_MODELS` | 所有 URL 统一收口，各 Controller 引用，禁止散落字面量 |

**基础字段（内部规范，所有可管理实体强制包含）**：`creater` / `create_time` / `updater` / `update_time` / `is_del`(逻辑删除 `@TableLogic` '0'/'1') / `creater_um` / `updater_um`。由 `AuditFieldMetaObjectHandler` 自动填充，`creater/updater/um` 取自 `OperatorProvider`（当前占位 null，待接入行内用户上下文）。**两处例外**：审计表 `mg_audit_log` 为高频追加表，不含这些基础字段；`mg_gateway_config` 含其余基础字段但**不含 `is_del`**（物理删除，理由见 §1 说明）。

>
> | 表 | 唯一键 |
> |---|---|
> | `mg_model` | `uk_model_id (model_id, is_del)` |
> | `mg_model_credential` | `uk_model_id (model_id, is_del)` |
> | `mg_app` | `uk_app_id (app_id, is_del)` |
> | `mg_app_model_auth` | `uk_app_model (app_id, model_id, is_del)` |
>
> `mg_model_credential` 必须一起纳入——`ModelService.delete()` 会逻辑删除凭证行，只改 `mg_model` 的话同名重建时模型能插入、凭证仍冲突。见增量脚本 `sql/upgrade_20260809_unique_key_include_is_del.sql`。
>
> **已知遗留语义**：`is_del` 仅 '0'/'1' 两值，故同一业务键最多只能存在一条软删行；同名"删除→重建→再删除"的第二轮删除仍会撞唯一键。实际影响很小，彻底解决需把 `is_del` 换成删除时间戳，另行评估。**`mg_gateway_config` 已改为物理删除**（无 `is_del` 列、实体无 `isDel` 字段）：`config_key` 即主键，软删后同 key 无法重建；配置非业务数据无留痕需求。见增量脚本 `sql/upgrade_20260809_gateway_config_physical_delete.sql`。

### 1.1 分页契约（强制）

带检索的列表接口统一走行内分页，**禁止**自建分页返回结构。

| 环节 | 约定 |
|---|---|
| 入参 | `XxxQueryBO extends com.pab.ficc.ibp.domain.base.bo.BaseBo`，**分页条件由前端经继承来的 `pageIndex` / `pageSize` 传入**；Controller 加 `@ParameterObject` |
| 分页对象 | 直接 `new Page<>(q.getPageIndex(), q.getPageSize())`，取 `BaseBo` 默认值（1 / 20）；**本项目不引入额外的收敛工具类** |
| 查询 | `mapper.selectPage(page, wrapper)`，**必须带稳定排序** |
| 出参 | `com.pab.ficc.ibp.domain.base.vo.PageVo`，Controller 返回 `Mono<Result<PageVo<XxxVO>>>` |

`PageVo` 结构：`{items, total, pageIndex, pageSize, pages}`。
`pageSize` 以**返回值**为准（服务端可能已收敛入参）。

**稳定排序规则**：
- 一般表按 `id DESC`
- **`mg_audit_log` 必须 `create_time DESC, id DESC`** —— 高频追加表同一毫秒可能写入多条，
  只按 `create_time` 排序会在翻页时重复/漏行

已改造的接口：`GET /modelgate/models`、`GET /modelgate/apps`、`GET /modelgate/audit`、`GET /modelgate/payload`。

- **`mg_request_payload` 同理必须 `create_time DESC, id DESC`**，且列表查询**禁止 `SELECT *`**——
  三个 `LONGTEXT` 正文列一页就是几十 MB，只能取 `CHAR_LENGTH` / `LEFT(...)`，全文走单条详情接口。

> **禁止**在前端对已分页的列表做本地 filter 搜索：前端只持有当前页，本地过滤等于「只能搜到当前页」，
> 搜索会静默失效。关键字必须作为查询条件下推到服务端，且**搜索时重置 `pageIndex=1`**。

## 2. 管理接口定义（强制，路径和字段名不得更改）

> 所有接口路径统一定义于 `common.UrlConstant`，Controller 通过常量引用（如 `@RequestMapping(UrlConstant.MG_MODELS)`、`@GetMapping(UrlConstant.DETAIL)`）。URL 字符串值与下文一致，未变化。

### 2.1 通用响应结构

管理接口（Controller）统一返回行内标准 `Result`（`com.pab.ficc.ibp.web.result.Result`）：

```json
{
  "resultCode": "00000000",
  "resultMessage": "操作成功",
  "data": {},
  "requestId": "abc123def456",
  "requestTime": "2026-04-23 10:00:00.000",
  "logTraceId": "abc123def456"
}
```

- `resultCode="00000000"` 表示成功，其余为业务错误码
- HTTP 状态码与 `resultCode` 分开：HTTP 4xx/5xx 代表协议层错误，`resultCode!="00000000"` 代表业务拒绝
- `requestId`/`logTraceId` 取自 `TraceContext`（WebFlux 下跨 reactor 线程可能为空，属已知限制）
- **注意**：网关对外业务流量（`/v1/**`）由 Filter 直接返回错误，仍使用旧结构（`code`/`message`），与管理接口独立，互不影响

### 2.2 模型管理接口

> **路径设计原则**：所有管理接口路径固定，变量通过 `@RequestParam` 或请求体传递，便于 RBAC 权限表按固定路径绑定角色。请求体对应 `domain.bo` 下的 `*RequestBO` 类。

**GET /modelgate/models** - 获取模型列表

Response `data`（`ModelVO`）:
```json
[{
  "id": 1,
  "modelId": "gpt-4o-platform-b",
  "upstreamModelId": "gpt-4o",
  "modelName": "GPT-4o（平台 B）",
  "provider": "openai",
  "modelType": "chat",
  "apiSpec": "openai",
  "upstreamUrl": "https://api.openai.com",
  "upstreamPath": "/v1/chat/completions",
  "timeoutMs": 30000,
  "enabled": true,
  "createTime": "2026-04-23 10:00:00.000"
}]
```

**GET /modelgate/models/detail?modelId={modelId}** - 获取模型详情

**POST /modelgate/models** - 创建模型（`CreateModelRequestBO`）

Request body:
```json
{
  "modelId": "gpt-4o-platform-b",
  "upstreamModelId": "gpt-4o",
  "modelName": "GPT-4o（平台 B）",
  "provider": "openai",
  "modelType": "chat",
  "apiSpec": "openai",
  "upstreamUrl": "https://api.openai.com",
  "upstreamPath": "/v1/chat/completions",
  "timeoutMs": 30000,
  "defaultParams": "{}",
  "forceParams": "{}",
  "paramMapping": "{}",
  "description": "OpenAI GPT-4o",
  "credential": {
    "authType": "api_key",
    "secretKey": "sk-xxx"
  }
}
```

> `modelId` 是调用方填写在请求体 `model` 中的**网关对外 ID**；`upstreamModelId` 是供应商原始模型 ID。
> 后者留空时直接使用 `modelId`，非空时网关在转发前改写，请求鉴权/授权/配额/审计仍按 `modelId`。
> 响应体由上游原样返回，不把模型 ID 换回对外值。
>
> 模型身份只允许由 `modelId/upstreamModelId` 表达；创建、更新和草稿测试若在有效 JSON
> `forceParams` 顶层发现 `model`，管理 API 返回 400 并提示改用 `upstreamModelId`。
> `defaultParams/forceParams/paramMapping` 非空时都必须是 JSON 对象，且 `paramMapping` 的目标值必须为
> 非空字符串；管理写入口与草稿测试均显式返回 400。运行期逐项忽略只兜底历史或直接改库的脏数据。
>
> `paramMapping`：自定义字段映射 JSON，对应 `mg_model.param_mapping`，仅 `apiSpec=custom` 时生效（见 §1 建表 SQL 与 01-需求规约「自定义参数映射 P1」）。非 custom 规范可省略。

#### `upstreamUrl` 与 `upstreamPath` 的职责划分（强制）

| 字段 | 内容 | 示例 |
|---|---|---|
| `upstreamUrl` | 协议 + 域名 + 端口，**不含接口路径** | `https://api.openai.com` |
| `upstreamPath` | 接口路径，可空 | `/v1/chat/completions` |

**路径解析规则**（`ProviderAdapter.resolvePath`，各适配器一致）：配了 `upstreamPath` 用它，留空则回落到该规范的默认值。

| apiSpec | `upstreamPath` 留空时的行为 |
|---|---|
| `openai` / `custom` | **透传调用方请求路径**（业务侧 SDK 发什么就转发什么） |
| `anthropic` | 固定 `/v1/messages` |
| `azure_openai` | **忽略本字段**——`upstreamUrl` 本身即完整部署 URL（含路径与 `api-version`），再拼路径会破坏它 |

- **留空即维持旧行为**，存量模型无需回填；增量脚本 `sql/upgrade_20260809_model_upstream_path.sql` 只加列不改数据
- **连通性测试与对话测试必须使用同一解析结果**（`ModelConnectivityService.probePath`），
  否则会出现「测试通过但业务 404」这种最误导人的情况
- 前端在 `apiSpec=azure_openai` 时须将该输入框置灰并说明原因，**禁止**让用户填一个不生效的值

**PUT /modelgate/models/update** - 更新模型（`UpdateModelRequestBO`，字段集与创建一致）

- 不改名：`modelId` 传当前对外 ID，`newModelId` 省略。
- 改名：`modelId` 仍传**原对外 ID**用于定位，`newModelId` 传新对外 ID。凭证和授权依靠
  `ON UPDATE CASCADE` 同事务级联；历史审计/报文不改写。
- 创建、更新、删除模型与凭证必须在同一数据库事务中完成；相关缓存只在提交成功后失效。
- 项目手工装配 Druid 并排除了数据源事务自动配置，因此由 `TdsqlMybatisPlusConfig` 显式提供
  `tdsqlTransactionManager`，上述事务必须指定该名称；只添加 `@Transactional` 而没有事务管理器不算完成。
- 改名还必须清理所有受影响 App 的授权缓存，否则新 ID 会在 TTL 内被误判为未授权。
- Redis QPS/日/月配额键均包含对外 `modelId`。QPS 旧键会在约 2 秒内自然过期；日/月计数不在线迁移，
  新 ID 从 0 重新累计。原因是改名时可能仍有在途请求及异步 Token 回写，在线复制无法同时避免漏计和重复计数。
  有严格配额要求时应在低流量窗口改名，优先采用“新建模型 + 逐步迁移调用方”。
- 主动缓存失效只清处理管理请求实例的 Caffeine；当前没有跨实例失效广播。其他副本依靠模型/凭证
  30 秒、授权 60 秒 TTL 收敛，生产变更窗口须按最长 60 秒考虑。

`credential` 为可选对象，**缺省表示本次不修改凭证**；传了则按下列规则落库（强制）：

| 情况 | 行为 |
|---|---|
| `authType=none` | 清空 `access_key` / `secret_key`——"不鉴权"不得在库中残留密钥 |
| `secretKey` 留空 | **沿用库中原密钥**。编辑页出于安全不回显密钥，用户不重填是常态，不得覆盖为空 |
| `secretKey` 有值 | 加密后覆盖 |

- 凭证列的清空必须用 `LambdaUpdateWrapper` 显式 `set`：MyBatis-Plus 默认 NOT_NULL 策略会跳过 null 字段，
  走实体更新会导致 `authType=none` 时清不掉密钥列。
- 更新后必须同时 evict 模型缓存与**凭证缓存**，改名时清新旧两个 key；缓存失效在事务提交后执行。
- 适配器构造上游鉴权头时必须判定 `authType`（见 `ProviderAdapter.shouldAuthenticate`）：
  `none` 时即使库中残留密钥也**禁止**发送鉴权头。

**GET /modelgate/models** 与 **/detail** 的 `data` 附带 `authType`、`accessKey`、`secretKeyConfigured`（布尔）
供编辑页回显；**`secretKey` 属机密，任何接口都不下发**。

**PATCH /modelgate/models/enable?modelId={modelId}** - 启用模型

**PATCH /modelgate/models/disable?modelId={modelId}** - 禁用模型

**DELETE /modelgate/models/delete?modelId={modelId}** - 删除模型（存在活跃授权时返回 400；逻辑删除）

**POST /modelgate/models/test?modelId={modelId}** - 连通性测试

向上游发送一次**真实**的最小推理请求（chat → `/v1/chat/completions` 且 `max_tokens=1`；embedding → `/v1/embeddings`）。
请求体 `model` 必须使用 `upstreamModelId`（空则回退 `modelId`）；参数合并顺序
`defaultParams → forceParams → upstreamModelId → paramMapping`、供应商适配、鉴权 Header 与 URL 拼接
均复用真实转发逻辑。

**判定规则（强制）**：**仅上游返回 2xx 时 `success=true`**。鉴权失败（401/403）、地址错误（404）、
参数被拒（400/422）、限流（429）、上游异常（5xx）、超时 / DNS 失败 / 连接拒绝，一律 `success=false`
并在 `message` 中给出原因与排查方向。**禁止**因"请求已发出"或"模型记录存在"就判定连通。

**两种入参形态**（二选一，body 优先）：

| 形态 | 用法 | 场景 |
|---|---|---|
| 查库模式 | 仅 `?modelId=`，无 body | 列表页测试已保存模型，SK 从库中解密后使用 |
| 草稿模式 | body 传 `TestConnectionRequestBO` | 新增模型时记录尚未入库，用表单配置直接探测 |

Request body（草稿模式，可选；`secretKey` 为明文，**不落库、不写服务端日志，浏览器控制台也必须脱敏**）:
```json
{
  "modelId": "gpt-4o-platform-b",
  "upstreamModelId": "gpt-4o",
  "modelType": "chat",
  "apiSpec": "openai",
  "upstreamUrl": "https://api.openai.com",
  "upstreamPath": "/v1/chat/completions",
  "timeoutMs": 30000,
  "defaultParams": "{}",
  "forceParams": "{}",
  "paramMapping": "{}",
  "credential": { "authType": "api_key", "secretKey": "sk-xxx" }
}
```

编辑页始终提交当前草稿。若 query `modelId` 指向已保存模型且草稿未重填 `secretKey`，服务端只复用
库中解密后的旧密钥（`authType=none` 时不复用）；上游地址、上游真实模型 ID、默认/强制参数和字段映射
仍以草稿为准。禁止为了复用密钥而退回整条数据库旧配置，否则“测试连通”会测试错误对象。

Response `data`（`ConnectivityTestVO`）:
```json
{
  "success": true,
  "latencyMs": 342,
  "message": "连通成功",
  "httpStatus": 200,
  "upstreamUri": "https://api.openai.com/v1/chat/completions",
  "upstreamBody": "{\"id\":\"chatcmpl-...\"}"
}
```

- `httpStatus`：未建立连接（超时 / DNS / 连接拒绝）时为 `null`
- `upstreamBody`：上游响应体片段，默认最多 1 MiB 字符，可通过 `modelgate.connectivity-test.max-body-chars` 调整
- 上述正文只返回当前管理请求，不写入服务日志；失败日志仅记录响应字符数，避免大响应或敏感模型输出落盘
- 探测超时取 `min(model.timeoutMs, 15000)`，缺省 10000——模型本身可能配了很长超时（如 570s），但测试必须尽快给结论
- **连通性测试结果不作为保存前置条件**：测不通仍允许创建/更新模型（见 [05 §边界](./05-边界限制与禁止规则.md)）

```json
  "appId": "crm-service",
```

**POST /modelgate/models/chat/test?modelId={modelId}** - 管理面对话测试

用调用方给定的 OpenAI 规范请求体（`messages` / `temperature` / `max_tokens` 等）直连上游，
适配器逻辑、超时策略、失败归类与连通性测试完全一致，响应结构同为 `ConnectivityTestVO`。

- **上游密钥不出服务端**：凭证在服务端解密并由适配器注入请求头，**禁止**任何接口把 `secretKey` 下发浏览器。
- query 参数 `modelId` 用于定位网关模型；`body.model` 由服务端强制覆盖为该记录解析出的
  `upstreamModelId`（空则 `modelId`），浏览器传入的 model 不具有决定权。
- 发送前同样应用 `defaultParams / forceParams / paramMapping`；因此模型测试与真实转发不会因配置字段遗漏而表现不一致。
- **不支持流式**：返回聚合后的完整响应，不做 SSE 透传。
- **本通道跳过**凭证鉴权 / 访问控制 / 模型授权 / 配额限流，验证的是"模型配置本身能否调通"，
  **不等价于**业务系统调 `POST /v1/chat/completions` 的完整链路。

> 管理页测试弹窗原有的「调用凭证（Bearer）」输入框已移除：那里要的是**接入系统凭证**
> （`mg_app_credential`，业务流量那一跳），与模型的**上游凭证**（`mg_model_credential`）是
> 链路上前后两跳的不同凭据，混用会被 `CredentialAuthFilter` 直接 401。

### 2.10 报文记录查询接口

报文表 `mg_request_payload` 与 `mg_audit_log` 通过 `trace_id` 关联，分工：审计回答
"成不成功、多久、多少 token"，报文回答"到底发了什么、上游回了什么"。
报文**仅对开启了 `mg_app_model_auth.payload_log_enabled` 的「接入系统 × 模型」授权产生**，
且按 `modelgate.payload-log.retention-days`（默认 **7 天**）物理清理，超期不可找回。

**GET /modelgate/payload** - 分页列表（**不返回正文全文**）

参数（全部可选）：`appId` / `modelId` / `traceId`（**前缀匹配**）/ `isStream`(true|false) /
`upstreamStatus` / `finishReason` / `truncated`(**只接受 none|response**) /
`startTime` / `endTime`（ISO 本地时间，如 `2026-08-18T10:30`）/ `keyword` /
`pageIndex` / `pageSize`（**上限 200**）。排序固定 `create_time DESC, id DESC`。

> **`traceId` 是前缀匹配（`likeRight`）不是全等**：列表展示的 traceId 是截断值（前 12 字符），
> 全等的话用户复制界面上看到的内容去筛选**永远查不到**（实测：完整 16 位 → 1 条，
> 界面显示的 12 位 → 0 条）。前缀匹配在 `idx_trace_id` 上是范围扫描，索引仍然生效。

> **`truncated` 只接受 `none` / `response`**，传其它值返回 `INVALID_PARAMETER`。
> DDL 注释历史上写的是四态 `none|request|response|both`，但 `PayloadService.toEntity` 实际只写
> `truncated ? "response" : "none"`——请求侧根本没有截断机制（`BodyParseFilter` 用
> `DataBufferUtils.join` 一次性读全请求体，无字节上限；`max-capture-bytes` 只作用于响应采集）。
> 允许查 `request`/`both` 会返回 200 + 空列表，让人得出"这段时间没有请求被截断"的**错误结论**，
> 所以显式拒绝，让不合法取值响亮地失败。`finishReason` **不做**白名单——取值由上游模型决定，
> 写死会把新模型的合法取值拒掉。

> ⚠️ **`keyword` 有前置约束**：正文检索是 LONGTEXT 上的 `LIKE '%x%'`，走不了索引，
> 单独使用即全表扫描。后端要求它必须与下列**之一**同时使用，否则返回 `INVALID_PARAMETER`：
> `traceId`（**≥8 位前缀**）或**两端齐全且跨度 ≤24 小时**的时间范围。
>
> - traceId 要求 ≥8 位：前缀匹配下 1 位十六进制只滤掉 15/16，当收窄条件等于没有。
> - 时间范围要求有界：早先只判 `!= null`，`startTime=1990-01-01` 这种一眼假的下界照样放行
>   （实测直接 200），防护形同虚设。只给单端同理——在保留期仅 7 天的表上几乎等于全表。
> - **`appId` / `modelId` 不算**收窄条件（这一版收紧了）：它们能走索引**定位**，
>   但不给候选集任何**上界**。内网通常只接个位数的系统，主力 appId 常占全表七成到十成，
>   `keyword + 主力系统` 实际仍是近乎全表的 LONGTEXT 扫描。它们仍是有用的过滤条件，
>   只是不能单独充当 keyword 的准入券。
> - `isStream` / `upstreamStatus` / `finishReason` / `truncated` 同样不算：
>   无索引且区分度极低（`upstream_status=200` 能占九成以上）。
>
> 关键字里的 `%` `_` `!` 会被**转义**后再拼进 LIKE，并显式带 `ESCAPE '!'` 子句。
> MyBatis-Plus 的 `like()` 只把值包成 `%值%`、不转义通配符——实测 `keyword=%` 曾返回全表。
> **转义符刻意不用反斜杠**：`sql_mode` 含 `NO_BACKSLASH_ESCAPES` 时不存在默认转义符，
> 反斜杠方案会静默失效（正常关键字如 `100%` 查不到任何行，单个 `%` 又变回大范围匹配），
> 而 JDBC URL 没有用 `sessionVariables` 固定 `sql_mode`。

> **`pageIndex` 有 OFFSET 上限**：`(pageIndex-1) × pageSize ≤ 50000`，超出返回 `INVALID_PARAMETER`
> 并提示改用时间范围定位。深翻页与 keyword 无关，是另一条同样能全表扫的路径，
> 而分页条的「末页」按钮精确命中最大合法 OFFSET——被跳过的每一行都要物化完整 LONGTEXT。

> **超时与线程隔离**：两个查询方法带 `@Options(timeout = 30)`（JDBC statement 级，
> 真正在服务端取消语句），Controller 再加 35s 兜底。查询跑在**专用线程池** `mg-admin-payload`
> （4 线程 / 队列 64）而非全局 `Schedulers.boundedElastic()`——后者是 Reactor 全局单例，
> 网关热路径的五个 Filter 都在用它，且队列深 100000、无超时，被管理面慢查询占满时
> 网关鉴权任务只会安静排队，表现为 `/v1/**` 延迟抬升而日志干净。

> 匹配范围为 `request_body` 与 `response_text`，**不含 `response_raw`**（SSE 分帧原文里
> 同一句话被切碎在多帧，LIKE 匹配不到完整词，搜它只会给出误导性的空结果）。

> **`pageSize` 上限 200**：`BaseBo.setPageSize` 是裸 setter，框架层**不做任何收敛**
> （实测 `pageSize=5000` 被原样接受），必须在 Controller 里封顶。报文行带正文预览与三个跨表
> 子查询，单页过大会长时间占住一条 Druid 连接（池上限 100）。
> ⚠️ 同样的裸 setter 问题对 `/modelgate/audit`、`/models`、`/apps` 一样存在，尚未处理。

```json
  "modelId": "gpt-4o",
  "isStream": true,

```
`requestLen` / `responseRawLen` / `responseTextLen` 为 `CHAR_LENGTH`（字符数，非字节数），
`requestPreview` / `responsePreview` 为对应列前 160 字——都在 SQL 侧算完，**LONGTEXT 内容不出 MySQL**。

`inputTokens` / `outputTokens` / `tokenSource` **取自 `mg_audit_log`，不是报文表的列**（报文表按设计
不冗余存 Token，唯一真相在审计表）。实现用**标量子查询**而非 LEFT JOIN，两个理由缺一不可：

1. **正确性**——两表 `trace_id` 上都只有普通索引、无唯一约束，JOIN 时审计侧一旦出现同
   `trace_id` 多行，报文行会被放大成多行，分页 `total` 与列表内容一起错乱；子查询带 `LIMIT 1`，
   结构上保证一条报文只出一行。
2. **兼容 Wrapper**——`${ew.customSqlSegment}` 生成的是不带表前缀的列名（`app_id = ?`、
   `ORDER BY create_time`），JOIN 进第二张表后这些列全部 ambiguous，SQL 直接报错。

子查询走 `mg_audit_log.idx_trace_id`，每行四次索引点查（三个取值 + 一个计数）。

> ⚠️ **`trace_id` 不是唯一键，且调用方可以复用它**：`TraceWebFilter.resolveTraceId` 优先沿用
> 入站的 `X-Trace-Id`（设计意图是跨系统串联）。一次上游事务扇出成多次模型调用时，
> 两表各写 N 行，子查询只能取到其中一行 → N 行报文显示同一份 Token。
> 因此三个取值子查询统一带 `ORDER BY a.id`（保证**确定且可复现**地取 id 最小那行），
> 并额外返回 `auditMatchCount`；**`auditMatchCount > 1` 时 Token 不可信**，
> 前端显示为「⚠ Token 存疑」而非具体数字。根治需要给报文行冗余 audit 行 id（改采集侧 + DDL）。

> Token 为 `null`（关联审计记录查不到）与为 `0`（确实没消耗）**含义完全不同**，前端分别按 `-` 和 `0`
> 展示，禁止合并——一律按 0 展示会把数据异常伪装成"这次没烧 token"，这正是 token 恒为 0 的旧 bug
> 长期没被发现的原因。`tokenSource=estimated` 是本地按字符估算的，页面必须标出，不可当账算。

**GET /modelgate/payload/detail?id={id}** - 单条全文

Response `data`（`PayloadDetailVO`）在上表字段基础上，用 `requestBody` / `responseRaw` /
`responseText` 三个全文字段替代长度与预览字段，Token 三项同样保留。记录不存在时返回
`INVALID_PARAMETER` 并提示"可能已过保留期被清理"。

> 详情**不用 `BaseMapper.selectById`**：那只能拿到 `mg_request_payload` 自己的列，Token 在
> `mg_audit_log` 里会整体丢失。改用 `selectDetailById`，与列表同一套标量子查询。

**GET /modelgate/payload/meta** - 配置回显

```json
{"enabled": true, "retentionDays": 7, "cleanupCron": "0 30 2 * * ?", "maxCaptureBytes": 67108864}
```
供管理页展示"报文能查多久"。前端**不得写死**这些数值——它们是 `application.yml` 配置项，
写死必然与实际部署漂移。

### 2.11 容器平台探测端点

路径由**行内容器平台约定，不可更改**。平台在三个场景分别调用，拿不到 200 就认为应用没起来
并反复重启容器。三者都**不需要任何凭证**（挂在 `/actuator/` 前缀下，业务过滤器全部跳过），
且 **GET / POST 都接受**（平台用哪个方法未约定，405 同样会触发重启）。

| 场景 | 路径 | 200 的条件 | 非 200 时 |
|---|---|---|---|
| 存活检查 | `GET|POST /actuator/detection/running` | **进程活着就永远 200** | — |
| 流量检查 | `GET|POST /actuator/detection/available` | 启动完成 且 未在优雅退出中 | 503 `starting` / `draining` |
| 优雅退出 | `GET|POST /actuator/detection/shutdown` | 总是 200（幂等） | — |

响应体是纯文本（`running` / `available` / `draining`），**不是** `Result` 结构——
平台只看状态码，包一层反而增加解析失败的可能。

> ⚠️ **存活检查禁止加入任何依赖健康检查**（DB/Redis/上游）。存活失败的语义是"重启这个进程"，
> 把依赖写进去会让数据库抖动的一瞬间所有实例同时被重启，把局部故障放大成全面中断，
> 且重启后依赖仍没好 → 无限重启。依赖健康属于流量检查该考虑的范畴，
> 而本网关即使 MySQL 不可用，凭证/授权走 Caffeine 缓存仍能转发相当一部分流量。

> **优雅退出会顺带刷盘**：置 draining 后，同步把 `AuditService` / `PayloadService` 的内存队列
> 尽力写入数据库（15 秒时限），避免发版时丢失未落库的审计与报文。
> `@PreDestroy` 里另有一份兜底，应对平台不调该端点、直接 SIGTERM 的情况。

### 5.3 关键业务级联规则

1. **App 禁用** → 该 App 下所有凭证立即失效（缓存强制刷新）
2. **凭证禁用** → 仅该凭证失效，同系统其他凭证不受影响
3. **模型授权禁用** → 该 App 访问该模型返回 403，其他模型不受影响
4. **模型禁用** → 所有 App 访问该模型返回 503
5. **授权过期** → 过期后等同于禁用，返回 403，记录不自动删除
6. **App 删除** → 级联删除该 App 下所有凭证、授权、访问规则
