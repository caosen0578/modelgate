# Spec Me2AI · 09 · 准发压测方案

> **文档性质**：准发（准生产）性能验证指南。用 JMeter 在内网压测，确认 ModelGate 在目标并发下的容量、稳定性与降级行为。

---

## 0. 核心方法论：用「可控延迟的 mock 上游」

LLM 上游本身要 30–180s。**直接压真实模型 = 测模型，不是测网关。** 要测 ModelGate 自身容量，必须用 mock 上游：

| mock 类型 | 行为 | 测什么 |
|---|---|---|
| 零延迟 mock | 立即返回固定 JSON | **网关每请求净开销**（过滤器链 + 鉴权 + Redis + body 缓冲的纯 CPU）——唯一可横向对比配置/版本的数字 |
| 固定延迟 mock | 恒定 N 秒后返回；`stream=true` 时按 token 间隔吐 SSE | **并发长连接承载**（连接池、Netty 直接内存、FD） |

mock 可用简单 Nginx/Go stub。**关键指标 = 网关净增延迟 = 总延迟 − mock 延迟。**

> ⚠️ **JMeter 自身的坑**：每线程占住连接整个 30–180s，模拟 500 并发 = 500 个 OS 线程常驻。单机 JMeter 撑不住 → 必须**分布式（多 slave）+ 非 GUI 模式（`jmeter -n -t`）+ 加大 JMeter 堆（`HEAP`）**。否则瓶颈在压测机不在网关。

---

## 1. 压测场景阶梯（建议顺序）

| # | 场景 | 目的 | 关键观测 |
|---|---|---|---|
| 1 | 基线 1 并发（零延迟 mock） | 网关单请求延迟地板 | 网关净增延迟 |
| 2 | 阶梯加压 50→150→300→500→800 并发 | 找拐点/饱和点 | 连接池 pending、P95、错误率 |
| 3 | 冷缓存 vs 热缓存 | L1 miss 打 DB 的代价 | boundedElastic 队列、Druid 连接 |
| 4 | 流式 SSE 专项 | 长连接 + 直接内存 | Netty direct memory、FD |
| 5 | 大 body（接近 10MB）+ 高并发 | BodyParseFilter 缓冲压力 | 堆/直接内存曲线 |
| 6 | 稳定性 soak（目标并发跑 2–4h） | 内存/FD 泄漏、GC 趋势 | 堆是否回落、审计队列水位 |
| 7 | 尖峰 spike（瞬时突发） | 限流 + 突发容量 | 429 计数、burst 行为 |
| 8 | 故障注入：杀上游 / 杀 Redis | 熔断 + 降级（fail-open） | 熔断状态、429 是否放行 |

## 2. JVM 推荐参数（Java 17，起步值，按观测调）

```bash
# ---- 堆 ----
-Xms4g -Xmx4g                      # 起止相等避免动态扩容抖动；按 soak 内存曲线调
-XX:MaxMetaspaceSize=256m

# ---- 直接内存（关键！Netty SSE/body 缓冲走堆外）----
-XX:MaxDirectMemorySize=2g         # 必须显式设，别用默认(=Xmx，易与堆争内存)

# ---- GC：流式低停顿优先 ----
-XX:+UseG1GC -XX:MaxGCPauseMillis=200
# 若堆>8g 且延迟敏感，可换 ZGC：-XX:+UseZGC（JDK17 亚毫秒停顿）

# ---- 故障快速失败（K8s 自愈）----
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump
-XX:+ExitOnOutOfMemoryError

# ---- K8s CPU limit 下让 JVM 正确识别核数（影响 Netty/boundedElastic 线程数）----
-XX:ActiveProcessorCount=<容器CPU核数>
```

- 系统层：`ulimit -n 65535`（FD），否则高并发连接 `Too many open files`。
- Reactor Netty IO 线程默认 = CPU×2，通常不动；需要时 `-Dreactor.netty.ioWorkerCount=N`。

## 3. 网关/连接池推荐参数（对齐 `application.yml`）

| 参数 | 现值 | 建议 | 说明 |
|---|---|---|---|
| `httpclient.pool.max-connections` | 500 | =峰值并发上游调用数×1.5，压测拐点后定 | **上游并发硬天花板**，pending 长期 >0 即卡这里 |
| `pool.acquire-timeout` | 30000 | 保持，压测看是否触发 | 池满等待超时 |
| `pool.type` | FIXED | 保持 | 固定池 |
| `response-timeout` | 570s | 保持 < SLB 600s | 长响应 |
| `connect-timeout` | 5000 | 保持 | |
| `RequestSize.maxSize` | 10MB | 结合 body 压测确认 | 每请求缓冲内存来源 |
| `audit.buffer-size` | 200000 | soak 看水位调 | 满则丢审计（见 metric） |
| `rate-limit default-rate/burst` | 5 / 10 | 压测限流场景验证 | Redis Lua 滑窗 |
| 熔断 `slowCallDuration` | 180s | 保持 | 别误熔断正常长响应 |

- 补充：显式设 `pool.pending-acquire-max-count`（默认 2×maxConnections）界定等待队列，避免请求无限堆积。

## 4. 压测指标清单（5 层）

### A. 客户端 / JMeter 侧（SLA 面）
- 吞吐：req/s、成功 TPS（LLM 场景数值低，别只看这个）
- 响应时间：avg / **P90 / P95 / P99** / max
- **TTFB（首字节）** + 流式的**首 token 时间、token 间隔、整流时长**
- **错误率 %** 及错误分类：超时 / 429 / 503 / 连接拒绝 / 连接重置
- 活跃并发线程数（与错误率对照找拐点）

### B. 网关 JVM 侧（核心健康）
- CPU 利用率（容器 limit 内）
- 堆：young/old 占用、**GC 频率**、**GC 停顿(STW) ms**、GC 吞吐%；soak 看 **old gen 是否持续上涨（泄漏）**
- **直接内存(Netty)**：使用量 vs MaxDirectMemorySize（SSE/大 body 必看）
- 线程：Netty event-loop、**boundedElastic 池大小 + 排队**（鉴权 L1 miss 打 DB 走这里）、总线程数
- **Reactor Netty 连接池**：acquired / **pending** / idle（pending>0 = 饱和）
- **FD/socket 数**（soak 看泄漏）
- 来源：`/actuator/prometheus`（Micrometer 指标已暴露）

### C. 过滤器 / 业务侧
- **审计队列水位**：`modelgate.audit.queue.size` / `.capacity`；丢弃计数 `modelgate.audit.dropped.total`
- **429 限流拒绝计数**（QuotaFilter）
- **熔断器状态/切换**（CLOSED→OPEN→HALF_OPEN，按 model_id；`resilience4j_circuitbreaker_state`）
- **Caffeine L1 命中率**（凭证/模型/授权缓存）
- Redis 调用延迟/失败（降级 fail-open 是否触发）

### D. 中间件侧
- **Redis**：ops/s、延迟、连接数、CPU、slow log、**Lua EVAL 延迟**
- **MySQL/TDSQL**：慢查询、CPU/IO、**审计 batchInsert 延迟**
- **Druid 连接池**：active / pool-size / **wait-count / wait-time**（池不够会阻塞 boundedElastic）

### E. 上游侧（mock）
- mock 收到的并发连接数（验证 = 网关放行数）
- 上游返回延迟/错误率（驱动熔断）

## 5. 判定红线（压测前先定）

| 指标 | 建议红线 |
|---|---|
| **网关净增延迟**（总延迟 − mock 延迟） | 稳态 < 30–50ms |
| 错误率（除有意 429） | < 0.1% |
| GC 停顿 | G1 < 200ms；流式敏感更严 |
| 内存 | 无 OOM；**soak 后堆能回落**（无泄漏）；直接内存不逼近上限 |
| FD | soak 全程平稳，无持续增长 |
| 审计队列 | `queue.size` 全程不持续逼近 `capacity`；`dropped.total` 不增长 |
| 连接池 pending | 目标并发下 ≈ 0 |
| 熔断恢复 | 杀上游后能开断，恢复后 60s 内自动 HALF_OPEN→CLOSED |

---

## 6. 与代码相关的关键提醒

- `/v1` 流量**不走 Controller**（Gateway 直接路由）。每请求成本 = **8 个过滤器 + 鉴权(L1 命中很便宜) + Redis Lua + body 缓冲**。**热缓存路径很轻，冷缓存打 DB 才是重点** → 务必分别测冷/热（场景 3）。
- 审计是异步批量（2s / 5000 条），**不在热路径**；DB 写入跟不上会丢日志 → soak 必看 `modelgate.audit.queue.size` 与 `dropped.total`。
- `BodyParseFilter` 缓存整个请求体字节（≤10MB）；高并发大 body 是堆/直接内存主要压力源（场景 5）。
- 限流走 Redis Lua 滑窗，Redis 故障时 QuotaFilter **fail-open**（放行）；故障注入（场景 8）要验证这一点符合预期。
