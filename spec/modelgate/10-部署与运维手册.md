## 1. 环境资源清单（申请用）

> 不再经 Apollo 下发配置——申请到 MySQL/Redis 实例后，直接把连接信息写进 `application.yml` 即可。

Venus 数据源中间件、内网 Redis 集群 SDK。

**网络**：网关需可访问全部上游模型地址（`mg_model.upstream_url`）；入口经 SLB（idle timeout 600s，网关 `response-timeout=570s` 先于其超时）。

### 1.1 内网合规部署：Apollo 叠加层（不在本仓库，单独记录）

> 上面"不需要 Apollo"针对的是 `D:\code\modelgate` 本仓库的标准直连方案。**内网侧因合规要求需要接入 Apollo**，
> 这是在内网合并出的独立代码上叠加的一层，`bootstrap.yaml` / `ApolloConfig` 均不在本仓库，本节仅记录已验证过的结论，
> 供内网部署对照，避免下一次合并重新踩坑（详见 [11 §21.2](./11-变更记录.md)）。

- 必须显式依赖 `spring-cloud-starter-bootstrap`——缺失时 `bootstrap.yaml` 整个不会被读取（不是"读不到某几项"，
  是这层配置源根本不进 Spring 环境），Apollo 与本地配置会同时失效，现象具有很强误导性。
- `apollo.bootstrap.namespaces` 订阅哪些命名空间需要谨慎：**未验证但需留意的风险**——若命名空间（尤其
  `ficc-ibp-dih.web-common-config` 这类跨服务公共命名空间）里定义了 `spring.cloud.gateway.*` 或 `modelgate.*`
  前缀的键（哪怕是残留/占位），Spring Boot 对 List 类型属性是"优先级最高的单一来源整体生效，不跨源合并"，
  会把本地网关路由/密钥配置整体顶掉而不是部分覆盖。

## 2. 配置项清单

> **本项目不使用环境变量，也不使用 Spring Profile。** `application.yml` 是唯一配置文件、
> 单一固定文档，所有参数都是字面量。部署到不同环境（dev/test/prod）时，
> **直接改这份文件里对应的值**即可，不依赖任何 `export`、不依赖 `SPRING_PROFILES_ACTIVE`、
> 不依赖 `-D`/`--` 启动参数覆盖。这是决策，不是权宜之计：之前用环境变量做覆盖时，
> 反复出现过"改了配置项但忘了同步 export，改动像没生效一样"的情况，直接改字面量能杜绝这一类问题。

| 配置项（`application.yml`） | 说明 |
|---|---|
| `modelgate.crypto.key` | 32 字节 base64；用于上游 SK/AKSK **及接入凭证**加密。**为空时创建凭证/AKSK 验签运行期报错**。生成方法见 **§2.1**；⚠️ **必须与数据库连接串分离保管**，见 **§2.2**。生产部署前必须把这一行换成生产专用密钥 |
| `spring.cloud.gateway.server.webflux.routes[model-route].uri` | Gateway 静态路由占位地址（`http://127.0.0.1:9090`）；真实转发目标由 `ModelRouteFilter` 按模型配置动态覆盖，这个值本身从不生效，不需要改 |
| ~~`ADMIN_TOKEN_OPS`~~ / ~~`ADMIN_USERNAME`~~ / ~~`ADMIN_PASSWORD`~~ | 已移除，随 `AdminAuthFilter` 一并删除，管理面鉴权由内网体系承担 |

### 2.1 `modelgate.crypto.key` 生成方法

**格式要求**：Base64 字符串，**解码后必须恰好 32 字节**（AES-256 密钥长度）。
表现为 **44 个字符**、末尾一个 `=`。长度不对启动即抛：

```
modelgate.crypto.key 解码后必须恰好为 32 字节，当前为 N 字节。生成命令：openssl rand -base64 32
```

四种生成方式任选其一（均在 Windows + Git Bash 环境实测通过）：

```bash
# ① openssl —— 首选；Git Bash 自带（/mingw64/bin/openssl），Linux/Mac 亦有
openssl rand -base64 32
```

```bash
# ② Node.js —— 装了 node 的机器最省事
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
```

```powershell
# ③ PowerShell —— 无 openssl 的 Windows 机器；兼容 Windows PowerShell 5.1
$b=New-Object byte[] 32; [Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b); [Convert]::ToBase64String($b)
```

```bash
# ④ 纯 JDK —— 内网机器可能只有 java，用 JDK 自带的 jshell（JDK 9+）
printf 'System.out.println(java.util.Base64.getEncoder().encodeToString(java.security.SecureRandom.getSeed(32)));\n/exit\n' | jshell -s -
```

**生成后校验**（应输出 `32`）：

```bash
echo -n '<把生成的密钥粘这里>' | base64 -d | wc -c
```

**注入方式**：直接改 `application.yml` 里 `modelgate.crypto.key` 这一行的字面值，不用环境变量：

```yaml
modelgate:
  crypto:
    key: 生成的44位base64
```

> **单一固定文档，没有 profile 覆盖层**：`application.yml` 只有这一处 `modelgate.crypto.key`，
> 改这一行就是唯一生效的地方，不会再有"改了没生效、因为实际生效的是另一份文件/文档块"这类情况。
> 仓库里默认值是本地联调测试密钥（`bW9kZWxnYXRlLWxvY2FsLWRldi1hZXMyNTYta2V5ISE=`，解出来是可读字符串
> `modelgate-local-dev-aes256-key!!`，等于没加密），**部署前必须替换成生产专用密钥**，
> 否则相当于用一把公开可见的密钥加密所有上游凭证与接入凭证。

> **🚫 禁止让程序自动生成。** 曾被问到能否在密钥为空时由 `CryptoService` 自己 `SecureRandom` 生成一把——
> **不行**：每次重启密钥都变，存量密文全部解不开；多副本部署时 A 实例加密的密文 B 实例也解不开，
> 请求打到哪个 Pod 全看运气。密钥必须跨重启跨实例恒定。

### 2.2 `modelgate.crypto.key` 保管要求（强制）

接入凭证已改为**可解密存储**（业务决策：投产后凭证轮转会中断关联系统业务，运维必须能找回，
见 [05 §4.1](./05-边界限制与禁止规则.md)）。这意味着：

> **数据库 + 该密钥同时泄露 = 全部接入凭证一并失守。**

缓解手段只有"分离保管"一条，因此：

- [ ] 该密钥**禁止**和数据库连接串写在同一份对外分发的配置文件副本里（`application.yml` 里两者物理相邻，
      分发/备份/权限管控时要能分开处理，不能因为在同一个文件就当成同一份敏感度对待）
- [ ] 持有 DB 账号的人**不应**同时具备读取这个密钥的权限（不同权限主体）
- [ ] **生成一次就存好，不要每次部署重新生成**——它与库中密文绑死
- [ ] 轮换该密钥会导致**全部存量密文无法解密**，须先用旧密钥导出明文、换钥后重新加密入库——**无回滚窗口，切勿随意轮换**

> ⚠️ **本地数据不要带去生产**：本地库里的上游 SK 与接入凭证是用测试密钥加密的，
> 换成生产密钥后一律解不开。生产应重新生成密钥 + 重新录入模型凭证 + 重新颁发接入凭证。

## 3. 构建与启动

```bash
mvn clean package        # JDK 17 + Maven；产物 target/modelgate-1.0.0-SNAPSHOT.jar
```

**推荐 JVM 参数**（依据 [09-压测方案](./09-压测方案.md)，按压测结果调整）：

```bash
java -Xms4g -Xmx4g -XX:MaxMetaspaceSize=256m \
     -XX:MaxDirectMemorySize=2g \
     -XX:+UseG1GC -XX:MaxGCPauseMillis=200 \
     -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump \
     -XX:+ExitOnOutOfMemoryError \
     -XX:ActiveProcessorCount=<容器CPU核数> \
     -jar modelgate.jar
```

系统层：`ulimit -n 65535`。

**端口与探针（K8s）**：

| 项 | 值 |
|---|---|
| 服务端口 | 10811（`application.yml` `server.port`；⚠️ 此前本表两次写错，先误写 8080、后误写 8088，探针配置照抄会连不上，以 `application.yml` 实际值为准） |
| liveness / readiness | `GET /actuator/health`（无需鉴权） |
| 指标抓取 | **已移除**（不接 Prometheus/Grafana，见 §5） |
| 副本 | 无状态，可水平扩展；限流/配额状态在 Redis，多副本一致 |

**启动成功判据**：日志最后几行是 `config/StartupBannerPrinter` 在 `ApplicationReadyEvent` 打出的
`ModelGate 启动成功`提示（含 Profile/Port/PID 与管理后台/业务入口/健康检查地址），
**打出来即代表可以收流量**（比 Spring 自己那行 `Started ModelGateApplication in ...` 更靠后，
也更容易在满屏 INFO 里找到）。需要静音：`modelgate.startup-banner.enabled=false`。

## 5. 监控与告警

> **⚠️ 本项目不接 Prometheus / Grafana**（决策见 [11 §18](./11-变更记录.md)）。
> `micrometer-registry-prometheus` 依赖、`metrics/GatewayMetrics`、`AuditService` 的 Gauge/Counter
> 埋点、`/actuator/prometheus` 与 `/actuator/metrics` 端点**均已移除**，
> 原先的 `modelgate_*` 指标一个都不存在了。
> **可观测性全部落在日志上**，告警请在日志采集侧（ELK/内网日志平台）按关键字配置。

### 5.1 关键日志告警项（替代原指标告警）

| 日志关键字 | 含义 | 告警建议 |
|---|---|---|
| `[AuditService] Queue full, dropping audit log` | 审计队列满、正在丢日志（行尾带累计丢弃数） | 出现即严重——DB 写入跟不上 |
| `[AuditService] Batch insert failed` | 审计批量落库失败，本批丢失 | 出现即严重 |
| `[CircuitBreaker] Circuit OPEN, fast-fail` | 熔断器已打开，正在快速失败 | 出现即警告 |
| `[CircuitBreaker] Upstream error: status=5xx` | 上游返回 5xx | 5 分钟内密集出现 → 警告 |
| `[CircuitBreaker] Upstream exception` | 上游连接异常/超时 | 同上 |
| `[CredentialAuth] Invalid credential` | 凭证校验失败 | 短时间大量出现 → 疑似暴力尝试 |

> 后两条 `Upstream *` 是本轮**新加**的：它们原先只打指标不打日志，Prometheus 拿掉后
> 上游故障会在日志里完全不可见，故补为 WARN。

### 5.2 JVM / 容器层

进程与 JVM 层面（内存、GC、线程、FD）**改由容器平台自带监控承担**，本进程不再自行暴露。
需要临时查看时用 `jstat` / `jmap` / `jstack` 直连进程。

### 5.3 日志通道

- Logback（`logback-spring.xml`），业务日志带 MDC `traceId`；响应头 `X-Trace-Id` 可反查。
  ⚠️ traceId 此前**恒为空**（WebFlux 跨线程 ThreadLocal 丢失），本轮已彻底修复，
  且覆盖管理面与业务流量全部请求；调用方可自带 `X-Trace-Id` 实现跨系统串联（见 [11 §16.2](./11-变更记录.md)）
- **审计现在是全量的**：被拒绝的请求（401/403/429）也会入 `mg_audit_log`，
  此类记录 `app_id` 为空——排查"谁在拿无效凭证反复试"就靠它（见 [11 §16.3](./11-变更记录.md)）
- 文件 appender 输出 JSON（logstash-encoder），便于 ELK 采集；告警关键字见 §5.1
- 注：`[AdminAuth] Invalid token` 已不存在（`AdminAuthFilter` 随管理面鉴权外移一并删除）

## 7. 已知设计取舍（风险登记，运维需知）

| 项 | 行为 | 影响 |
|---|---|---|
| 审计内存队列 | 进程崩溃丢失未刷盘记录（≤20万条）；队列满丢弃新记录 | 审计弱一致，主链路优先 |

### 7.1 超长请求相关的外部依赖（**投产前必须确认**，均不在本仓库）

内部模型处理复杂问题时实测可跑满 **20 分钟**才返回 `[DONE]`。网关侧已按"不设超时、
等模型响应"调整，但以下三项在网关之外，不确认就会出现"改了网关却没效果"：

| # | 待确认 | 不确认的后果 |
|---|---|---|
| 1 | **F5 / SLB 的 idle timeout 实际值**（最要紧） | `response-timeout` 已放宽到 1800s，但 SLB 若仍是 600s，**非流式**长请求照样在第 600 秒被网络设备砍断。排查时极易误判成网关没生效 |
| 2 | 容器平台 `terminationGracePeriodSeconds` 是否 ≥600s | `timeout-per-shutdown-phase` 已提到 600s，但平台默认 30s 会先 SIGKILL，改了等于没改 |
| 3 | 平台对 `/actuator/detection/available` 返回非 200 的处理：只摘流量还是重启容器？ | 只摘流量 → 可把 `modelgate.detection.available-always-200` 改为 `false`，draining 期间自动停发新流量；会重启容器 → 必须保持 `true`，改为要求平台在调 `/shutdown` 后等 N 分钟再发 SIGTERM |

### 7.2 已知取舍：慢调用熔断已整体关闭

`slowCallDurationThreshold: 24h` 让慢调用率恒为 0，**等同关闭**。
原因：本网关上游是 LLM，"跑得久"是正常业务形态而非故障，而
`CircuitBreakerFilter`(order -50) 量的是**响应体写完**的时长——
一条 1200s 的*正常* SSE 流会被记成"耗时 1200 秒的调用"，
最近 20 次里 18 次超阈值就会 OPEN 并用 503 拒绝真实流量。

> ⚠️ **不要"顺手"删掉这两行配置。** 删了会退回默认 `slowCallRateThreshold=100` +
> `slowCallDurationThreshold=60s`，而判定是 `slowCallRate >= threshold`；
> 本项目几乎每次调用都超过 60s ⇒ 慢调用率 100% ⇒ `100>=100` 成立 ⇒ **照样熔断，比原来更糟**。

**上游真故障仍会熔断**，靠的是 `failureRateThreshold`（5xx / 连接异常），那才对应"上游坏了"。

### 7.3 服务连通性探测可能对上游产生副作用

`mg_service.probe_method` 默认 `GET`（无副作用）。若录入者显式登记为 `POST`/`PUT`/`DELETE`，
点一次「🧪 测试」就会**真的调用**上游那个接口——若它是写操作会产生真实数据。
网关无法替业务判断哪个接口幂等，因此：
- 白名单外的方法一律回落 `GET`
- `GET`/`HEAD` 强制不带请求体
- **非 GET 探测服务端会打 WARN**：`[ServiceConnectivity] 使用非 GET 方法探测…`，
  排查脏数据来源时按这条日志查

## 8. 容量基线

- 设计基准：400 用户 ≈ 150 并发，连接池 500（扩到 800 用户时连接池改 800 并重估 JVM 堆）
- 审计存量：稳态 ≈ QPS × 86400 × 90（保留 90 天）；30 QPS ≈ 2.3 亿行，需评估分区或缩短 `retention-days`
- 单请求内存：BodyParseFilter 全量缓存请求体（≤10MB/请求），高并发大 body 场景按 09 文档压测确认
